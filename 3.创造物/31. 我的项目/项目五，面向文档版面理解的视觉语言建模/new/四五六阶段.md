# 阶段四
# 1. 这一阶段在做什么？

上一阶段 OCR-only 模型只看：

tokens

例如：

Name : John Smith Date : 2024

它不知道这些词在页面上哪里。

这一阶段模型要看：

tokens + bboxes_norm

也就是：

{  
  "tokens": ["Name", ": ", "John", "Smith"],  
  "bboxes_norm": [  
    [100, 120, 180, 150],  
    [185, 120, 195, 150],  
    [300, 120, 350, 150],  
    [355, 120, 420, 150]  
  ],  
  "labels": [  
    "B-QUESTION",  
    "I-QUESTION",  
    "B-ANSWER",  
    "I-ANSWER"  
  ]  
}

模型不仅知道：

John Smith 是文本内容

还知道：

John Smith 在 Name 的右边

这就是版面理解的核心。

---

# 2. 为什么这个阶段重要？

因为 FUNSD 是表单字段抽取任务。表单里的很多语义不是纯文本决定的，而是由 **文本内容 + 页面位置关系** 决定的。

例如：

Name: John Smith  
Date: 2024-01-01

纯文本模型看到：

Name Date John Smith 2024-01-01

有时还能猜出答案。

但如果表单变复杂：

Name        Date  
John Smith  2024-01-01

或者：

Applicant Name       John Smith  
Supervisor Name      Alice Brown

只看文本容易混淆。

而加入位置后，模型可以学到：

1. answer 经常在 question 的右侧或下方  
2. header 经常在页面上方或区域开头  
3. 同一行相邻 token 可能属于同一字段  
4. 不同区域的 answer 不应混在一起

所以这阶段的实验能回答一个关键问题：

> **坐标信息是否能提升 FUNSD 字段抽取效果？**

这会成为你报告里的一个核心对比：

OCR-only vs Text + Layout

---

# 3. 这个模型是不是视觉语言模型？

严格来说，这个阶段的模型还不是完整视觉语言模型，因为它没有直接使用图像像素。

它是：

文本 + 位置 baseline

或者叫：

layout-aware text baseline

它的位置在整个项目里是：

OCR-only baseline  
    ↓ 加入 bbox  
Text + Layout baseline  
    ↓ 加入 image  
LayoutLMv3

所以它是 OCR-only 和 LayoutLMv3 之间的桥梁。

---

# 4. 推荐实现方式

不要一上来自己复现 LayoutLM。这个阶段保持简单、可解释。

推荐结构：

BERT / DistilBERT 文本编码器  
+  
bbox 位置特征编码器  
+  
分类头

具体来说：

## 文本分支

输入 token：

["Name", ": ", "John", "Smith"]

经过 tokenizer 和 BERT / DistilBERT：

hidden_states: [batch, seq_len, hidden_size]

例如 hidden_size = 768。

---

## 位置分支

每个 token 有一个 bbox：

[x0, y0, x1, y1]

可以先归一化到 0~1000，然后输入一个小 MLP：

bbox: [4]  
→ Linear (4, 128)  
→ ReLU  
→ Linear (128, bbox_hidden_size)

得到：

bbox_features: [batch, seq_len, bbox_hidden_size]

---

## 融合方式

最简单的是拼接：

fused = concat (text_hidden, bbox_features)

然后分类：

classifier (fused) → label logits

例如：

text_hidden: 768  
bbox_feature: 128  
fused: 896  
num_labels: 7

最终输出：

O  
B-QUESTION  
I-QUESTION  
B-ANSWER  
I-ANSWER  
B-HEADER  
I-HEADER

---

# 5. 最容易出错的地方：bbox 和 subword 对齐

上一阶段你已经处理了 word-level label 到 subword label 的对齐。

这一阶段还多了 bbox 对齐。

原始 word：

unbelievable

被 tokenizer 切成：

un  
##believable

label 对齐可能是：

B-ANSWER  
-100

bbox 对齐建议是：

原 word 的 bbox 复制给所有 subword

例如：

un             bbox = [100, 100, 200, 130]  
##believable   bbox = [100, 100, 200, 130]

special token 的 bbox 用：

[0, 0, 0, 0]

比如 `[CLS]`、`[SEP]`、`[PAD]`。

所以本阶段必须保证：

input_ids 长度 == attention_mask 长度 == bbox_features 长度 == labels 长度

# 1. 这一阶段和前两个模型的关系

你现在已经有两个 baseline：

1. OCR-only  
   输入：tokens  
   不看 bbox，不看图像  
  
2. Text + Layout  
   输入：tokens + bboxes_norm  
   不看图像

下一阶段是：

3. LayoutLMv3  
   输入：tokens + bboxes_norm + image

它们构成非常清晰的对比链条：

|模型|文本|位置|图像|
|---|---|---|---|
|OCR-only|✅|❌|❌|
|Text + Layout|✅|✅|❌|
|LayoutLMv3|✅|✅|✅|

这就是你报告里“多模态输入对比”的核心。

---

# 2. LayoutLMv3 在做什么？

之前的 Text+Layout baseline 是你自己加了一个 bbox MLP：

BERT 文本 hidden states + bbox feature → classifier

而 LayoutLMv3 是专门为文档理解设计的模型。它会同时处理：

1. 文本 token  
2. token 对应的 bbox 坐标  
3. 页面图像 patch

对于 FUNSD 表单字段抽取任务，它要预测每个 token 的 BIO 标签：

O  
B-QUESTION  
I-QUESTION  
B-ANSWER  
I-ANSWER  
B-HEADER  
I-HEADER

所以这一阶段不是问答，也不是生成 Markdown，而是：

token classification / sequence labeling

---

# 3. 这一步为什么比前两步复杂？

主要复杂在三件事。

## 第一，输入多了 image

之前只需要 JSON 里的：

tokens  
labels  
bboxes_norm

现在还要读取：

image_path

所以每条样本要变成：

image + words + boxes + word_labels

---

## 第二，bbox 必须是 0-1000

LayoutLM 系列通常要求 bbox 是归一化后的整数坐标：

[x0, y0, x1, y1]，范围 0 到 1000

你上一阶段已经做了：

bboxes_norm

所以 LayoutLMv3 直接使用 prepared 数据即可。

---

## 第三，label 对齐交给 processor 处理更稳

LayoutLMv3 推荐用 processor 统一处理：

image  
tokens  
boxes  
word_labels

它会生成：

input_ids  
attention_mask  
bbox  
pixel_values  
labels

其中：

input_ids      文本 token id  
attention_mask 文本 mask  
bbox           token 坐标  
pixel_values   图像 patch 输入  
labels         BIO 标签

这比你手动处理 image + tokenizer 更稳。
