
# 一阶段
## 1. 这一步不是在训练模型

你现在要让 Claude Code 做的事情不是：

输入数据 → 训练模型 → 得到预测结果

而是：

FUNSD 原始文件  
→ 读取图片、OCR 文本、bbox、标签  
→ 清洗和统一格式  
→ 保存成 processed JSON  
→ 给后面的模型训练使用

所以这一步的目标是：

原始数据集能不能被程序稳定、正确、统一地读出来？

老师任务说明里第一项就是数据处理：读取文档图像、OCR 文本、文本框坐标和标签信息，并完成清洗、坐标归一化、排序、划分和统计。你的 FUNSD reader 就是完成这条主线的第一步。

---

## 2. FUNSD 数据集里有什么？

FUNSD 是一个表单理解数据集。它不是让你自己跑 OCR，而是数据集本身已经提供了类似 OCR 的标注结果。

每张表单图片通常配一个 annotation JSON，里面会有很多文本块，例如：

Name  
Date  
Invoice Number  
John Smith  
2024-01-02

每个文本块通常包含：

1. 文本内容 text  
2. 坐标 box / bbox  
3. 实体标签 label  
4. 有时还有 linking / relation 信息

在你这个项目里，我们第一阶段主要用：

image_path  文档图片路径  
tokens      OCR 文本 token  
bboxes      每个 token 对应的文本框坐标  
labels      每个 token 对应的字段类别标签

暂时可以不处理复杂关系 linking，因为你的主线是：

> 表单字段抽取 / token classification

---

## 3. 什么叫“字段抽取”？

比如一张表单里有：

Name: John Smith  
Date: 2024-01-02  
Total: $100

模型要判断每个 token 是什么角色。

例如：

|token|label|
|---|---|
|Name|QUESTION|
|:|QUESTION|
|John|ANSWER|
|Smith|ANSWER|
|Date|QUESTION|
|2024-01-02|ANSWER|

FUNSD 里常见实体类别包括：

question  
answer  
header  
other

但训练序列标注模型时，通常要转换成 BIO 格式：

B-QUESTION  
I-QUESTION  
B-ANSWER  
I-ANSWER  
B-HEADER  
I-HEADER  
O

BIO 的意思是：

B = Begin，某个实体的开始  
I = Inside，某个实体的内部  
O = Outside，不属于实体

例如：

Full Name: John Smith

可以变成：

Full      B-QUESTION  
Name      I-QUESTION  
:         I-QUESTION  
John      B-ANSWER  
Smith     I-ANSWER

为什么要 BIO？因为模型不仅要知道 token 属于什么类别，还要知道实体边界在哪里。

---

## 4. 这一步和三个模型的关系

你后面要比较三个模型：

1. OCR-only 文本模型  
2. 文本 + 位置模型  
3. LayoutLMv3 模型

这三个模型都要用同一份 processed 数据。

### OCR-only baseline 会用

{  
  "tokens": ["Name", ": ", "John", "Smith"],  
  "labels": ["B-QUESTION", "I-QUESTION", "B-ANSWER", "I-ANSWER"]  
}

它只看文字，不看坐标。

---

### 文本 + 位置 baseline 会用

{  
  "tokens": ["Name", ": ", "John", "Smith"],  
  "bboxes_norm": [[100, 120, 180, 150], ...],  
  "labels": ["B-QUESTION", "I-QUESTION", "B-ANSWER", "I-ANSWER"]  
}

它看文字，也看文本框位置。

---

### LayoutLMv3 会用

{  
  "image_path": "xxx. png",  
  "tokens": ["Name", ": ", "John", "Smith"],  
  "bboxes_norm": [[100, 120, 180, 150], ...],  
  "labels": ["B-QUESTION", "I-QUESTION", "B-ANSWER", "I-ANSWER"]  
}

它同时看：

文本 tokens  
位置 bboxes  
原始页面图像 image

所以你现在这一步做得越规范，后面三个模型就越容易复用。

---

理想情况下，执行完数据读取脚本后，会生成：

funsd_experiment/data/processed/train. json

funsd_experiment/data/processed/test. json

## 6. 这一步最重要的不是“代码多”，而是“对齐正确”

数据读取最容易出问题的地方是：

### 第一，token 和 label 必须一一对应

必须保证：

len (tokens) == len (bboxes) == len (labels)

如果 token 有 200 个，bbox 也必须 200 个，label 也必须 200 个。

否则训练时一定会报错，或者更糟糕：模型在错位数据上训练。

---

### 第二，bbox 必须和 token 一一对应

错误例子：

tokens: ["John", "Smith"]  
bbox:   [[100,100,200,130]]

这就不对，因为两个 token 只有一个框。

正确方式应该是：

tokens: ["John", "Smith"]  
bbox:   [[100,100,140,130], [145,100,200,130]]

或者如果 FUNSD 标注本身是 word 级别，就直接读取 word 级 bbox。

---

### 第三，标签要统一

FUNSD 原始标签可能是：

question  
answer  
header  
other

你的模型训练标签应该统一为：

B-QUESTION  
I-QUESTION  
B-ANSWER  
I-ANSWER  
B-HEADER  
I-HEADER  
O

也可以先在 reader 阶段保留原始标签，后面 preprocess 再转 BIO。  
但我建议这一步就先输出 BIO，因为后面模型训练更直接。



# 二阶段
## 1. 这一阶段到底在做什么？

上一阶段你得到的是：

funsd_experiment/data/processed/train. json  
funsd_experiment/data/processed/val. json  
funsd_experiment/data/processed/test. json

里面每条数据大概是：

{  
  "id": "000000",  
  "image_path": "...",  
  "width": 1000,  
  "height": 1294,  
  "tokens": ["Name", ": ", "John", "Smith"],  
  "bboxes": [[100, 120, 180, 150], ...],  
  "labels": ["B-QUESTION", "I-QUESTION", "B-ANSWER", "I-ANSWER"]  
}

现在第二阶段要把它升级成：

{  
  "id": "000000",  
  "image_path": "...",  
  "width": 1000,  
  "height": 1294,  
  "tokens": ["Name", ": ", "John", "Smith"],  
  "bboxes": [[100, 120, 180, 150], ...],  
  "bboxes_norm": [[100, 92, 180, 116], ...],  
  "labels": ["B-QUESTION", "I-QUESTION", "B-ANSWER", "I-ANSWER"],  
  "sort_strategy": "yx"  
}

也就是多做几件事：

1. 清洗坏数据  
2. 把 bbox 坐标归一化到 0-1000  
3. 按阅读顺序重新排序文本框  
4. 统计数据集特征  
5. 输出报告表格

---

## 2. 为什么要做 bbox 坐标归一化？

FUNSD 的 bbox 原始坐标是基于图片真实像素的，比如：

图片宽度 1000，高度 1294  
bbox = [100, 120, 180, 150]

但是不同文档图片的尺寸可能不一样。如果直接把原始像素坐标喂给模型，模型会受到图片大小影响。

所以 LayoutLM / LayoutLMv2 / LayoutLMv3 这一类模型通常使用统一坐标范围：

0 ~ 1000

归一化公式是：

x0_norm = int (1000 * x0 / width)  
y0_norm = int (1000 * y0 / height)  
x1_norm = int (1000 * x1 / width)  
y1_norm = int (1000 * y1 / height)

比如原图：

width = 1000  
height = 1294  
bbox = [100, 120, 180, 150]

归一化后大约是：

[100, 92, 180, 115]

这样模型看到的位置就不是“第 120 个像素”，而是“页面高度约 9% 的位置”。

这对表单字段抽取非常重要。因为很多字段不光靠文本判断，还靠位置判断。例如：

表头 header 往往在页面上方  
问题 question 往往在答案 answer 左边  
答案 answer 往往跟在 question 右侧或下方

---

## 3. 为什么要做文本框排序？

模型一般不是一次看到一整张图的二维结构，而是把文本 token 当成一个序列处理：

token_1, token_2, token_3, token_4, ...

所以 token 的顺序会影响模型理解。

如果顺序乱了，模型看到的可能是：

John, Date, Name, Smith, 2024

这很难学。

比较合理的阅读顺序应该是：

Name, John, Smith, Date, 2024

因此我们要实现至少两种排序策略：

1. original：保留 FUNSD 原始标注顺序  
2. yx：先按 y 坐标从上到下，再按 x 坐标从左到右

这一步后面还可以直接变成你的“拓展实验”之一：

> 比较不同文本框排序方式对字段抽取结果的影响。

这正好对应老师要求里的“位置信息利用优化”。

---

## 4. 为什么要做数据统计？

数据统计不是形式主义，它是后面报告和实验设计的依据。

你至少要知道：

1. train / val / test 各有多少样本  
2. 每个 split 有多少 token  
3. 每个类别有多少 token  
4. QUESTION / ANSWER / HEADER / O 是否类别不平衡  
5. 每页平均 token 数是多少  
6. 是否有页面 token 数超过 512  
7. 是否有空文本、异常 bbox、超出页面范围的 bbox  
8. OCR 噪声大概有哪些

为什么关注 `512`？

因为 BERT、LayoutLMv3 这类模型常见最大输入长度是：

512 tokens

如果一页超过 512，就会被截断。  
这会导致模型看不到页面后半部分内容，也会成为后面错误分析的重要原因。

# 三阶段
这是你项目里的第一个“真正训练模型”的阶段，但它有一个关键限制：

> **只用 OCR 文本，不用 bbox，不用图像。**

这样做的意义是：先建立一个最简单但合理的 baseline，后面才能证明“加入位置信息”和“加入图像信息”到底有没有提升。老师任务要求至少实现两类可比较基线，并完成训练/微调和指标评估，所以 OCR-only baseline 是整个实验对比链条的起点。

# 1. 这一阶段在做什么？

上一阶段你已经得到：

funsd_experiment/data/prepared/val. json  
funsd_experiment/data/prepared/test. json

里面有：

{  
  "tokens": ["Registration", "No.", "533"],  
  "bboxes": [[...], [...], [...]],  
  "bboxes_norm": [[...], [...], [...]],  
  "labels": ["B-QUESTION", "I-QUESTION", "B-ANSWER"]  
}

但是本阶段的 OCR-only 模型只读取：

tokens + labels

不用：

bboxes_norm

也就是说，它要学习：

No.          → I-QUESTION

它完全不知道这些词在页面左边、右边、上方还是下方。

# 2. 为什么要先做 OCR-only baseline？

因为你的最终实验不是单个模型，而是对比实验：

模型 A：OCR-only 文本模型  
模型 B：文本 + bbox 位置模型  
模型 C：LayoutLMv3 文本 + 位置 + 图像模型

如果你一上来只做 LayoutLMv3，报告里只能说：

LayoutLMv3 效果不错。

但不能证明：

是文本起作用？  
是位置起作用？  
是图像起作用？  
还是模型更大所以起作用？

有了 OCR-only baseline，你后面就可以写：

OCR-only 已经能识别一部分 question / answer；  
加入 bbox 后 answer 与 question 的边界更稳定；  
LayoutLMv3 进一步利用图像和布局，对 header 或复杂区域提升更明显。

这就是“实验路线”的核心。

---

# 3. 这个模型本质上是什么？

这一步是一个 **token classification** 任务。

Hugging Face 官方文档对 token classification 的描述是：给句子里的每个 token 分配一个标签，NER 是最常见的 token classification 任务之一。你的 FUNSD 字段抽取和 NER 很像，只不过标签不是人名、地名，而是 `QUESTION / ANSWER / HEADER / O`。

所以模型输入是：

tokens:  
["Name", ": ", "John", "Smith"]

模型输出是：

labels:  
["B-QUESTION", "I-QUESTION", "B-ANSWER", "I-ANSWER"]

Hugging Face 的课程也说明，做 token classification 时通常使用 `AutoModelForTokenClassification`，并配置 `id2label` 和 `label2id` 来保存标签映射。

---

# 4. 最重要的知识点：word-level label 和 subword tokenization

FUNSD 的标签通常是 word 级别：

tokens: ["Registration", "Number"]  
labels: ["B-QUESTION", "I-QUESTION"]

但是 BERT / DistilBERT tokenizer 可能会把一个 word 切成多个 subword。

例如：

"Registration" → ["registration"]

或者：

"unbelievable" → ["un", "##believable"]

这时标签怎么对齐？

常见做法是：

原始 word:      unbelievable  
subword:       un, ##believable  
label:         B-ANSWER, -100

`-100` 的意思是：训练 loss 忽略这个位置。

为什么要忽略后续 subword？  
因为原始标注只给了 word 一个标签，如果每个 subword 都重复标签，训练时长词会被重复加权，不太公平。

所以这个阶段最容易出 bug 的地方就是：

tokens、subword tokens、labels 的对齐

Claude Code 必须认真处理这个。

# 5. 本阶段建议用哪个模型？

建议先用：

distilbert-base-uncased

原因：

1. 比 bert-base-uncased 小；  
2. 训练快；  
3. 足够作为 OCR-only baseline；  
4. 后面重点模型是 LayoutLMv3，不必在第一个 baseline 上耗太多资源。

也可以保留配置项，允许改成：

bert-base-uncased

但是默认建议 DistilBERT。
