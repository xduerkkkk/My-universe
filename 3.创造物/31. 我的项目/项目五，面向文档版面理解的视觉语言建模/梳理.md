# 把 PDF 或图片变成页面图”到底是什么意思？

意思是：

> **把 PDF 的某一页变成一张普通图片，比如 PNG/JPG，或者变成一个 OpenCV/Numpy 可以处理的像素矩阵。**

比如：

paper. pdf 第 1 页  
→ page_001. png  
→ shape = [高度, 宽度, 3]  
→ 后续可以送进 OCR、版面检测模型、VLM


所以“PDF 转页面图”的本质是**渲染**：

PDF 页面描述  
→ 按指定 DPI/缩放比例绘制成像素  
→ 得到一张页面截图

PyMuPDF 就是常用工具。它的文档里说，文档页面图像在 PyMuPDF 中表示为 Pixmap，可以通过 `Page.get_pixmap()` 从页面创建；Pixmap 本质上就是矩形像素集合。

所以这一步通常用：

PyMuPDF / fitz  
pdf2image  
poppler

而不是 PaddleOCR。

举个例子：

如果 PDF 是 LaTeX 论文导出的，文字可以复制，那你可以用 `pypdf` 直接提取文本。

如果 PDF 是扫描件，文字只是图片的一部分，那 `pypdf` 基本没法读出文字，就要：

PDF → 页面图片 → OCR



# OCR 准确来说是什么意思？

OCR = **Optical Character Recognition，光学字符识别**。

准确地说，现代 OCR 通常不是一步，而是两步或多步：

图片  
→ 文本检测：哪里有字？  
→ 文本识别：这些字是什么？  
→ 可选：方向矫正、版面排序、后处理

比如一张图片里有一句话：

基于视觉语言模型的文档理解

OCR 系统会先找到这行文字的区域：

{  
  "bbox": [100, 250, 700, 290]  
}

然后识别内容：

{  
  "text": "基于视觉语言模型的文档理解",  
  "score": 0.98  
}

PaddleOCR 的文本检测模块文档也说，文本检测模块负责定位图像中包含文字的区域，并通常输出文字区域的 bounding boxes，再交给文本识别模块进一步处理。

所以 OCR 的核心输出通常是：

{  
  "text": "识别出的文字",  
  "bbox": [x1, y1, x2, y2],  
  "confidence": 0.97  
}

# PP-Structure 和 PaddleOCR 是一个意思吗？

不是。

更准确地说：

> **PaddleOCR 是一个大工具箱 / 项目；PP-Structure 是 PaddleOCR 里的文档结构化解析 pipeline。**

可以这样理解：

PaddleOCR  
├── 普通 OCR：文本检测 + 文本识别  
├── 表格识别  
├── 版面分析  
├── 关键信息抽取  
├── 文档解析  
└── PP-Structure / PP-StructureV3

PP-Structure 做的不是单个 OCR 功能，而是一个复杂文档解析流程。官方文档描述它的版面分析任务时说，图像会先经过版面分析模型，被划分为 text、table、figure 等不同区域；表格区域送入表格识别模块，文本区域送入 OCR 引擎，最后再做版面恢复。

所以你说得很对：

> PP-Structure 不是“到哪都的一个功能”，而是一个 pipeline。

它的流程大概是：

文档图片  
→ 版面分析：标题/正文/表格/图片等区域  
→ 文本区域：OCR  
→ 表格区域：表格结构识别  
→ 图片区域：保留或描述  
→ 版面恢复：输出结构化结果

# 5. “作为基线方法”是什么意思？

这里的 baseline 就是：

> **对比方法 / 参考方法 / 起点方法。**

不是说我们一定要仿照它，也不是说它就是我们的创新。

它的作用是回答：

> 我的方案相比现成工具，有没有改进？  
> 哪些场景更好？  
> 哪些场景更差？  
> 引入 VLM 后有没有带来收益？

比如你可以设置三组实验：

Baseline A：PP-Structure  
Baseline B：纯 Qwen2.5-VL 端到端解析  
Our Method：版面检测 + OCR + 局部 VLM + 结构化生成

然后比较：

版面检测准确率  
表格解析质量  
Markdown 还原质量  
问答准确率  
证据定位准确率  
运行速度  
输出稳定性

所以 baseline 的意义是**做参照系**。

如果你只做自己的系统，没有 baseline，老师会问：

> 你怎么证明这个系统有效？

但如果你说：

> 我用 PP-Structure 作为基线，和我的混合式 VLM 文档解析流程做对比。

这就像一个完整实验了。


# 那为什么不用 OCR 文本 + LLM？为什么要 VLM？

很多情况下，**确实可以只用 OCR + LLM**。

比如纯文字问题：

这篇文章的摘要是什么？  
作者提出了什么方法？  
实验用了哪些数据集？

如果 OCR 文本质量好，那流程可以是：

OCR 带坐标文本  
→ LLM  
→ 回答  
→ 用 bbox 做证据定位

这完全合理。

但 VLM 的作用出现在这些场景：

## 场景一：问题依赖视觉内容

用户问：

图 3 中的曲线趋势说明了什么？  
这个流程图表达了什么步骤？  
这张页面里哪个模块最重要？

OCR 只能读出图里的文字，不能完整理解图的视觉结构。

这时要用 VLM 看图或看裁剪区域。

## 场景二：复杂表格/版面结构 OCR 读乱了

很多论文是双栏结构，OCR 可能输出成：

左栏第一行  
右栏第一行  
左栏第二行  
右栏第二行

阅读顺序就乱了。

VLM 可以看整页视觉布局，辅助判断：

先读左栏，再读右栏  
标题在上方  
图注属于下方图片  
表格横跨两栏

当然，最终排序最好还是结合版面检测和规则做，不要完全依赖 VLM。

## 场景三：图片区域没有文字

比如文档里有一张缺陷检测图、遥感变化图、神经网络结构图。

OCR 输出可能是空的。

但 VLM 可以回答：

这张图展示了模型整体架构。  
左侧是输入图像，中间是特征提取模块，右侧是分类输出。

这就是 OCR 做不到的。

---

## 场景四：需要局部视觉理解

你的系统不一定把整页都丢给 VLM，而是：

版面检测发现一块区域是 table/figure/formula  
→ 裁剪该区域  
→ 只把这个局部图像交给 VLM  
→ 让 VLM 解释这个区域

这比整页 VLM 更省、更稳定。

# 最终流程
PDF / 图片  
↓  
如果是 PDF：用 PyMuPDF/pdf2image 渲染成页面图  
↓  
版面检测：找到 title/text/table/figure/formula 等区域  
↓  
OCR：对文本区域识别文字，得到 text + bbox  
↓  
表格区域：用表格识别或 VLM 解释  
↓  
图片/图表区域：裁剪后交给 VLM 理解  
↓  
结构化整合：生成 JSON / Markdown  
↓  
LLM 问答：基于结构化文本和 VLM 区域描述回答问题  
↓  
证据定位：返回 page_id + bbox  
↓  
前端高亮

可以记成一句话：

> **OCR 负责读字，版面检测负责找块，VLM 负责看图理解，LLM 负责组织答案。**


假设上传一页论文：

标题  
两栏正文  
一张模型结构图  
一个实验结果表格

## OCR 输出：

[  
  {  
    "text": "A Vision-Language Model for Document Understanding",  
    "bbox": [100, 60, 900, 120]  
  },  
  {  
    "text": "Table 1. Comparison of different models...",  
    "bbox": [120, 600, 900, 640]  
  }  
]

OCR 可以读字，但不一定知道表格在比较什么。

## 版面检测输出：

[  
  {  
    "type": "title",  
    "bbox": [100, 60, 900, 120]  
  },  
  {  
    "type": "figure",  
    "bbox": [100, 250, 900, 520]  
  },  
  {  
    "type": "table",  
    "bbox": [100, 600, 900, 850]  
  }  
]

它知道哪里是图、哪里是表。

## VLM 对表格区域输出：

{  
  "region": "table_1",  
  "summary": "该表格比较了不同模型在准确率和 F1 上的表现，其中 Model B 效果最好。"  
}

## LLM 最终回答：

用户问：

哪个模型效果最好？证据在哪？

系统答：

Model B 效果最好，因为它在 Accuracy 和 F1 两个指标上都高于其他模型。  
证据位于第 1 页 Table 1 区域。

前端高亮：

{  
  "page": 1,  
  "bbox": [100, 600, 900, 850]  
}

这就是完整闭环。

# 对比实验 
## 这三者到底有什么区别？

### A. 纯 OCR / 传统文档解析 pipeline

流程：

PDF/图片  
→ 版面分析  
→ OCR  
→ 表格识别  
→ Markdown/JSON

优点是：

便宜  
稳定  
速度快  
有 bbox 坐标  
容易批量处理  
容易评测

缺点是：

不真正理解图表  
不理解图片语义  
复杂表格容易乱  
双栏阅读顺序可能错  
公式、流程图、科研图理解弱

比如它能读出：

Model A Accuracy 91.2  
Model B Accuracy 93.8

但它不一定能总结：

Model B 在主要指标上优于 Model A。

PP-StructureV3 官方文档本身也说明，它是一个由版面区域分析、OCR 子流程，以及可选的表格识别、公式识别、图像预处理等模块组成的 pipeline，不是单一 OCR 功能。

---

### B. 纯 VLM 端到端解析

流程：

PDF 页面图片  
→ Qwen2.5-VL / GPT-4o / Gemini / InternVL 等 VLM  
→ 直接让它输出 Markdown/JSON/答案

优点是：

语义理解强  
能看图、看表、看流程图  
能解释图表含义  
能直接回答自然语言问题

缺点是：

成本高  
多页文档处理难  
输出格式不稳定  
可能幻觉  
bbox 证据定位弱  
批量处理不一定划算

比如它能回答：

图 2 展示了模型整体架构。

但它也可能把图里没有的模块“脑补”出来，或者输出的 JSON 格式前后不一致。

IBM 介绍 Granite-Docling 时也提到，通用 VLM 做 OCR/文档转换会有不稳定问题，而可靠企业级流程需要避免单个错误影响整体工作流。

---

### C. OCR + VLM 混合式解析

流程：

PDF/图片  
→ OCR/版面分析拿到文字、区域、坐标  
→ 对表格、图表、图片、复杂区域裁剪  
→ VLM 只理解关键视觉区域  
→ LLM 整合为 Markdown/JSON/问答答案  
→ 返回证据 bbox

优点是：

比纯 OCR 更懂语义  
比纯 VLM 更稳定  
比纯 VLM 成本低  
能保留 bbox 证据定位  
能解释表格、图表、图片  
更适合做可视化系统

这就是你的课题真正有意义的地方。

结论：

> 双栏/图表页面，混合式更稳。

### 例子三：实验结果表格

纯 OCR 能读出表格文字，但表格结构可能丢：

Model Accuracy F1 A 91.2 88.5 B 93.8 90.1

纯 VLM 能解释：

B 模型更好。

但它可能漏数字或编错数字。

混合式可以：

OCR/表格识别保留数字  
VLM/LLM 解释趋势  
回答时高亮表格 bbox

结论：

> 表格任务需要 OCR 的精确性 + VLM/LLM 的语义解释。

---

### 例子四：流程图 / 模型结构图

纯 OCR 只能读图中文字：

Input  
Encoder  
Decoder  
Output

但不理解箭头关系。

纯 VLM 可以解释流程图。

混合式可以：

OCR 读取图中文字  
VLM 理解箭头、模块关系、整体含义  
最终生成图说明

结论：

> 图像语义区域必须用 VLM。

---

### 例子五：需要证据定位的问答

用户问：

哪个模型效果最好？证据在哪？

纯 OCR + LLM 可以回答，但证据可能只是文本片段。

纯 VLM 可以回答，但不一定给稳定 bbox。

混合式可以回答：

Model B 最好，证据来自第 3 页 Table 2 区域，bbox=[...]

并在网页上高亮。

结论：

> 证据定位是混合式系统的重要价值。
