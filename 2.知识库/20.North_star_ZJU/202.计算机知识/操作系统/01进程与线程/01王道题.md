	在 Linux 世界里，任何一个进程死掉后，都必须由它的“父亲”来收尸（调用 `wait()` 或 `waitpid()` 系统调用，读取子进程的退出码并销毁它的 PCB 遗体）。如果父亲先死了，孤儿进程要是没人管，等它运行结束时就会变成永远无法销毁的“僵尸进程”，白白占用 PID 资源。

54. D 
    线程同步可以导致用户级线程切换
    承接上面的用户级线程（ULT）模型。假设进程 A 内部有线程1 和线程2，它们都在用户态运行，内核只看得到进程 A。
	
	1. **发生同步：** 线程1 运行到一半，发现需要一把锁（或者一个信号量），而这把锁目前被线程2 拿走了。线程1 必须等待（同步）。
	    
	2. **触发切换：** 线程1 放弃执行，它并没有调用操作系统的系统调用去让自己阻塞（因为如果它调用了阻塞系统调用，内核会把**整个进程 A** 都挂起，线程2 也没得跑了）。
	    
	3. **用户态偷梁换柱：** 线程1 只是调用了线程库内部的函数。线程库的代码（运行在用户态）迅速把线程1 的寄存器保存到它在用户空间自己开辟的“用户态 TCB”里，然后把线程2 的上下文加载到 CPU 上。
	    
	
	整个过程中，CPU **从来没有切换到内核态**，操作系统内核对此一无所知，它只看到进程 A 在老老实实地执行指令，但实际上进程 A 内部已经悄悄完成了从线程1 到线程2 的华丽转身。这就是“线程同步导致用户级线程切换”。

	**导致创建新进程的场景在工业界和教科书里只有以下 4 种**（背下这个四分法，秒杀所有题）：
	
	1. **用户登录（User Login）：** 用户输入密码登录成功，系统必须为他开辟一个专属的家园（在 Linux 下是拉起一个 `bash` 进程，在 Windows 下是拉起 `explorer.exe` 桌面进程）。

	3. **操作系统提供服务（OS Service）：** 系统内核主动发起的。比如你插上打印机，系统检测到了，主动创建为一个“打印后台服务进程”来伺候你。
	    
	4. **应用请求创建（Process Spawning）：** 现有的老进程自己生儿子。比如多进程 Web 服务器（如 Nginx）为了并发处理请求，自己调用 `fork()` 创造出子进程。

72. ?D?<font color="#ff0000">!!</font>
	![[01王道题-1769001457504.jpeg]]系统调用是用户程序发出的请求，自然也要回归到用户态
	“执行系统调用”，难道不是说执行一段内核的程序吗？为什么导致 CPU 从内核态转为用户态？那阻塞进程，唤醒进程，执行 CPU 调度，对内核态用户态有转化吗
	题目问的是：下列操作**完成时**，导致 CPU 从内核态转为用户态的是？
	
	这意味着，这个操作的最后一版汇编指令执行完的瞬间，CPU 的硬件指针必须刚好掉回用户态（Ring 3）。
	
	### D. 执行系统调用（为什么它是绝对正确的金标准）
	
	- **过程：** 用户进程在用户态调用 `read()` $\rightarrow$ 触发软中断陷入内核 $\rightarrow$ 内核执行对应的系统调用内核程序。
	    
	- **完成时的瞬间：** 当这个系统调用把活全部干完、准备结束（完成）的时候，它调用的最后一条指令必然是 **中断返回指令（如 `iret` 或 `sysret`）**。
	    
	- **结果：** 这条指令一旦执行完毕，CPU 硬件立刻被强行拨回**用户态**。所以，系统调用的“完成”和“返回用户态”是同一个绑定动作。
	    
	
	### A. 阻塞进程（为什么完成时不切用户态）
	
	我们来看内核里 `block()` 这个函数执行完时在干嘛：
	
	- **场景：** 进程 A 发现读不到数据，陷入内核，内核调用内部的 `block(process_A)` 函数。
	    
	- **执行：** 内核把进程 A 的状态改成阻塞态，把它挂到等待队列里。
	    
	- **完成时的瞬间：** `block()` 函数的代码执行到最后一行大括号 `}` 结束了。**此时，CPU 能回到用户态吗？** 绝对不能！因为进程 A 已经被阻塞了，用户态现在没有任何程序可以返回。
	    
	- **接下来的动作：** `block()` 完成后，内核会立刻在内核态内部调用 `schedule()`（调度函数）去物色下一个倒霉蛋。也就是说，**`block()` 完成的瞬间，CPU 依然百分之百滞留在内核态**。
	    
	
	### B. 执行 CPU 调度（为什么完成时不切用户态）
	
	我们再看内核里 `schedule()` 这个函数执行完时在干嘛：
	
	- **执行：** 内核的调度程序在就绪队列里挑挑拣拣，终于选出了进程 B。
	    
	- **完成时的瞬间：** 调度算法算完了，`schedule()` 业务结束。此时它只是在内核里**选好了人**，CPU 的特权级依然是内核态。
	    
	- **接下来的动作：** 接下来内核要执行的是**进程上下文切换（Context Switch）**，去恢复进程 B 的寄存器。只有等这些切换脏活全干完、最后执行进程 B 的中断返回时，才会切回用户态。所以调度本身的“完成”并不直接导致切态。
	    
	
	### C. 唤醒进程（为什么完成时不切用户态）
	
	- **场景：** 键盘或者磁盘一震动，触发了硬件中断，CPU 陷入内核。内核的 `wakeup(process_A)` 函数开始干活。
	    
	- **执行：** 内核把进程 A 从等待队列里捞出来，放回就绪队列，改写它的 PCB 状态为“就绪”。
	    
	- **完成时的瞬间：** `wakeup()` 函数最后一行代码执行完。此时，CPU 还在中断处理程序里呢！内核接下来可能要继续处理剩下的中断后半部，或者转去执行调度。
	    
	- **结果：** `wakeup()` 完成的瞬间，**CPU 依旧在内核态里忙活**，它并没有直接一脚跨进用户态。

### 1. 软件实现方法（著名的“老四样”）

- **单标志法（严格轮流转）：**
    
    - ❌ **违反“空闲让进”：** 如果现在临界区空闲，本该轮到进程 A 进，但进程 A 此时根本不想进；那即使进程 B 疯狂想进，也只能在外面干等。
        
- **双标志先检查法：**
    
    - ❌ **违反“忙则等待”：** 两个进程可能同时检查到对方没加锁，然后同时加锁、同时冲进临界区，直接翻车。
        
- **双标志后检查法：**
    
    - ❌ **违反“空闲让进”和“有限等待”：** 两个进程可能同时先把自己的锁锁上，然后互相发现对方也锁了，于是在外面互相谦让，导致谁也进不去（死锁）。
        
- **Peterson 算法（软件完美版）：**
    
    - 满足了前三个（空闲让进、忙则等待、有限等待）。
        
    - ❌ **违反“让权等待”：** 进不去的那个进程，会在最后一行 `while(flag[turn] && turn == winner);` 里卡住忙等，不停地消耗 CPU 寿命。
        

### 2. 硬件实现方法

- **TSL 指令 / SWAP 指令（硬件自旋锁）：**
    
    - 满足了前三个（安全、不给数据写崩）。
        
    - ❌ **违反“让权等待”：** 拿不到锁的进程卡在 `while(TSL(&lock));` 里疯狂吃 CPU（自旋）。
        

### 3. 信号量机制

- **整型信号量：**
    
    - 满足了前三个。
        
    - ❌ **违反“让权等待”：** 资源不够时，卡在 `while(S <= 0);` 里忙等。
        
- **记录型信号量（现代完全体）：**
    
    - **同时满足全部四个原则！**
        
    - ✨ **为什么？** 因为它在资源不够时，内部代码执行了 `block()` 原语，让进程直接去阻塞队列里闭眼睡觉（让出 CPU 权力），等资源够了再由别人执行 `wakeup()` 叫醒它。
