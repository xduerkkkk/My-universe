进程组成
- PCB：给OS看的（这个OS，操作系统内核，有点抽象。怎么具体？OS应该就是代码！PCB就是OS这个代码能认识的数据结构）

- 动态：进程 以时间角度来看  每时每刻不可能都一样 有可能正在运行 有可能堵塞 有可能 没运行
- 结构性：这个有点废话了  由进程组成可知

# 进程的状态

按时间角度
首先进程得被初始化 程序段、PCB都得被加载（<font color="#ff0000">数据段空间仍然会被分配，只是此时未填充具体数据</font>）
那么此时就是，**创建态**

接着，创建好了自然而然就可以被CPU拿去 CPU会运行程序的此时这个状态（CPU还没拿） 叫**就绪态**表示我已经准备好被CPU拿去运行了

被CPU运行的过程就叫**运行态**
运行时，若出现什么需要外部资源的情况即此刻我这个进程运行不下去了自然而然，变成阻塞态被CPU踢下去 CPU此时会拿其他就绪态。

如果等了会时间，需要等待的东西好了，进程又说“我准备好被CPU拿去运行了”
此时就变成**就绪态**。

运行变阻塞是主动,   **因为是进程执行代码,明确知道接下来我要数据,这行代码是主动发起系统调用请求挂起**

当然如果进程完了，就叫，结束态,等着cpu回收资源

那么状态之间的转换
- 创建到就绪 显然
- 就绪 到运行   
- 运行到阻塞  
- 阻塞到就绪 
- <font color="#ff0000">漏了一个</font>，**运行也能到就绪**。*是因为CPU调度算法  不给你运行太长时间*  <font color="#ff0000">再加一个，抢占。</font>


进程之间的组织  就说 我们有很多进程  比如一堆就绪态排队 到底咋排？
一种是链表 这样好处就是 相当于一个优先队列
一种是索引 这样就 比较清晰 想拿哪个拿哪个 


# 进程的控制

那么，我们进程既然状态是时刻有可能切换的，  但我们每次切换可能有多个步骤
比如，阻塞态切换到就绪态时，还要把阻塞态移动到就绪态队列，可能还有xx操作等等像这种对于一个动作必须连带着有多个动作的情况，就会出现问题。 

即以时间为角度，动作的间隙出问题！  比如刚把阻塞态切换到就绪态，还没来得及移动队列呢，就有东西读取阻塞态队列。那不就糟糕了， 我实际上已经就绪了，却被读出“堵塞”。
所以我们希望，这些动作都是一口气完成，没有动作间隙被其他东西误解。

那么，我们控制，就用的“原语”
其实，动作间隙的时候还有其他动作发生，应该叫“中断”？ 
或者我感觉 这是很自然的？ 不对  CPU只有一个核的话，那确实，应该是动作间隙的瞬间，CPU又运行其他程序，比如读取阻塞队列了。
所以，我们的原语，就是“关中断”指令 + “恢复中断”指令，把我们的系列动作夹在中间。
这样就肯定没有别的程序打扰 CPU就一直运行此进程，一直做一系列动作了。

# 同步互斥概念
俩个进程为同步关系：意为俩进程是合作地，共同实现一个最终目标。**双方都知道对方的存在**，可以主动协调好顺序。
同步亦称“直接制约”

俩个进程为互斥关系，则是说俩进程都要对临界资源访问，这是一种被动的，不得不互斥的关系，他们开始的时候**不知道对方的存在**，它们之间**没有合作目的**，只是因为竞争同一个资源，所以产生了制约关系。

称“间接制约”

在某种程度上，**互斥可以看作是一种极其特殊的同步**。当你用代码（比如信号量 Semaphore）去实现互斥时，你其实也是在让进程之间进行“同步”——只不过这时候同步的唯一目的，仅仅是为了保护资源，而不涉及更复杂的业务逻辑协作。

设计信号量，是为了控制进程之间的执行关系；它既可以用来实现同步，也可以用来实现互斥。同步和互斥不是先后关系，而是两种不同的进程制约关系。


- 空闲让进，激进一点的理解，只要临界区空闲了，应该立马有进程访问
- 忙则等待，临界区在被访问时，其他想访问的进程需等待
- 有限等待，一定不能让想访问的进程一直等待
- 让权等待，如果一个进程得到了进临界区的机会，但却进不了临界区，应立马把机会让给别人




## 软件实现
单标志法
```
int flag = 0;

A进程：
while(flag!=0);
访问临界资源;
flag = 1;

B进程:
while(flag!=1);
访问临界资源;
flag = 0;
```

不满足空闲让进，同时不满只让权等待？


双标志先检查
```
bool flag[2];
flag[0] = false;
flag[1] = false;

A进程：
while(flag[1]);
flag[0] = true;
访问临界区;
flag[0] = false;

B进程：
while(flag[0]);
flag[1] = true;
访问临界区;
flag[1] = false;

```
相对于单标志，满足让权等待，不存在空转的状态？
但是缺点也有，就是检查和上锁若不是原子语句，则可能出现同时访问临界区。
同时访问的操作一般称为“忙则等待”

双标志后检查
```
bool flag[2];
flag[0] = false;
flag[1] = false;

A进程：
flag[0] = true;
while(flag[1]);
访问临界区;
flag[0] = false;

B进程：
flag[1] = true;
while(flag[0]);
访问临界区;
flag[1] = false;

```
虽解决先检查的忙则等待，但没解决“空闲让进”，因为有可能 `flag[0] = true; 紧接着跳到 flag[1] = true;` 

Peterson 算法
```
bool flag[2];
int turn = 0;

flag[0]=true;
turn = 1;
while(flag[1]&&turn==1)
```
不满足让权等待

# 死锁
产生死锁的条件，四个必须都满足
- 互斥
- 不剥夺条件：资源是主动释放，无抢占
- 请求和保持条件：若进程已保持了一个资源，但又提出新请求，但请求无效（因资源被别的进程占用），此时他仍然对自己已有的资源保持不放
- 循环等待条件：存在一种资源的循环等待链
