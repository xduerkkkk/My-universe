> [!abstract] 章节主线
> OS 一方面向下管理 CPU、内存、设备与文件，另一方面向上通过系统调用提供受保护的服务。理解本章要抓住三条线：**并发与系统类型 → 用户态/内核态与中断接口 → 内核结构、启动和虚拟化边界**。

## 1. OS 的职责与接口层次

| 概念 | 本质 | 典型例子 | 常见误区 |
|---|---|---|---|
| 操作系统内核 | 管理硬件资源、提供保护与抽象 | 调度、内存管理、中断、文件系统核心 | 把所有系统软件都算作内核 |
| 系统调用 | 用户程序进入内核服务的受控入口 | read、write、fork | 与普通函数调用或命令混同 |
| 库函数 | 用户态 API 和封装 | printf、malloc、sin | 认为每个库函数都必然陷入内核 |
| 系统命令 | 可由 Shell 启动的程序 | ls、mkdir、tasklist | 把命令名当成系统调用名 |
| 编译器、Shell | 通常运行在用户态的系统软件 | GCC、Bash、PowerShell | 因为“系统”二字就归入内核 |

- OS 可以把源程序作为文件管理，但通常不负责理解源代码的业务语义。
- “由 OS 完成”在 408 中通常指内核或其初始化代码完成，不是指任何运行在用户态的软件。

## 2. 并发、并行与系统发展

### 并发与并行

- **并发**：多个任务的执行时间区间重叠，在一段时间内共同推进。
- **并行**：多个任务在同一物理时刻由不同执行单元同时执行。
- 单核可并发但通常不能真正并行执行多个普通指令流；多核可同时具备并发与并行。

### 系统类型对比

| 系统 | 主要目标 | 典型机制 | 主要局限 |
|---|---|---|---|
| 单道批处理 | 自动连续处理作业 | 作业成批提交 | CPU 与 I/O 难重叠，资源利用率低 |
| 多道批处理 | 吞吐量、资源利用率 | 多道程序驻留内存、并发执行 | 交互性差，周转时间不直观 |
| 分时系统 | 较短响应时间、公平交互 | 时间片轮转、动态调度 | 切换频繁，吞吐量未必最高 |
| 实时系统 | 截止时间和可靠性 | 优先级、定时和可预测调度 | 设计关注最坏情况而非平均速度 |

> [!warning] 校正
> - “进程越多，CPU 利用率一定越低”不成立。适度提高多道程序度可掩盖 I/O 等待；过高才可能因换页、调度和争用导致性能下降。
> - “I/O 设备永远在工作”也不成立。多道程序只能提高设备被利用的概率，不能保证持续忙碌。

## 3. 用户态、内核态与指令权限

### 判断特权指令的底层逻辑

如果用户程序执行某指令后可以直接影响全局硬件、其他进程或保护边界，该指令通常必须受特权级控制。

| 类别 | 通常权限 | 原因 |
|---|---|---|
| 直接 I/O、关中断、设置页表/控制寄存器 | 内核态 | 可影响全系统资源与安全 |
| 陷入/访管指令 | 用户态可执行 | 用于合法、受控地请求内核服务 |
| 算术、逻辑、普通转移、一般数据传送 | 用户态可执行 | 只在当前程序授权范围内计算 |

- 用户态不能直接修改特权位，需通过系统调用陷入、异常或外部中断进入内核。
- 教材的“广义中断”可包含外中断与内中断；精确答题时应写明是中断、异常还是陷入。

## 4. 系统调用、普通调用与中断响应

### 系统调用流程

1. 用户程序准备系统调用号和参数。
2. 执行陷入/系统调用指令。
3. 硬件切换到内核入口并保存最小返回现场。
4. 内核检查参数、执行服务，必要时阻塞或调度。
5. 恢复现场并通过受控返回指令回到某个用户进程。

### 保存责任

| 状态 | 典型保存者 | 说明 |
|---|---|---|
| 返回地址/断点、必要状态字 | 硬件机制 | 体系结构规定的最小现场 |
| 通用寄存器、扩展上下文 | 内核入口代码 | 保存可能被处理程序改写的状态 |
| TLB 地址空间状态 | 体系结构 + OS | 切地址空间时可能刷新，也可用 ASID/PCID 区分 |

> [!warning] 条件与边界
> - 外中断可以在 CPU 处于用户态或内核态时到来；是否响应取决于屏蔽和优先级。
> - “断点”是恢复执行所需地址，不必然等于陷入指令本身地址。
> - 普通过程调用也可能按调用约定保存多个寄存器，不能只背“只保存 PC”。

### 时钟中断与时间片

**周期性时钟中断 → 更新时间、CPU 计时和定时器 → 剩余时间片可能减一 → 达到调度条件后才可能触发调度。**

时钟中断、时间片耗尽、进程切换是三个不同层次的事件。

## 5. OS 结构

| 结构 | 典型特点 | 优点 | 代价 |
|---|---|---|---|
| 分层式 | 上层调用下层，接口明确 | 易验证、结构清晰 | 层次固定，跨层开销与灵活性问题 |
| 大内核/宏内核 | 较多服务处于内核空间 | 调用路径短、性能通常较高 | 故障隔离和维护难度较大 |
| 微内核 | 保留最小机制，服务更多在用户态 | 隔离、扩展、移植较好 | IPC 与切换开销较大 |
| 模块化/混合内核 | 内核模块与多种机制结合 | 在性能和维护间折中 | 分类边界不如教材模型整齐 |

### 机制与策略

- **机制**回答“如何实现”，如上下文如何切换、消息如何传递。
- **策略**回答“选择谁、选择什么”，如采用哪种调度优先级。
- 分离后可在尽量不改底层机制的情况下替换策略；具体哪些策略位于内核或用户态取决于实现。

## 6. 启动流程

### 传统 BIOS + MBR 模型

**BIOS 自检和选启动设备 → 读取并执行 MBR → MBR 查活动分区并加载 PBR/VBR → 后续引导器装入 OS 内核。**

| 组件 | 主要职责 |
|---|---|
| BIOS | 上电自检、初始化基础设备、选择启动介质 |
| MBR | 引导代码 + 分区表；定位活动分区并转交控制 |
| PBR/VBR | 分区级引导，继续加载引导器或内核 |

> [!warning] 适用条件
> 该链路是 408 常见的传统 BIOS/MBR 模型。UEFI/GPT 使用 EFI 系统分区和不同的启动管理流程。

## 7. 虚拟机监控程序

| 类型 | 所在位置 | 典型特点 |
|---|---|---|
| 第一类 VMM | 直接位于硬件之上 | 路径短、隔离和资源控制通常更强 |
| 第二类 VMM | 位于宿主 OS 之上 | 复用宿主驱动与生态，额外经过宿主层 |

- 第二类 VMM 不需要“主体完全处于最高特权级”；通常由用户态管理程序与内核模块配合。
- 多个 VM 同时处于运行期只说明并发；是否并行取决于物理核心。
- VMM 代码量没有脱离功能范围的普遍大小关系，不能用安装包体积替代理论判断。

## 8. 易混概念与绝对词检查

- **系统调用 vs 系统命令**：内核接口 vs 可执行程序。
- **陷入指令在用户态执行 vs 陷入处理在内核态执行**：触发点和处理阶段不同。
- **时钟中断 vs 时间片用完**：周期事件 vs 调度条件。
- **中断到来 vs 进程切换**：前者不必然引起后者。
- **用户态 vs 用户程序归属**：运行状态不等于软件类别；微内核服务可在用户态，但仍是 OS 服务。
- **“唯一/必然/完全”**：优先检查体系结构、教材简化模型和现代实现差异。
