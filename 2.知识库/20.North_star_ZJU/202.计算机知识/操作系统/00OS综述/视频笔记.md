# OS 的作用：
- 文件管理
- 存储管理
- 处理机管理
- 设备管理

接口：
- 直接给用户使用
	- 联机
	- 脱机（批指令）
	- 图形（属于另一维度）
- 给程序员的
	- 程序接口，即系统调用
		- 库函数，除了一些简单纯计算库在用户空间中运行，其他需要调用 write、mmap 等底层指令的库函数，本质就是系统调用

- **提供给人类用户的接口**：叫“命令接口”（你敲键盘用的黑框框，或者鼠标点的图形界面）。
- **提供给应用程序的接口**：叫“程序接口”，它的真身就是**系统调用 (System Call)**！

# OS 特征
OS 特征包括并发，共享，虚拟，异步

 并发性的严格定义是若干事件在同一时间间隔内发生。
   **为什么不是“同一时刻”？**
   同一时刻，CPU 只能处理一个事情。对人类的时间感知来说，1 秒很短，1 秒这个时间间隔跑了很多任务，就是并发。其实是 CPU 每一瞬间都切换任务，推进的。

对资源的共享，
若是互斥共享，必须一个进程占用**并且完成任务**，才能下一个进程

而同时共享，有可能是并发的，（微信 qq 发文件）
也有可能是并行的（扬声器音乐+游戏）
![[视频笔记-1773991238625.jpeg]]

并发和共享互为存在条件
- 程序只有有能力并发，才能做到共享资源
- <u>有效的共享机制是并发的基础，若无法协调资源访问，并发难以执行</u>（操作系统必须提供诸如**锁（Mutex）**或**信号量**的机制，让资源能够安全地被共享，并发才能顺利进行。）

没有并发性，就谈不上虚拟性（你的电脑只有 1 个 CPU、16GB 内存，但你却能同时流畅地开着微信、IDE、游戏和浏览器，每个程序都觉得自己独占了一个完整的 CPU 和巨大的内存空间。）

<u>由于有并发性，就带来了异步性</u>




# 操作系统历史
1. 手工操作
   稍稍进化：引入外围机，提升 IO 效率（因为减少了 CPU 空闲时间），称为脱机 IO
2. 批处理
	- 单道
	  但若运行的任务需要 IO，CPU 也只能空闲等待低速 IO
	- 多道。
	  引入 IO中断，CPU 可转而执行其他任务。故而吞吐量高。**注意，这个任务切换是被动的，只有当前运行的任务主动需要做 I/O 阻塞了，或者任务执行完了，CPU 才会转去执行下一个任务。**
3. 分时（多任务操作系统）
   与之前的多道批处理，区别是引入时间片，**切换任务变为主动**的。另外就是可以交互。多道是一口气输入很多任务，榨干 CPU 去处理。但分时操作系统，人为可以随意添加任务。所以说分时操作系统是面向多用户。
4. 实时
	- 硬实时
	- 软实时
	  硬就是严格在截止时间前，软就是可以稍稍延迟。

多道程序设计是一种**设计思想**或**底层技术**。把多个程序同时塞进内存里。只要当前程序因为等 I/O 阻塞了，CPU 就立刻无缝切换给下一个程序。


# 操作系统体系结构
![[视频笔记-1774076067403.jpeg]]

分层结构：
- **可以逐层往上，便于调试和验证**；层间接口清晰，便于扩充和维护
- 但不可跨层调用，**效率低，调用执行时间长**

内核包含的功能：
- 支撑功能：时钟管理、中断机制、原语
- 资源管理：进程管理，存储器管理，设备管理

用户进入内核态的**唯一途径**就是中断和异常

模块化：
- 模块间逻辑清晰便于维护，可多模块同时开发；**支持加载新模块**；任何模块之间**可互相调用**，
- 但模块之间相互依赖，**难以调试**

大内核：
- 性能高，内核内部可以互相调用
- 但内核庞大复杂，难以维护；某个模块出错就可能导致整个系统崩溃

微内核：
- 易于维护，内核可靠性高，某个模块出错不会导致整个系统崩溃
- 但性能低，需要频繁切换用户态内核态，用户态下各个模块不能互相调用只能消息传递

- **微内核里放了啥**：只放了维持系统运行**最最最底层的骨架**——硬件中断、时钟、低级上下文切换、最基础的进程调度（机制）、以及进程间通信（IPC）。这就没了！它的代码量非常小（可能只有几万行）。

- **大内核里放了啥**：大内核不仅包含了上述所有的底层骨架，它还把**文件系统、网络协议栈、内存管理的高级算法、甚至是成百上千种硬件设备驱动程序（显卡、网卡、磁盘）**，统统塞进了内核态！它的代码量极其庞大（比如 Linux 内核有上千万行代码）。

在微内核架构中，刚才提到的“文件系统”、“网络协议栈”、“设备驱动”，全被**踢出了内核态，降级成了运行在用户态的普通进程**。

## 大内核特点

为什么<u>占用内存空间大？</u>

大内核是一个**“单体结构（Monolithic）”**。所有的子系统（文件、网络、驱动）在编译时，被链接成了一个极其巨大的二进制可执行文件（比如 Linux 的 `vmlinux`）。 只要系统一开机，这个巨大的文件就会被整体加载到物理内存的内核区。哪怕你这台电脑根本没有网卡，也没有挂载什么特殊的文件系统，相关的代码依然死死地霸占着宝贵的内核物理内存。

为什么<u>不方便拓展？</u>（与可靠性低强绑定）

大内核里所有的模块都在同一个内核地址空间里裸奔，相互之间直接通过 C 语言的**函数调用**来通信。

- **拓展难**：如果你想给大内核增加一种新的文件系统支持，你必须修改内核源代码，**重新编译整个庞大的内核，并且重启计算机**。代码耦合度极高，牵一发而动全身。（_注：虽然现代 Linux 引入了可装载内核模块 LKM 来缓解这个问题，但在经典理论中，单体内核的拓展性就是极差的。_）

- **可靠性低（牵一发死全局）**：因为大家都在内核态，拥有最高硬件权限。如果你新加的显卡驱动写了一个死循环或者指针越界，由于没有内存隔离，它会直接把整个内核的数据结构写烂，导致**系统瞬间蓝屏/内核崩溃（Kernel Panic）**。


## 微内核特点

#### 1. 为什么更方便分布式系统开发？

**核心技术原因：IPC（进程间通信）机制的绝对统一与位置透明性。**

- **大内核的本地调用**：在大内核中，用户程序调用文件系统是通过**函数调用**。这种基于共享内存地址空间的函数调用，**绝对无法跨越物理机器**。

- **微内核的消息传递**：微内核强制要求所有服务（如文件服务器、网络服务器）都在独立的用户态进程中。它们之间只能通过**构造消息包并发送**来通信。

- **网络延伸（质变点）**：在单机微内核中，进程 A 发送消息给进程 B，微内核在内存中拷贝这个消息。如果你把系统变成分布式集群，你只需要在底层把“内存拷贝”替换成“网络协议栈（如 TCP/IP）”。对于上层的进程 A 来说，**它发出的消息包格式完全不变，它根本不需要知道接收方进程 B 是在同一块主板的 RAM 里，还是在地球另一端的服务器里。** 这种将本地 IPC 无缝扩展为 RPC（远程过程调用）的能力，是微内核天生适合分布式的物理基础。
    

#### 2. 为什么可移植性高？

**核心技术原因：硬件相关代码的代码量被极度压缩。**

- **移植的本质代价**：把操作系统从 x86 架构移植到 ARM 架构，所有直接操作 CPU 寄存器、操作 MMU（内存管理单元）、处理特定主板中断控制器的**汇编代码和底层 C 代码**，必须全部重写。
    
- **大内核的灾难**：大内核包含了所有的设备驱动（显卡、网卡、硬盘）。这些驱动直接与硬件物理引脚和寄存器打交道，这意味着你需要重写上百万行与硬件强绑定的代码。
    
- **微内核的优势**：在微内核中，所有的设备驱动、文件系统、网络协议栈都是运行在用户态的**纯逻辑代码**（硬件无关）。它们依赖标准 C 库，可以直接跨平台重新编译。真正需要你手动重写汇编代码去适配新硬件的，**仅仅只有那几万行的微内核核心代码（处理底层中断、时钟和基本上下文切换）**。工作量呈指数级下降。

|**功能模块**|**大内核（如 Linux）的做法**|**微内核（如 seL4）的做法**|
|---|---|---|
|**文件系统**|内核态。包含 EXT4、NTFS、VFS 等几十万行代码。|**赶出去！** 变成用户态的 `file_server` 进程。|
|**网络协议栈**|内核态。完整的 TCP/IP、路由表、Socket 驱动。|**赶出去！** 变成用户态的 `network_server` 进程。|
|**设备驱动**|内核态。显卡、声卡、网卡、USB 驱动都在内核。|**赶出去！** 变成用户态的驱动进程。坏了不影响内核。|
|**虚拟内存**|内核态。管换页、管 LRU 置换算法。|微内核只负责最基础的**物理页映射（机制）**。至于页面怎么置换、什么时候换进磁盘（策略），**赶出去**由用户态内存管理器管。|
|**进程调度**|内核态。复杂的红黑树 CFS 调度算法。|微内核只负责**执行切换动作（机制）**。至于谁该运行，由用户态的策略服务器说了算。|

# 操作系统开机
![[视频笔记-1774077383810.jpeg]]
#### Step 1: BIOS 初始化基本硬件，建立中断向量表

- **物理位置**：主板上的 ROM 芯片。
    
- **能力极限**：BIOS 极其原始，它**绝对看不懂**什么是 C 盘、D 盘，也看不懂什么是 NTFS、FAT32 文件系统。
    
- **唯一动作**：硬件通电自检（POST）完成后，BIOS **根据设定的启动顺序**找到第一块硬盘。
  它只会做极其机械的一件事：**读取这块物理硬盘的第 0 柱面、第 0 磁头、第 1 扇区（也就是绝对的物理第一个扇区，LBA 0），并将其加载到内存的 `0x7C00` 物理地址处，然后将 CPU 的控制权 (PC 寄存器) 交给这个地址。**

- **这个被加载的第一个扇区，就是 MBR。**
    

#### Step 2: MBR (主引导记录) 加载到内存

- **物理限制**：MBR 就是刚才说的硬盘第一个物理扇区。一个扇区有多大？**严格的 512 字节（Bytes）！**
    
- **空间解剖**：这 512 个字节被死死地切分成了三个部分：

    1. **引导代码（446 字节）**：真正的可执行机器指令。
        
    2. **分区表（64 字节）**：硬盘的分区地图。
        
    3. **魔数（2 字节）**：`55 AA`，告诉 BIOS 这是一个合法的启动扇区。
        
- **为什么 MBR 的任务是“检查分区表，确定活动分区，调入 PBR”？**
    
    - **原因 1（无法直接加载 OS）**：MBR 的可执行代码只有区区 **446 字节**！用 446 字节写一套汇编代码去解析复杂的 NTFS 文件系统并找到几十 MB 大小的操作系统内核文件？在物理上绝无可能！
        
    - **原因 2（必须查分区表）**：既然自己无能为力，它只能找帮手。硬盘被分成了 C、D、E 盘，操作系统到底装在哪个盘？MBR 自己的代码立刻去读取紧挨着它的那 **64 字节的分区表**。
    
    - **原因 3（寻找活动分区）**：分区表里有 4 个表项（每个 16 字节），MBR 的代码会遍历这 4 个表项，检查哪一个表项的第一个字节是 `0x80`（代表**活动分区/Active Partition**，通常就是装了系统的 C 盘）。
        
    - **原因 4（交出接力棒）**：找到 C 盘后，MBR 提取出 C 盘的**起始物理扇区号**。MBR 的最后一行代码，就是向磁盘控制器发指令：把 C 盘的第一个扇区（这就是 PBR）读进内存，然后让 CPU 跳过去执行。MBR 的使命到此彻底结束。


#### Step 3: PBR (分区引导记录 / Volume Boot Record) —— 懂文件系统的大管家

- **物理位置**：活动分区（如 C 盘）的第一个扇区。
    
- **能力升级**：PBR 是在安装操作系统时被写入的。它不仅包含第一扇区，通常还会连带加载紧随其后的多个扇区构成一个更大的引导程序（如 Windows 的 `BOOTMGR`，Linux 的 `GRUB Stage 2`）。
    
- **最终动作**：因为 PBR 的代码量足够大，它包含了**极其精简的文件系统解析代码**（比如极简版的 NTFS 驱动）。它终于能够看懂 C 盘的文件目录树，顺着根目录找到 `/Windows/System32/ntoskrnl.exe` (或 Linux 的 `/boot/vmlinuz`)，将这个真正的操作系统大内核加载到内存中，完成系统启动。

# 虚拟机
![[视频笔记-1774078839886.jpeg]]

![[视频笔记-1774082231425.jpeg]]
业界将 VMM 严格分为两类：
1. **第一类 VMM（裸金属型 / Type 1）**：
    
    - **架构**：物理硬件 $\rightarrow$ **VMM** $\rightarrow$ 客户机操作系统 (Guest OS)。
        
    - **特征**：VMM 直接安装在裸硬件上，**它本身就是一个精简版的操作系统**。它拥有硬件的绝对控制权。
        
    - **性能**：极高。因为客户机的指令请求只需要经过一层 VMM 就能直达硬件。
        
    - **代表产品**：VMware ESXi, Microsoft Hyper-V。
        
2. **第二类 VMM（宿主型 / Type 2）**：
    
    - **架构**：物理硬件 $\rightarrow$ 宿主机操作系统 (Host OS) $\rightarrow$ **VMM** $\rightarrow$ 客户机操作系统 (Guest OS)。
        
    - **特征**：底层的物理机上先安装了一个完整的传统操作系统（比如 Windows 11），**VMM 仅仅是运行在这个 Host OS 上的一个普通应用程序**。
        
    - **性能**：较低。客户机的硬件请求必须先交给 VMM，VMM 再作为普通程序向 Host OS 发起系统调用，Host OS 最后才去操作硬件。
        
    - **代表产品**：**VMware Workstation**（第 17 题的考查对象）, VirtualBox。

### 二、 第 17 题解析：VMware Workstation 的物理属性

> **正确答案：B（错误的是 B）**

**逐项技术剖析：**

- **A. 正确（特权指令拦截机制）**：
    
    在虚拟化环境中，客户机操作系统 (Guest OS) 认为自己拥有最高权限，它会尝试执行修改页表、关中断等“敏感指令”。但底层的物理 CPU 知道当前运行的是虚拟机，绝对不会直接执行这些指令。**物理硬件会产生一次异常（陷入），将控制权强行交给底层的 VMM，由 VMM 去“模拟”执行这条指令**。这就是虚拟化核心的“陷入-模拟（Trap-and-Emulate）”机制。
    
- **B. 错误（反硬件常识）**：
    
    虚拟机在逻辑上向客户机提供的是一套**标准化的“通用虚拟硬件”（虚拟的主板、CPU、磁盘）**。既然是通用硬件，只要操作系统支持这套硬件架构（如 x86），你就可以在里面安装 Windows、Linux，甚至可以在同一个虚拟机的虚拟磁盘上划分多个分区，安装“双系统”并进行多重引导。绝不存在“只能安装一种”的物理限制。
    
- **C. 正确（Type 2 的本质）**：
    
    VMware Workstation 是典型的**第二类 VMM**，它在 Windows/macOS 看来，和微信、Word 没有本质区别，就是一个运行在用户态的应用程序（带有内核态的驱动模块）。
    
- **D. 正确（虚拟化的存储封装）**：
    
    虚拟机的整套硬件状态和数据，在物理宿主机的文件系统上，被彻底封装成了几个普通文件（比如 `.vmdk` 虚拟磁盘文件，`.vmx` 配置文件）。

### 三、 第 18 题解析：VMM 的底层边界

> **正确答案：B（I 和 III 正确）**

**逐项技术剖析：**

- **I. 正确（架构决定效率）**：
    
    第一类 VMM（裸金属型）直接运行在物理硬件上，不存在中间宿主操作系统的系统调用开销，资源调度链路最短，效率必然高于第二类 VMM。
    
- **II. 错误（代码量逻辑推导）**：
    
    VMM 的核心功能非常纯粹：**CPU 状态切换、内存地址嵌套映射、设备中断路由**。它不需要像完整操作系统那样包含庞大的图形用户界面 (GUI)、成千上万种声卡/显卡/外设的具体驱动程序。因此，**VMM 的代码量通常远远小于一个完整的操作系统内核**（例如 VMware ESXi 只有几百 MB，而 Windows 动辄几十 GB）。
    
- **III. 正确（虚拟化基本定义）**：
    
    将一台物理服务器通过时间片轮转和空间隔离，虚拟出 N 台逻辑上独立的虚拟机，这是 VMM 存在的最基本意义。
    
- **IV. 错误（特权级剥离）**：
    
    题目说“第二类 VMM 需要**完全**运行在最高特权级”。这是错的。
    
    以 VMware Workstation 为例，它的主体图形界面、配置管理进程都**运行在用户态（Ring 3）**。只有负责拦截敏感指令和内存映射的极小一部分“内核模块（Kernel Driver）”才运行在**最高特权级（Ring 0）**。它绝不是“完全”在最高特权级运行。
