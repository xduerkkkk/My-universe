

像 GCC 这种工具，通常被叫做"编译器"，但它实际上是个驱动程序（driver），背后调用了一整套工具：预处理器（cpp）、编译器本体（cc1，负责高级语言→汇编）、汇编器（as，负责汇编→机器码）、链接器（ld）。所以当你敲 `gcc hello.c -o hello` 时，GCC 内部把汇编这一步也做了，对你透明。

所以你说的"编译程序里包含了汇编程序，然后直接编译→链接"——本质上是：GCC 把"高级语言→汇编→机器码"这几步打包了，最后再链接。狭义上"编译"只是其中一段，但工具帮你连着做完了。

下面用具体例子把整条链走一遍。

假设两个源文件：

```c
// main.c
#include <stdio.h>

int add(int a, int b);   // 声明，不是定义

int main() {
    int r = add(3, 4);
    printf("%d\n", r);
    return 0;
}
```

```c
// add.c
int add(int a, int b) {   // 定义在这里
    return a + b;
}
```

关键点：`main.c` 里只声明了 `add`，没有它的实现代码。`add` 的机器码在 `add.c` 里。

现在分步执行，观察每一步的产物。

第一步：预处理（`gcc -E main.c -o main.i`）
把 `#include <stdio.h>` 展开（把头文件内容整个贴进来），处理宏、去掉注释。产物还是 C 代码，只是被"摊平"了。

第二步：编译（`gcc -S main.i -o main.s`）
高级语言 → 汇编语言。产物 `main.s` 是文本形式的汇编代码，里面会有类似：

```asm
main:
    ...
    movl    $4, %esi
    movl    $3, %edi
    call    add          # 这里只是"调用add"，但add在哪还不知道
    ...
```

注意 `call add` 这条：编译器知道要调用 `add`，但 `add` 的机器码地址此刻是未知的，因为 `add` 不在这个文件里。这个悬而未决的引用，是理解链接的核心。

第三步：汇编（`gcc -c main.s -o main.o`）
汇编语言 → 机器码。产物 `main.o` 是目标文件（object file），二进制，但还不能运行。它内部有一张符号表（symbol table）：
- `main`：已定义，有具体机器码
- `add`：未定义（undefined），标记为"外部符号，等待别人提供"
- `printf`：未定义，等待 C 标准库提供

同样地，`add.c` 单独走完这三步得到 `add.o`，它的符号表里 `add` 是已定义的。

第四步：链接（`gcc main.o add.o -o hello`）
链接器（ld）干的事：
1. 把多个 `.o` 文件的代码段、数据段合并到一起。
2. 符号解析（symbol resolution）：`main.o` 里那个未定义的 `add`，去别的 `.o` 里找谁定义了它——在 `add.o` 里找到了，配上对。`printf` 则在 C 标准库里找到。
3. 重定位（relocation）：确定每段代码在最终程序里的实际地址，然后回填。之前 `call add` 那条指令里 `add` 的占位地址，被改写成 `add` 真正所在的地址。

链接完成后得到可执行文件 `hello`，所有符号都有确定地址了，可以运行。

一句话串起来的心理表征：

编译器/汇编器是逐个文件独立工作的，它遇到"本文件里没有的东西"（外部函数、外部变量）时，只能留个记号说"这里要用某某符号，但我不知道它在哪"。链接器则站在全局视角，把所有文件的记号和定义对上号，并填上真实地址。所以：

- 编译（含汇编）解决的是"把每个源文件各自翻译成机器码"
- 链接解决的是"把这些独立的机器码块拼成一个完整程序，并解决跨文件的引用"

这也解释了两类经典错误：
- 编译错误：单个文件内部的语法/语义问题（比如少写分号、类型不匹配）
- 链接错误：语法都对，但符号对不上。比如 `add.c` 忘了编译进来，链接器报 `undefined reference to 'add'`；或者两个文件都定义了同名的 `add`，报重复定义（multiple definition）。


408 里的三种链接方式，是按"链接这个动作发生在什么时刻"来分的。沿用上面 `main.o`、`add.o` 和库函数 `printf` 的例子。

前提先明确：链接要解决的核心问题始终是"把未定义的外部符号（如 `add`、`printf`）对应到真正的机器码，并填上地址"。三种方式的区别只在于——这件事什么时候做。

一、静态链接（static linking）

时机：程序运行之前，装入内存之前就全部链接好。

做法：链接器把 `main.o`、`add.o`，以及 `printf` 所在的库（静态库 `.a` 文件里对应的目标模块）全部合并，符号解析 + 重定位一次做完，产出一个完整、自包含的可执行文件 `hello`。运行时它不再依赖任何外部模块。

在例子里：`printf` 的机器码会被直接拷贝进 `hello` 这个文件。

特点（精确）：
- 可执行文件体积大：每个用到库函数的程序都各自拷贝一份库代码。100 个程序用 `printf`，内存/磁盘里就有 100 份 `printf` 代码。
- 库更新后，必须重新链接整个程序才能生效。

- 运行时无链接开销，装入即可执行。
二、装入时动态链接（load-time dynamic linking）

时机：目标模块在装入内存时，边装入边链接。

做法：`hello` 这个文件里不含 `printf` 的机器码，只保留一个"需要 `printf`，它在某个库里"的记号。当操作系统要把 `hello` 装入内存运行时，装入程序（loader）发现有未链接的外部模块，就去找到对应的库模块，一并装入内存并完成链接（符号解析 + 重定位）。

特点：
- 便于模块共享：多个程序若都用同一个库，装入时可以让它们指向内存里同一份库代码（这就是共享库 / shared library 的基础）。
- 便于更新：库单独存在，替换库文件后，下次程序装入时自动用新版本，不必重新链接程序。
- 装入阶段有额外时间开销。

三、运行时动态链接（run-time dynamic linking）

时机：程序执行到需要调用某个模块时，才对该模块进行链接。用不到就一直不链接。

做法：`hello` 装入内存开始运行，某个外部模块（比如某个很少走到的分支里才调用的函数）在真正被调用到的那一刻，才去装入并链接。如果程序这次运行根本没走到那个分支，该模块就完全不被装入。

特点（精确）：
- 加快装入速度、节省内存：不用的模块根本不进内存。
- 特别适合有大量分支、且很多分支平时走不到的程序（很多功能模块可能一次运行都用不上）。
- 每次调用未链接模块时才链接，把开销分散到运行期，且只为实际用到的部分付出代价。

三者对比（一句话抓住区别）：

| 方式 | 链接时刻 | 是否所有模块都被装入 |
|------|----------|---------------------|
| 静态链接 | 运行前，装入前 | 全部合并进可执行文件 |
| 装入时动态链接 | 装入内存时 | 用到的库全部装入 |
| 运行时动态链接 | 执行到调用时 | 只装入实际执行到的模块 |

需要澄清一个常见混淆：

408 教材（唐/王道体系）里"装入时动态链接"和"运行时动态链接"是操作系统层面对"链接时机"的三分法。而工程实践中你听到的"动态链接库"（Linux 的 `.so`、Windows 的 `.dll`）——用 `dlopen` 手动加载的对应运行时动态链接，程序启动时由动态链接器自动加载的更接近装入时动态链接。考试按上面三分法答题即可，不要用工程里的粗略叫法去套。
