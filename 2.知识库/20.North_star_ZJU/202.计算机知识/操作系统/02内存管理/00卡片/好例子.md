为了让你彻底看清底层的运作机制，我们直接设定一个严格的物理环境：
*   **页大小（Page Size） = 物理块大小 = 4KB（4096 字节）。**
*   **指令长度设定：** 假设所有指令和数据都有明确的字节地址。

假设你写了这样一段 C 代码，编译后形成了以下逻辑地址空间：
```assembly
// 逻辑页 0 (地址 0 ~ 4095)
[逻辑地址 100]: LOAD R1, [逻辑地址 4196]   // 把全局变量 x 读入寄存器
[逻辑地址 104]: JUMP [逻辑地址 4200]      // 跳转到函数 func_A 执行

// 逻辑页 1 (地址 4096 ~ 8191)
[逻辑地址 4196]: 0x0000000A               // 全局变量 x (值为10)
[逻辑地址 4200]: ...                      // 函数 func_A 的第一条指令
```

### 一、为什么页式分配绝对不能用“静态重定位”？

现在，OS 要把这个程序装入物理内存。因为是页式分配，OS 找了两个**不连续**的物理页框：
*   **物理页框 5**（起始地址：5 * 4096 = 20480）分配给 **逻辑页 0**。
*   **物理页框 20**（起始地址：20 * 4096 = 81920）分配给 **逻辑页 1**。

**如果强行使用“静态重定位”（装入时修改指令）：**
装入程序必须在把代码写入内存的瞬间，修改指令里的地址。
1. 看第一条指令 `LOAD R1, [4196]`。装入程序发现 `4196` 属于逻辑页 1，现在放在物理页框 20。它必须算出物理地址：`81920 + (4196 - 4096) = 82020`，然后把内存里的指令篡改成 `LOAD R1, [82020]`。
2. 看第二条指令 `JUMP [4200]`。装入程序算出物理地址 `82024`，把指令篡改成 `JUMP [82024]`。

**为什么这种做法在现代 OS 中是灾难（即不能用的原因）？**
1. **性能代价极大：** 装入程序必须**逐条**扫描并解析所有指令（反汇编），判断哪个操作数是地址，还要查它属于哪个页，算出物理地址后再改写。对于几百 MB 的程序，装入极其缓慢。
2. **破坏了页面换出（Swap）机制：** 如果物理内存紧张，OS 把逻辑页 1 换出到磁盘，过一会儿再换入到**物理页框 30**。此时物理地址全变了！但内存里逻辑页 0 的指令已经被静态写死成 `JUMP [82024]` 了，程序直接跑飞。
3. **破坏了代码共享：** 如果代码被修改成了特定的物理地址，这个代码页就只能给当前进程用了，无法与其他进程共享。

**页式的动态重定位是怎么做的？**
装入程序**一个字节都不改**，直接把指令原封不动搬进内存（内存里依然是 `LOAD R1, [4196]`）。OS 只做一件事：建一张页表 `[页号0 -> 框号5, 页号1 -> 框号20]`。
当 CPU 执行到 `LOAD R1, [4196]` 时：
1. MMU 硬件瞬间截获逻辑地址 `4196`。
2. MMU 硬件拆分：`4196 / 4096 = 页号1`，`4196 % 4096 = 偏移量100`。
3. MMU 查页表：页号 1 对应框号 20（起始地址 81920）。
4. MMU 输出最终物理地址：`81920 + 100 = 82020`。
这一切在 CPU 流水线中由硬件极其快速地完成，支持页面随时在物理内存中移动（只需改页表）。

### 二、动态重定位搭配三种链接的演示

现在，你的代码里多了一行 `printf("Hello");`。`printf` 不在你写的代码里，它在标准库 `libc` 中。我们来看看在这个页式+动态重定位的环境下，三种链接分别发生什么。

#### 1. 静态链接 + 动态重定位
*   **链接时机：** 编译后，链接器（如 `ld`）直接介入。
*   **发生什么：** 链接器把 `libc` 中 `printf` 相关的机器码，**硬拷贝**到你的可执行文件中。此时，你的逻辑地址空间变大了。假设 `printf` 被分配在**逻辑页 2**（地址 8192 开始）。你的代码变成 `CALL [8192]`。
*   **装入时：** OS 把逻辑页 0、1、2 分别装入三个物理页框，建立包含 3 个表项的页表。
*   **运行时（动态重定位）：** CPU 执行 `CALL [8192]`，MMU 算出页号 2，查页表，映射到对应的物理页框并执行。
*   **缺点：** 磁盘上每个 C 程序文件里都塞了一个 `printf`，极其浪费外存；内存中如果有 100 个进程，就会装入 100 个完全相同的 `printf` 副本。

#### 2. 装入时动态链接 + 动态重定位
*   **链接时机：** 编译后的可执行文件里**没有** `printf` 的代码，只有一个记录（“我需要 `libc.so` 里的 `printf`”）。
*   **装入时发生什么（核心区别）：** OS 准备运行你的程序。OS 扫描到这条记录，于是去磁盘找 `libc.so`。OS 把 `libc.so` 的代码装入物理内存（或者发现内存里已经有了）。然后，OS 将 `libc.so` 的物理页框，**映射到你当前进程的页表中**，比如分配为逻辑页 5。接着，OS 修改你进程的数据区（如全局偏移表 GOT），把你代码里的调用指向逻辑页 5。
*   **运行时（动态重定位）：** CPU 执行调用指令，访问逻辑页 5，MMU 查表，映射到 `libc.so` 所在的物理页框。
*   **缺点：** 如果你的程序里有 1000 个外部函数，OS 在**启动瞬间**要把这 1000 个库全部找齐、建立好页表映射。如果其中 999 个函数你根本执行不到，这种装入方式浪费了大量的启动时间和内存映射空间。

#### 3. 运行时动态链接 + 动态重定位（现代 OS 主流，强依赖缺页中断）
*   **链接时机：** 和上面一样，可执行文件里只有记录，没有代码。
*   **装入时发生什么：** OS 完全**不理会**那个 `libc.so`。OS 只把你的逻辑页 0 和 1 映射好。对于 `printf`，OS 在你的进程里放一个“存根（Stub，一小段桩代码）”，或者在页表里给 `printf` 预留的逻辑页表项的**有效位（Valid Bit）设为 0**。程序极速启动。
*   **运行时发生什么（高潮在这里）：** 
    1. CPU 执行到调用 `printf`，试图访问那个无效的逻辑地址/存根。
    2. MMU 去查页表，发现**有效位为 0**。
    3. MMU 立刻触发**缺页中断（Page Fault）**，CPU 暂停执行用户程序，陷入内核态。
    4. OS 内核接管，发现：“哦，你试图访问的是 `libc.so` 里的 `printf`”。
    5. OS 此时才去物理内存找 `libc.so`（如果没有，就从磁盘读进来），然后修改你进程的页表，把对应逻辑页的表项填上物理框号，**并将有效位置为 1**。
    6. 中断返回。CPU 重新执行刚才引发中断的那条调用指令。
    7. 这一次，MMU 查页表，有效位是 1，**动态重定位**成功，直接算出物理地址并执行。
*   **结果：** 实现了“不执行到该代码，就绝对不产生链接和装入开销”。
