   关闭文件指讲文件当前控制信息从内存写回磁盘，而**不是将文件数据写回磁盘**。
   为啥？那数据的修改到底怎么实现？
   **数据的修改当然会写回磁盘，但它不是由 `close()` 这个动作“强制、同步”去做的。** 这里引入了一个操作系统的核心作弊神器——**内核缓冲区（Buffer/Page Cache）**。
   数据缓冲区里的“脏数据”写回磁盘，有以下几种触发时机：
	 - **异步后台线程（主要靠它）**：操作系统后台有一个守护线程（比如 Linux 的 `flusher` 线程），每隔一段时间（比如 30 秒）就会疯狂扫描内存，把所有标记为“脏”的数据块批量刷进磁盘。
    
	- **内存不够了**：当系统内存紧张，需要回收缓冲区时，会把脏数据强制刷回磁盘，然后清空内存。
	    
	- **用户手动强刷**：你在写代码时调用了 `fsync(fd)` 或 `sync()`，这是在命令系统：“别等了，立刻给我把数据埋进磁盘！”

8. A？
   内存索引节点是磁盘索引节点 copy 过来的，是读文件过来的，甚至不是打开文件过来的，是吗？然后只多一个 count，其他和磁盘的节点一样？
   
   `open()` 去磁盘上查目录，找到这个文件的 FCB / Inode，然后**把这个 FCB / Inode 从磁盘 copy 到内存里！** 这就叫建立“打开文件表”和“内存索引节点”。`open` **绝对不会**去把文件里的文章内容（数据）读到内存里。
   
   **`read()` 操作的核心任务**：看着内存里已经建好的打开文件表，顺着里面的物理块地址，去磁盘把真正的**文件内容（数据数据数据！）**读进内存缓冲区。
   
   内存 Inode 确实是从磁盘 Inode 复制来的。多加的几个动态属性：count、dirty bit、设备号
   
   count记录当前整个系统中有多少个进程/表项正在使用这个内存 Inode。进程 A 关了文件 $\rightarrow$ 调用 `close()` $\rightarrow$ `count` 减 1，变成 1。由于 `count > 0`，系统知道还有别人在用，**绝对不能把这个 Inode 从内存中销毁**。进程 B 也关了文件 $\rightarrow$ 调用 `close()` $\rightarrow$ `count` 变成 0。系统一看 `count == 0`，说明没人用了，这时才会放心把这个 Inode 从内存里回收掉。
   
   `dirty bit`，在 `count` 降为 0，系统准备把这个 Inode 踢出内存时检测，看是否磁盘 IO
   
   device number 标记**这个文件到底在哪块物理磁盘、哪个分区上**。

    $$\text{FAT表总大小} = \text{FAT表项的总个数} \times \text{每个FAT表项占用的字节数}$$
    这个系统的最小物理单位是 **簇 = 8KB**。也就是说，不管文件多小，哪怕只有 1 个字节，系统也会直接分给它 8KB 的物理空间。
    $$\text{簇的总个数} = \frac{512\text{MB}}{8\text{KB}} = \frac{512 \times 1024\text{KB}}{8\text{KB}} = 65536 \text{ 个}$$
    磁盘上一共有 $65536$ 个簇。因为 FAT 表是全局的，每个簇都要在 FAT 表里占一行，所以 **FAT 表项的总个数 = 65536 个**。
    $2^{16} = 65536$。所以，你需要用 **16 个 bit（也就是 2 个字节）**，才能存得下一个簇号。
    每个 FAT 表项需要占用 **2B (Bytes)** 的空间。- $\text{FAT表总大小} = 65536 \text{ (个表项)} \times 2\text{B (每项大小)} = 131072\text{B}$

44. <font color="#ff0000">D?</font>
    open 要求文件路径与文件名，open 流程是什么？为何 read 只需要 open 返回的文件描述符，read 所需参数：fd、buf 首地址、传送字节数，怎么理解
    `open("/a/b/c.txt")`，操作系统先去磁盘找根目录 `/`，在里面按名字搜索，找到 `a` 目录的 Inode；去磁盘读 `a` 的数据块，在里面搜索 `b`；再去读 `b` 的数据块，最后终于在里面找到了 `c.txt` 的 Inode 编号。**（这里发生了大量的磁盘 I/O）**
    操作系统把 `c.txt` 的 Inode 从磁盘复制到内存的**“系统级打开文件表”**中。
    操作系统在当前进程的**“进程级打开文件表”**里找一个空闲的格子（比如第 3 号格子），让它指向系统表里的那个 Inode。
    操作系统把数字 `3` 返回给你。这个 `3` 就是**文件描述符（fd）**！
    当你调用 `read(fd, buf, size)`，也就是 `read(3, buf, 100)` 时：
    它直接去当前进程的表里找第 `3` 个格子。顺着指针瞬间找到内存里的 Inode。
    Inode 里不仅有文件的物理块地址，还有你现在的**“读写指针（当前读到第几个字节了）”**。
