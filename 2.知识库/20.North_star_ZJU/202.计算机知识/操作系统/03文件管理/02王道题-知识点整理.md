## 一、文件基础概念

### 1.1 设备文件分类（原题1）
UNIX 将 I/O 设备分为：
- **字符设备文件**：键盘、鼠标，不可寻址，按字符流读写
- **块设备文件**：硬盘、U盘，可寻址，按数据块读写

设备文件的 Inode 里存的是**主设备号**（找对应的设备驱动程序）和**次设备号**（区分同类型里的具体哪个设备，比如 1 号硬盘还是 2 号硬盘）。

> 🧠 **思维误区**：你选了 D，可能是把"设备文件"和普通数据文件的 Inode 内容搞混了。设备文件的 Inode 不存文件大小/数据块指针，而是存设备号。

### 1.2 打开文件操作的本质（原题3）
打开文件操作是把指定文件的**目录项复制到内存指定区域**。

具体来说，是复制到**系统打开文件表**中。系统打开文件表的记录项还包括索引（实际隐含在数组下标中）、打开计数器。

> 🧠 **思维误区**：选了 C 带问号，说明对 `open()` 到底做了什么不够清晰。你的直觉"复制目录项"是对的，但没明确是复制到哪个数据结构。完整链条见 Q44 的分析。

### 1.3 关闭文件操作：文件控制信息 ≠ 文件数据 ⚠️（原题5 · !!）
**关闭文件是指将文件当前控制信息从内存写回磁盘，而不是将文件数据写回磁盘。**

> 🧠 **思维误区——"close() 难道不保存数据？"模式**：你的直觉是 `close()` 应该把所有东西都写回磁盘。但操作系统的设计哲学是**控制信息同步、数据异步**。

**数据到底什么时候写回磁盘？** 内核缓冲区（Buffer/Page Cache）里的"脏数据"写回磁盘有以下触发时机：
- **异步后台线程（主力）**：OS 后台守护线程（如 Linux 的 `flusher` 线程）每隔约 30 秒将脏数据批量刷入磁盘
- **内存不够**：系统需要回收缓冲区时，强制刷回脏数据
- **用户手动强刷**：代码中调用 `fsync(fd)` 或 `sync()`，命令系统立即写回

> 🔗 相关卡片：[[./卡片/记忆--文件系统架构]]（理解缓冲层在六层架构中的位置）[[感悟--时间线梳理文件]]

### 1.4 目录文件的本质（原题7）
目录文件存放的是 **FCB 的集合**，既可能包含子目录的 FCB，又可能包含数据文件的 FCB。Windows 里的"我的文档"文件夹就是目录文件，里面既有 Word 文档又可能有子文件夹。

> 🧠 **思维误区**：你可能把"目录文件"和"普通文件"的数据内容搞混了。目录文件的"数据"就是一个个 FCB/目录项，不是文件内容。

### 1.5 内存 Inode vs 磁盘 Inode（原题8）
`open()` 的工作流程：
1. 去磁盘查目录，找到文件的 FCB/Inode
2. 把 FCB/Inode **从磁盘 copy 到内存** → 这就是建立"打开文件表"和"内存索引节点"
3. `open()` **绝对不会**把文件内容（文章数据）读到内存里

**`read()` 才负责**：看着内存里建好的打开文件表，顺着物理块地址，去磁盘把真正的内容数据读进内存缓冲区。

**内存 Inode 相比磁盘 Inode 多出的动态属性**：

| 属性 | 作用 |
|------|------|
| **count** | 记录全系统有多少进程/表项正在使用该内存 Inode。`open()` +1，`close()` -1。减到 0 时才从内存回收 |
| **dirty bit** | count 降为 0 准备回收时检测，若脏了则写回磁盘 |
| **device number** | 标记文件在哪块物理磁盘、哪个分区上 |

> 🔗 相关卡片：[[../卡片/辨析--引用计数器]]（链接计数 vs 打开计数的双胞胎辨析）
> 🔗 相关卡片：[[../卡片/辨析-目录文件的样子，inode的样子]]

### 1.6 文件目录项不包含自身物理位置（原题9 · FAT32）
FAT32 的目录项不包含文件自身的物理位置信息（物理位置由 FAT 表统一管理）。

### 1.7 Inode 的设计目的（原题10）
Inode 是为了**减少查找时的 I/O**——把 FCB 里最需要频繁读写的那部分单独抽出来，原来找文件要读整个目录项，现在只读 Inode 编号就行。其他环节的 I/O 省不了。

### 1.8 文件访问权限：用户优先级无关（原题13）
文件的访问由**用户访问权限**和**文件属性里的控制信息**共同限制，和**用户优先级没有关系**。

> 🧠 **思维误区**：你可能把"用户优先级"（调度相关）和"用户权限"（访问控制相关）混淆了。优先级决定 CPU 给谁用，权限决定谁可以打开文件。两个不同维度的概念。

### 1.9 文件保护的四层大门（原题14）
| 层级 | 干什么 | 手段 |
|------|--------|------|
| **系统级** | 防贼进院子——控制谁能登录电脑 | 注册、登录账号、密码校验 |
| **用户级** | 院子里不同人能进哪些房间 | 用户分类（root/普通/访客）、ACL 访问控制列表 |
| **目录级** | 保护整个房间不被乱搞 | 目录的读/写/执行权限 |
| **文件级** | 保护具体某个抽屉 | 文件属性：只读、隐藏、系统文件 |

### 1.10 异步 I/O 不影响磁盘 I/O 次数（原题15）
异步 I/O 只是提高 **CPU 利用率**（让 CPU 在等待磁盘时去干别的事），对**磁盘 I/O 次数**没有影响。

### 1.11 连续结构不利于动态增长（原题22）
连续结构不利于文件长度动态增长，主要原因是连续结构**要预留空间**——你不知道文件将来会增长多少。链接分配不需要预留，随便增。

> 🧠 **思维误区**：你可能只想到"连续结构要移动数据"，但更根本的原因是"必须提前知道文件有多大或预留多少"。链接结构没有这个约束。

## 二、文件物理结构（分配方式）

### 2.1 逻辑索引 vs 物理索引 vs FAT 表（原题26）
你在 Q26 的批注写道："突然感觉，显式链接的 FAT，和索引表，和逻辑上的索引文件，都挺像的啊"。这是个极好的洞察——它们确实都是 Key-Value 映射表。区别在于 Key 和 Value 是什么：

| | **逻辑索引文件** | **物理索引分配** | **FAT 表（显式链接）** |
|---|---|---|---|
| **层级** | 逻辑层（用户视角） | 物理层（OS 视角） | 物理层（OS 视角） |
| **Key** | 业务关键字（学号） | 逻辑块号 LBN | 当前物理块号 |
| **Value** | 逻辑记录号/偏移 | 物理块号 PBN | 下一个物理块号 |
| **范围** | 一个文件一张 | 一个文件一张（私人） | 全磁盘一张（全局） |
| **本质** | 按内容找位置 | 按顺序找位置，随机跳跃 | 靠上一个找下一个，内存里的链表 |

> 🔗 你的卡片完美覆盖了这个辨析：[[./卡片/辨析--逻辑索引 vs 物理索引 vs FAT 表]]

### 2.2 存储介质特性影响文件组织方式（原题28）
逻辑文件存放到存储介质上，采用的组织形式与**存储介质特性**有关。设备的分配方式完全是 I/O 章节的概念，不要混。

> 🧠 **思维误区——"概念跨章混淆"模式**：你把"设备的分配方式"和"存储介质特性"画了等号。这是 408 爱考的跨章混淆——文件章节的存储介质特性（顺序存取 vs 随机存取）≠ I/O 章节的设备分配方式（独占/共享/虚拟）。

### 2.3 文件中"加一块"的 I/O 次数分析 ⚠️（原题29 · !!）
题目说"在文件中加一块"，你没注意到可能是**在中间添加**而默认是末尾添加。任何时候加一块，**连续分配 I/O 次数最多**——因为可能要迁移整个文件。其他分配方式（链接、索引）无论如何都是改改指针/索引。

> 🧠 **思维误区——"默认假设"模式**：你把"加一块"默认理解为"在末尾追加"，但题目没有说。408 命题特别喜欢在"没说位置"的情况下考你最坏情况。**凡是没有明确说"在末尾"的，都要考虑任意位置。**

### 2.4 记录成组分解技术（原题30）
**关键澄清**：
- "逻辑记录长度"指的是**每行数据的大小**，不是"逻辑地址长度"
- "第 22 个逻辑记录"说明文件至少有 22 行数据
- 总大小 = 22 × 100B = 2200B，512B 的盘块装不下，必须分到多个盘块

**计算方法**：一个盘块装 5 个记录（512÷100=5，余 12B 浪费）。修改第 22 个记录：先读 5 次拿到第 5 块的数据 → 在缓冲区修改 → 写回磁盘 1 次 → **共 6 次 I/O**。（读记录时不产生 I/O——因为表项先读到缓冲区；最后写回 1 次。）

> 🧠 **思维误区——"望文生义"模式**：你把"逻辑长度"理解成了"逻辑地址的长度"。这是一种容易被缩写/简称坑的模式——408 喜欢用日常词汇当术语，比如"记录"是指一条数据行而不是"写入"的动作。

### 2.5 FAT 表大小计算（原题32-33）
**核心公式**：
$$\text{FAT表总大小} = \text{FAT表项总个数} \times \text{每个FAT表项的字节数}$$

**簇号位数 → FAT 表项字节数**：
- 有多少个 FAT 表项？全磁盘有多少个簇，就需要多少个表项
- 簇号是 16 位 → FAT 表项占 2 字节
- 例：512MB 磁盘，簇 = 8KB → 簇总数 = 512MB÷8KB = 65536 = 2^16 → 每个表项 2B → FAT 表总大小 = 65536×2B = 128KB

> 🧠 **思维误区——"单位转换遗漏"模式**：你在做这种题时经常忘记把自己算出的 bit 数转换成 Byte。Q38 你也有类似问题——"自己算出来是什么单位，答案问的是什么单位，不要光凭直觉选"。

### 2.6 隐式链接的指针在哪里？（原题35）
**隐式链接的指针不在内存 FCB 里，而是藏在每一个磁盘数据块的末尾。**

在中间插入一块时：内存中文件头指针改一下就行（0 次 I/O），但是块 X 内部原本写着"下一个指向空"的指针现在必须改成"下一个指向原本的第一块"。因为块 X 在磁盘上，**必须把块 X 读入内存，修改尾部指针，再写回磁盘**。

单级索引的话，改标记完全能解决（不需要读数据块）。

> 🧠 **思维误区——"指针在哪"的混淆**：你没注意到隐式链接和显式链接（FAT）的关键差异——FAT 的指针在内存，隐式链接的指针在磁盘数据块末尾。

### 2.7 连续分配的"移动"需要读+写（原题36）
你问：连续分配不是随机访问吗？为什么要读 45 次？

在计算机底层，"把磁盘上的块 A 挪到位置 B"的真实物理动作是：
1. 启动磁盘 I/O，把块 A 内容**读入**内存缓冲区
2. 启动磁盘 I/O，把内存缓冲区内容**写入**磁盘的 B 位置

→ 读写各算一次。即使连续分配支持随机访问，移动数据仍然需要逐块读写。

### 2.8 多级索引计算 ⚠️（原题37-40 · 37:? 38:!! 39:? 40:?）
**最容易犯的错**：算出有多少个"磁盘块"→ 直接当答案选了。**还需要乘以磁盘块大小才是文件长度！**

**Q37 推导链**：
- 磁盘地址 32 位 = 4B，只用于描述文件块地址
- 10 个直接指针 → 10 个数据块
- 1 个一级间接指针 → 指向一个索引块（4KB），容纳 4KB÷4B = 1024 个地址 → 1024 个数据块
- 总计：10 + 1024 = 1034 个数据块
- 索引信息总大小 = (10+1)×4B = 44B，远小于 4KB，不需要独立的盘块

**Q38 陷阱**：二级索引，一个盘块 2^8 个地址 → 2^8 × 2^8 = 2^16 个磁盘块 → **还要乘以磁盘块大小！**

> 🧠 **思维误区——"单位跳跃"模式**：你连续在 Q37-Q40 上出错，共同点是：算出了物理单位个数就以为算完了，忘了最后一个乘号。这是你的一个系统性问题——算出的东西是盘块数、bit 数还是字节数，必须看清楚。

### 2.9 FAT 用数组不用链表的原因（原题40）
**FAT 有随机访问的需求**——要快速定位某个簇号在 FAT 表中的位置（通过簇号直接做数组下标）。如果用链表，要 O(n) 遍历。

### 2.10 FCB 的内容（原题41）
FCB 包含：**基本信息、存取控制信息、使用信息**。

## 三、open / read 的完整流程

### 3.1 为什么 read 只需要 fd？（原题44）
**`open("/a/b/c.txt")` 的完整流程**：
1. OS 去磁盘找根目录 `/`，搜索找到 `a` 的 Inode
2. 读 `a` 的数据块，搜索找到 `b`
3. 读 `b` 的数据块，找到 `c.txt` 的 Inode 编号
4. **（大量磁盘 I/O 发生在这里！）**
5. 把 `c.txt` 的 Inode 从磁盘复制到内存的**系统级打开文件表**
6. 在**进程级打开文件表**中找一个空闲格子（比如 3 号），指向系统表里的 Inode
7. 返回数字 `3` → 这就是**文件描述符（fd）**

**`read(3, buf, 100)` 只需要 fd 的原因**：
- 直接去进程表找第 3 个格子 → 顺着指针瞬间找到内存 Inode
- Inode 里有物理块地址 + **读写指针（当前读到第几个字节了）**

**`read` 期间进程的状态切换**：
- 数据不在内存 → OS 剥夺该进程 CPU，从运行态切换到**阻塞态/睡眠等待**
- 内核在核心态检查权限、查系统打开文件表、指挥磁盘读数据
- 数据从内核缓冲区拷贝到用户区缓冲区
- 切换回**用户态**，控制权还给你
- **任何系统调用（open/close/read/write）都伴随一次用户态→核心态切换**

### 3.2 单个文件长度 vs 文件数量上限（原题46 · !!）
**单个文件的最大长度** = n（文件块数）× 块大小，由索引结构（几级间接指针）决定。

**Inode 总数**决定的是**这块硬盘上最多能存多少个文件**（文件数量的上限），而不是单个文件能有多大。哪怕你只有 2 个 Inode，只要级数够多、块够大，单个文件依然可以塞满整个硬盘。

> 🧠 **思维误区——"总量 vs 个体"混淆**：你把"文件数量上限"和"单个文件大小上限"当成了同一件事。

### 3.3 快速随机访问选连续结构（原题47）
要快速随机访问，选**连续结构**。

## 四、权限与文件大小计算

### 4.1 权限位的存储（原题50）
权限是**同时并存**的，不是"单选"的——文件必须把**所有人**的**所有权限**全部刻在 FCB 里。

4 类用户 × 5 种权限位 = **20 位**（不是 5 位！）

> 🧠 **思维误区——"权限是单选还是多选"**：你把权限理解成了"某个人"的"某种权限"，但 FCB 里存的是所有人所有权限的完整矩阵，是横向排开各自独立地盘的。

### 4.2 文件物理空间 ≠ 文件逻辑大小（原题51）
你没搞懂题意：求"磁盘空间大小"不就应该是文件大小吗？

**考点**：文件以**簇**为单位分配空间。哪怕只写了 1 字节，系统也必须批一整簇。所以：
- 文件逻辑大小 = 实际内容字节数
- 文件物理占用 = 簇数 × 簇大小（有内部碎片）
- **扇区是硬件单位，和文件分配无关！**（多个扇区合并定义为簇）

> 🧠 **思维误区——"扇区 = 分配单位"**：你混淆了硬件寻址单位（扇区 512B）和文件系统分配单位（簇 = 多个扇区）。

### 4.3 创建文件数量上限（原题52）
**创建文件数量上限 = 索引节点（Inode）数量上限。**

### 4.4 文件总数 ≠ FCB 总数（原题53 相关）
理解了这个就好。

## 五、文件目录

### 5.1 散列查找的局限性（原题1）
散列（Hash）确实快（O(1)），但：
- 有**哈希冲突**
- 目录文件变大时动态扩容非常麻烦
- **不支持模糊查找**（如 `*.txt`）
- 现代 OS 并非"都用它替代"，而是混合使用（NTFS/Ext4 喜欢用 **B+ 树/B 树**）

**路径查找**：找 `/usr/bin/gcc`，如果根目录里连 `usr` 都没找到，后面的 `bin` 和 `gcc` 根本不用找——"只要一个分量名未找到，就停止查找"。

UNIX/Linux 中，目录检索完成后拿到的仅仅是**Inode 编号**，还必须再去 Inode 表查一次才能拿到物理地址。

> 🧠 **补**：在树形目录中存在"当前目录"的定义，所以不一定每次从根目录按文件路径找。

### 5.2 多级目录的目的（原题3）
多级目录结构的目的是**解决命名冲突**（不同目录下可以有同名文件）。

**难道没有缩短时间吗？** 没有，反而**增加了**——多级目录和索引不同，不能随机访问，级数越多开销越大。查 `/a/b/c/d/e.txt` 要发生 5 次目录文件的磁盘 I/O。

> 🧠 **思维误区——"分级 = 索引 = 快"**：你把多级目录的"级"和多级索引的"级"混淆了。多级索引是用空间换随机访问（快），多级目录是为了命名隔离，反而增加了寻址 I/O。

### 5.3 硬链接 vs 软链接（符号链接）（原题6）
| | **硬链接** | **软链接（符号链接）** |
|---|---|---|
| 建立时 | 目录里加一个名字，指向**同一个 Inode**，Inode 的链接计数 +1 | **重新开户**——创建一个独立的新文件，里面存目标路径字符串 |
| Inode 链接计数 | +1（同一个计数器被多个文件名共享） | 目标文件计数**不变**；软链接自身的计数 = 1（因为它是独立的新文件） |
| 本质 | 同一个文件的多个名字 | 一个指向另一个文件的"路标文件" |

> 🔗 你的卡片完美覆盖：[[../卡片/辨析--引用计数器]]

### 5.4 硬链接的访问权限不一定相同 ⚠️（原题7 · !!）
F1 和 F2 共享同一个 Inode，**文件本身设定的读写权限绝对一样**。

但**访问权限是双向的**——还要看**是谁在访问**！如果进程 P1 是 root 运行，P2 是 guest 运行，则 P1 可以随意读写，P2 可能连看的资格都没有。所以**不同进程对同一文件的访问权限不一定相同**。

> 🧠 **思维误区——"属性单向思维"模式**：你只考虑了文件自身的权限属性，没考虑访问者的身份。权限 = 文件属性 × 访问者身份。

### 5.5 文件打开后不再用文件名（原题8）
只要文件被打开了，以后用户都不再用文件名而使用**文件描述符（fd）**，不管采用什么样式的目录结构。

### 5.6 目录检索 I/O 计算（原题13）
光写了找到目录项所需的 I/O，但**读入索引节点还需一次 I/O！**

> 🧠 **思维误区——"只算了找名字，忘了读 Inode"**：这是一个典型的惯性错误——找到文件名 ≠ 拿到文件数据。找到目录项后还需要读 Inode 才能得到物理块号。

### 5.7 删除文件 ≠ 删除快捷方式（原题17）
**删除文件不会导致快捷方式被删除**（快捷方式 = 软链接，是独立的文件）。

## 六、文件系统整体架构

> 🔗 你已经有超详细的卡片：[[./卡片/记忆--文件系统架构]]

### 6.1 文件系统的意义（原题1）
从用户角度看，文件系统的意义就是**能够按名存取文件**。否则就得写"存在硬盘第 3 张盘片第 12 磁道第 8 扇区"。

此外：
- **硬件大一统（抽象化）**：把不同的物理设备统一成文件接口
- 磁盘分配与回收
- 保护与共享
- 持久化与一致性

### 6.2 逻辑文件系统的功能 ⚠️（原题2 · !!）
逻辑文件系统的功能：
- 对文件**按名存取**
- 文件目录组织管理
- **文件名转换为文件描述符**
- 存储保护

> 🧠 **思维误区——"层级功能混淆"**：你容易把逻辑文件系统（第2层）和文件组织模块（第3层）的功能搞混。**只要涉及到"名字→fd""权限检查""维护打开文件表"，就是逻辑文件系统。只要涉及到"逻辑块号→物理块号""分配方式（连续/链接/索引）"，就是文件组织模块。**

### 6.3 文件区 vs 对换区的不同目标（原题6）
| | **文件区** | **对换区** |
|---|---|---|
| 目标 | **省空间**（精打细算） | **拼速度**（简单粗暴） |
| 分配方式 | 离散分配（切碎成块、多级索引） | 通常**连续分配** |
| 为何？ | 用户空间宝贵，犄角旮旯都要用 | 为了速度宁可浪费空间，不让磁头到处寻道 |

> 🧠 **思维误区——"对换区也要省空间"**：你把文件区和对换区的优化目标搞反了。对换区是临时中转站，速度优先；文件区是长期存储，空间利用率优先。

### 6.4 超级块/引导块/分区引导程序辨析（原题9 · !）
这是极易混淆的概念群：

| 概念 | 是什么 | 在哪里 |
|------|--------|--------|
| **MBR（主引导扇区）** | 硬盘第 0 个扇区——一个容器 | 磁盘最开头 |
| **主引导程序** | MBR 里装的**可执行代码**（446B） | 在 MBR 容器内 |
| **硬盘分区表** | MBR 里的分区布局信息（64B） | 在 MBR 容器内 |
| **分区引导扇区** | 每个分区的第 0 个扇区 | 每个分区开头 |
| **分区引导程序** | 分区引导扇区里装的 OS 启动代码 | 在分区引导扇区内 |

> 🧠 **思维误区——"容器 vs 内容"混淆**：你把"引导扇区"（物理位置）和"引导程序"（里面的代码）当成了一个东西。这和 MBR 是一个容器、里面装了引导程序和分区表，是类似的套路。

### 6.5 空闲空间管理方法 ⚠️（原题11 · !!）

| 方法 | 核心特征 | 连续分配友好度 |
|------|----------|:--:|
| **空闲表法** | 表格记录 [起始块号, 空闲块数]，类似内存动态分区 | ✅ 绝配 |
| **空闲盘块链** | 每个空闲块里藏指针串联，以"块"为单位 | ❌ 极难获得连续空间 |
| **空闲盘区链** | 每个连续空闲区串联，以"区"为单位 | ✅ 较容易分配连续空间 |
| **位示图法** | 二进制矩阵，每 bit 代表一个盘块的空/忙 | 中等 |
| **成组链接法** | UNIX 大招，100块一组套娃，内存栈+磁盘接力 | 中等 |

> 🔗 你的卡片：[[../卡片/辨析--四种外存空闲空间管理]]

### 6.6 位示图计算 ⚠️（原题14 · !/ 原题16 · !!）
**核心注意**：看清楚题干是**从 0 开始**还是**从 1 开始**！

**Q14 完整推导**（从 0 开始，盘块号 409612，盘块大小 1024B）：
1. $409612 \div 8 = 51201 \cdots 4$（商 = 字节号，余数 = 位内位置）
2. $51201 \div 1024 = 50 \cdots 1$（商 = 盘块号偏移，余数 = 盘块内字节号）
3. 位图从 32 号块开始存放 → 最终在**物理 82 号块（32+50）的块内第 1 号字节**

**Q16 陷阱**：算出来的是 $2^{22}$ **bit**!!!! 选项是 Byte，要除以 8！

> 🧠 **思维误区——"单位跳跃+下标偏移"双杀模式**：这是你最顽固的错误模式。Q14 同时踩了"从哪开始编号"的坑（＋32 号块偏移），Q16 又踩了 bit→Byte 转换的坑。位示图题必须强制自己：**第一步圈出"从 0/1 开始"，最后一步检查"答案是什么单位"。**

### 6.7 FAT 表天然兼职空闲空间管理（原题15）
FAT 表是一张覆盖全磁盘的"全局大网"。如果物理块 88 空闲，FAT 表的第 88 行就填特殊标记（如 0 或 FREE）。

操作系统找空闲块时，**直接从头遍历内存里的 FAT 表**——谁的格子里填的是 0，谁就是空闲块。**FAT 表天然就兼职了"空闲表"的功能**，不需要额外建空闲链表或位示图。
