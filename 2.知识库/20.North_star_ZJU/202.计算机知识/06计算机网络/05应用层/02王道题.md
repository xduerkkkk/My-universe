你的两个疑问暴露出考研中极其高频的两个核心概念混淆：**“DNS 的传输层协议”** 以及 **“面向无连接 vs 非持续连接”**。下面逐一进行纠偏：

---

### 一、纠偏 1：DNS 客户端与服务器之间根本不用 TCP 建立连接

* **技术事实**：主机向本地域名服务器（Local DNS）发起查询，以及 Local DNS 向上级服务器发起查询，**默认全部运行在 UDP 协议之上（熟知端口 53），是完全面向无连接的**。
* **为什么不用 TCP？**
  * 若使用 TCP：主机必须先进行**三次握手（耗费 1 个 RTT）**，再发查询请求得到回复（再耗费 1 个 RTT），解析时延直接翻倍；且服务器需要维持巨量的 TCP 控制块（TCB），并发性能极差。
  * 采用 UDP：客户端直接发送 1 个 UDP 数据报，服务端回 1 个 UDP 数据报，**无需握手，无需挥手，即发即走（面向无连接）**。
* **DNS 在什么特例下才使用 TCP？（408 补充考点）**
  1. **区域传送（Zone Transfer）**：主域名服务器与从域名服务器同步完整数据库时（数据量大，需可靠传输）。
  2. **报文超长**：当响应报文长度超过 **512 字节** 且未协商扩展 DNS（EDNS0）时，服务端会在响应中将截断标志位（**TC 标志**）置 1，强制客户端转用 TCP 重新发起查询。

---

### 二、纠偏 2：“非持续连接”绝不等于“面向无连接”

这是 408 中最具迷惑性的概念陷阱：

| 概念 | 所处层次 | 核心含义 | 典型代表 |
| :--- | :--- | :--- | :--- |
| **面向无连接<br>(Connectionless)** | **传输层 / 网络层** | 通信双方**完全没有建立连接（握手）和释放连接（挥手）的过程**。直接把报文丢进网络，不维护通信状态。 | **UDP、IP** |
| **非持续连接<br>(Non-persistent)** | **应用层** | 依然**严格基于面向连接的 TCP**。传输每个 Web 对象前都要**建立一次完整的 TCP 连接（三次握手）**，传输完毕后**立即释放该 TCP 连接（四次挥手）**。 | **HTTP/1.0** |

* **HTTP 的本质**：
  * HTTP 协议（无论是 HTTP/1.0、HTTP/1.1 还是 HTTP/2）都运行在 **TCP 协议（端口 80）** 之上，因此 **HTTP 必定是面向连接的**。
  * **非持续连接（Non-persistent Connection）** 只是说明一个 TCP 连接不能跨对象复用（发一张图片就断开一次 TCP），但它每一次发送数据前，**都必须老老实实执行三次握手建立 TCP 连接**，绝不是“无连接”。

---

### 一、详细计算过程（时间时序拆解）

本题明确给出条件：**非持久 HTTP/1.0**、**支持并行 TCP 连接**、**1 个 Web 基础页（HTML）+ 7 个引用图像**、**求“至少”所需的 RTT 数**。

必须分为两个**有先后依赖顺序**的阶段：

#### 阶段 1：获取基础 Web 页（HTML 文件）
浏览器必须先拿到 HTML 文件并解析它，才能知道页面里引用了哪 7 个图像，因此基础页**必须单独先下载**：
1. **TCP 三次握手**：耗时 **1 个 RTT**（第三次握手的 ACK 可以捎带 HTTP 请求）。
2. **HTTP 请求与接收 HTML 文件**：耗时 **1 个 RTT**。
- **阶段 1 总耗时** = $1 + 1 = 2 \text{ RTT}$。
- *传输完毕后，因为是非持久连接，该 TCP 连接立即断开。*

#### 阶段 2：获取 7 个引用的图像文件
浏览器解析 HTML 发现了 7 个小图像。因为题目指明**“支持并行连接”**且求**“至少”**，所以浏览器会**同时并发建立 7 条独立的 TCP 连接**：
1. **7 条 TCP 连接同时发起握手**：由于是并行进行，总耗时依然为 **1 个 RTT**。
2. **7 条连接同时发送 HTTP 请求并接收图片数据**：并行进行，总耗时依然为 **1 个 RTT**。
- **阶段 2 总耗时** = $1 + 1 = 2 \text{ RTT}$。

#### 最终总耗时
$$\text{总 RTT} = \text{阶段 1 (2 RTT)} + \text{阶段 2 (2 RTT)} = 4 \text{ RTT}$$

### 二、核心考点拆解（408 必考机制）

#### 1. 单个对象在非持久 HTTP/1.0 中的基础开销 = 2 RTT
- **第 1 个 RTT**：TCP 连接建立（Client 发送 SYN，Server 回复 SYN+ACK）。
- **第 2 个 RTT**：Client 发送第三次握手 ACK（捎带 `HTTP GET` 请求），Server 响应并回传对象数据。
- 单个 Web 对象在非持续连接下的总响应时延 = $2 \text{ RTT} + \text{传输时延}$（题目中“小图像”意味着传输时延忽略不计）。

#### 2. HTML 与内嵌对象的“依赖阻塞”
- 基础 HTML 与内嵌的 7 个图片**不能从一开始就并行**。
- 只有接收完 HTML 并完成语法解析，浏览器才能获得图片的 URL，因此阶段 1 和阶段 2 是**严格串行**的。

#### 3. 并行连接（Parallel Connections）的时延折叠
- 并行连接是指客户端同时向服务器建立多条 TCP 连接。
- 在理想状态下（带宽与服务器性能充足），$N$ 个对象的握手与数据传输在时间轴上是重叠的，耗时等同于传输 1 个对象（即 $1 \text{ RTT} + 1 \text{ RTT} = 2 \text{ RTT}$）。

### 三、考点发散：408 常见 4 种 HTTP 连接模式耗时对照表

假设获取 **1 个 HTML 页面 + $N$ 个内嵌对象**（忽略传输时延与 DNS 解析时延）：

| 连接模式                               | 耗时公式                                                   | 若 $N=7$ 时的总 RTT                        |
| :--------------------------------- | :----------------------------------------------------- | :------------------------------------- |
| **1. 非持续 + 无并行（完全串行）**             | $2 + 2N$                                               | $2 + 2 \times 7 = \mathbf{16\ RTT}$    |
| **2. 非持续 + 支持并行（本题）**              | $2 + 2$（假设完全并行）                                        | $2 + 2 = \mathbf{4\ RTT}$              |
| **3. 持续连接 + 非流水线（Non-pipelining）** | $1\text{(TCP)} + 1\text{(HTML)} + N \times 1$          | $1 + 1 + 7 \times 1 = \mathbf{9\ RTT}$ |
| **4. 持续连接 + 流水线（Pipelining）**      | $1\text{(TCP)} + 1\text{(HTML)} + 1\text{(所有对象一次性发出)}$ | $1 + 1 + 1 = \mathbf{3\ RTT}$          |

### 一、本题解题过程

1. **查表匹配（寻找现存映射）**：
   - 收到内网发往外网的数据包：`源 IP = 192.168.32.56`，`源端口 = 80`。
   - NAT 路由器在转换表中检索 `(源 IP, 源端口)`：
     - 表项 1：`(192.168.32.56, 21)` $\to$ 端口不匹配（是 21，不是 80）。
     - 表项 2：`(192.168.32.56, 20)` $\to$ 端口不匹配。
     - 表项 3：`(192.168.48.26, 80)` $\to$ IP 不匹配。
     - 表项 4：`(192.168.55.106, 80)` $\to$ IP 不匹配。
   - **结论**：这是一个**全新的出站连接**，表中**没有现成的匹配项**。

2. **路由器的动作**：
   - **动态建表**：NAT 路由器从未分配的端口池中挑出一个**空闲的外部转换端口**（例如 `2058`），向 NAT 转换表中**添加一条新记录**：
     `[2058, 192.168.32.56, 80]`。
   - **转换与转发**：将数据包的源 IP 替换为公网 IP `205.56.79.35`，源端口替换为 `2058`，重新计算 IP/TCP 头部校验和后转发至公网。

3. **排除错误选项**：
   - **A 错误**：端口 `2056` 已经被 `(192.168.32.56, 21)` 占用，如果复用该端口会导致外网回包时无法区分是发给 21 端口还是 80 端口（端口冲突）。
   - **C 错误**：内网主机主动访问公网是合法行为，NAT 路由器会动态建立映射，而不是丢弃。
   - **D 错误**：私有 IP 地址（`192.168.x.x`）在公网路由器上是**不可路由**的，直接转发会被公网骨干路由器直接丢弃。

### 二、 408 核心考点：NAT / NAPT 工作原理

#### 1. NAT 与 NAPT 的概念区分
- **狭义 NAT（1 对 1 转换）**：仅转换 IP 地址，不转换端口号。缺点是 1 个公网 IP 同时只能供 1 台内网主机上网。
- **NAPT（网络地址与端口转换，考研题中的 NAT 绝大多数指 NAPT）**：**同时转换 IP 地址和传输层端口号**。利用 16 位的端口号（可提供数万个端口），实现数百台内网私有主机**共享同一个公网 IPv4 地址**同时上网。

#### 2. NAT 转换表的出站与入站处理规则（核心机制）

* **出站（内网 $\to$ 外网，主动发起请求）**：
  1. 路由器检查数据报的 `(私网源 IP, 源端口)`。
  2. **若已存在表项**：替换为对应的 `(公网 IP, 转换端口)`，转发。
  3. **若不存在表项**：分配一个**新的空闲公网端口**，在表中**新增一条映射条目**，替换后转发。

* **入站（外网 $\to$ 内网，响应回包）**：
  1. 路由器检查数据报的 `(公网目的 IP, 目的转换端口)`。
  2. **若在表中命中**：替换为对应的 `(私网目的 IP, 私网目的端口)`，转发给内网目标主机。
  3. **若在表中未命中（外网无缘无故主动连接）**：**直接丢弃**（这也是 NAT 具备天然防火墙特性的原因）。

#### 3. NAT 破坏了网络分层的透明性
* 路由器本应工作在 **网络层（第 3 层）**，只查看并修改 IP 头部。
* 但 NAT/NAPT 路由器必须深入读取并修改 **传输层（第 4 层）** 的 TCP/UDP 端口号，并重新计算传输层校验和（Checksum），这违反了严格的分层独立原则。

#### 4. 必须牢记的 3 类专用私有 IP 地址块（408 必背）
* **A 类私有地址**：`10.0.0.0` $\sim$ `10.255.255.255`（掩码 `/8`）
* **B 类私有地址**：`172.16.0.0` $\sim$ `172.31.255.255`（掩码 `/12`）
* **C 类私有地址**：`192.168.0.0` $\sim$ `192.168.255.255`（掩码 `/16`）

*(只要源 IP 在以上三个范围内，报文出内网前必须经过 NAT 转换)*
