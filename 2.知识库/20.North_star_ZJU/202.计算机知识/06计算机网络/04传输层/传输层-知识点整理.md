## 章节主线

```text
IP 提供主机到主机的尽力而为交付
        ↓
传输层用端口扩展为进程到进程
  ├─ UDP：复用/分用 + 差错检测
  └─ TCP：连接 + 可靠字节流
          ├─ 序号、ACK、重传
          ├─ 流量控制 rwnd
          ├─ 拥塞控制 cwnd
          └─ 握手、挥手、计时器
```

## 1. 传输层服务与套接字

- **复用**：多个应用进程把数据交给同一个传输层协议。
- **分用**：接收端依据端口和连接标识把报文交给正确进程/socket。
- **端口**：16 位；熟知端口通常标识服务器，客户端常由 OS 分配临时端口。
- **UDP socket** 常主要按本地 IP/端口分用；**TCP 连接**通常由四元组唯一标识。

> [!warning] 端口由谁分配
> 应用请求绑定，操作系统内核管理端口命名空间和冲突；TCP 与 UDP 拥有不同端口空间，所以同一主机可同时存在 TCP 53 与 UDP 53。

## 2. UDP

### 2.1 首部

| 字段 | 长度 | 作用 |
|---|---:|---|
| 源端口 | 16 bit | 标识发送进程，可在特定场景为 0 |
| 目的端口 | 16 bit | 接收端分用 |
| Length | 16 bit | UDP 首部 + 数据，最小 8B |
| Checksum | 16 bit | 端到端差错检测 |

### 2.2 伪首部

伪首部把源/目的 IP、协议号和 UDP 长度加入检验和，防止数据被交给错误主机或错误上层协议。它不属于 UDP 在线路上传输的首部；接收端从 IP 首部重建。

IPv4 中 UDP 检验和可按协议规则不使用；IPv6 中 UDP 检验和通常必须使用。408 题目未特别说明时，按教材给出的具体语境处理。

### 2.3 UDP 的边界

UDP 不保证送达、顺序、去重、重传、流量控制和拥塞控制。应用可以在 UDP 之上自行实现可靠机制，但那是应用协议提供的，不是 UDP 本身提供的。

## 3. TCP 首部与字节流

| 字段 | 高频含义 |
|---|---|
| Source/Destination Port | 进程分用 |
| Sequence Number | 本段第一个数据字节序号；SYN/FIN 各占一个序号 |
| Acknowledgment Number | 下一个期望字节，ACK=1 时有效 |
| Data Offset | TCP 首部长度，单位 4B |
| Flags | SYN、ACK、FIN、RST、PSH、URG 等 |
| Window | 接收方通告的 rwnd，单位字节 |
| Checksum | 覆盖伪首部、TCP 首部和数据 |
| Options | MSS、窗口扩大、时间戳、SACK 等 |

TCP 面向的是**无边界字节流**，不是保留应用层报文边界。接收端可把多个 send 合并交付，也可把一次 send 分段接收；应用层若需要消息边界，要自行设计长度字段或分隔符。

## 4. 可靠传输机制

### 4.1 序号与累计确认

- 数据按字节编号。
- ACK=N 表示 N 之前的连续字节都收到，下一字节期待 N。
- 乱序到达的处理、是否立即发送重复 ACK 与缓存策略由实现决定；408 常按累计确认模型。

### 4.2 重传

- **超时重传**：RTO 到期仍未确认则重传；RTO 根据 RTT 估计动态调整。
- **快重传**：收到 3 个冗余 ACK 后，不等 RTO 即重传推测丢失的段。
- **去重**：重复段通过序号识别，不会重复交给应用。

### 4.3 可靠、连接、有序的关系

TCP 的确同时提供连接、可靠和有序，但这不意味着三个词互为定义。底层 IP 仍可丢包、乱序、改路；TCP 靠端系统状态恢复为可靠有序字节流。

## 5. 连接管理

### 5.1 三次握手

```text
Client                    Server
SYN, seq=x        →
                  ←        SYN+ACK, seq=y, ack=x+1
ACK, ack=y+1      →        （第三次可携带数据）
```

三次的核心不是“多确认一次”这么简单，而是让双方确认彼此的初始序号与双向收发能力，并避免迟到旧 SYN 让服务器误建连接。

### 5.2 四次挥手

TCP 全双工的两个方向分别关闭。收到 FIN 只表示对方不再发送数据，本方仍可继续发送，因此 ACK 与自己的 FIN 通常分开；若本方也已无数据，可合并。

主动关闭方最后进入 TIME_WAIT，等待 2MSL；被动关闭方可能停留在 CLOSE_WAIT，直到本地应用主动关闭 socket。

## 6. 流量控制

| 量 | 谁维护 | 是否在首部 | 作用 |
|---|---|---|---|
| `rwnd` | 接收方 | 是 | 通告剩余接收缓存 |
| `cwnd` | 发送方 | 否 | 反映网络拥塞承载能力 |
| `swnd` | 发送方计算 | 否 | `min(rwnd,cwnd)` |

零窗口后不能永久沉默：发送方启动持续计时器，周期性发送零窗口探测，直到收到非零窗口通告。

## 7. 拥塞控制

### 7.1 四个机制

- **慢开始**：`cwnd` 从小值开始，每 RTT 近似翻倍。
- **拥塞避免**：达到 `ssthresh` 后，每 RTT 约增加 1 MSS。
- **快重传**：3 个冗余 ACK 触发提前重传。
- **快恢复**：Reno 中避免回到 1 MSS，恢复后从门限附近线性增长。

### 7.2 教材题与现代实现

> [!warning] 初始拥塞窗口
> 408 传统题常默认 `cwnd=1 MSS`；现代 TCP 实现的初始窗口可能更大。做题必须服从题设或教材模型，不能把工程默认值混入计算。

> [!important] 发送窗口
> `swnd = min(rwnd, cwnd)`  
> 若接收缓存只进不出，`rwnd` 会不断下降；因此 `cwnd` 增长不等于可发送量持续增长。

## 8. TCP 计时器

| 计时器 | 触发 | 超时动作/目的 |
|---|---|---|
| 重传计时器 | 有未确认数据 | 重传，更新拥塞状态 |
| 持续计时器 | 收到零窗口 | 发零窗口探测，防死锁 |
| 保活计时器 | 长期空闲且启用 keepalive | 探测对端，失败后释放资源 |
| TIME_WAIT | 主动关闭方发最后 ACK | 等 2MSL，重发最后 ACK并清除旧报文影响 |

## 9. 公式与计算框架

### 9.1 序号回绕

> [!important] 回绕时间
> `T_wrap = 2^32 B / byte_rate`  
> 若给 bit/s，先除以 8。  
> 题目加入 MSL 时，常令 `T_wrap ≥ MSL` 求安全上限。

### 9.2 窗口与吞吐率

- 简化：`throughput ≤ min(C, W/RTT)`。
- 若 RTT 仅表示传播往返，且发送整个窗口需要 `W/C`：`throughput = W / (W/C + RTT)`。
- 带宽时延积：`BDP = C × RTT`；窗口至少接近 BDP 才能填满管道。

### 9.3 首部效率

- 传输层效率：`应用数据 / (应用数据 + 传输层首部)`。
- 若题目问 IP 数据报或以太网帧效率，分母必须继续加入对应下层首部。

## 10. TCP 大题时间轴模板

1. 明确计时起点：发 SYN、连接建立、发首个数据还是应用请求。
2. 标注第三次握手是否捎带请求。
3. 按 `cwnd/rwnd` 计算每 RTT 可发多少 MSS。
4. 判断 ACK、FIN 是否能与数据捎带或合并。
5. 主动关闭方进入 TIME_WAIT 后再加 2MSL。
6. 若给发送速率或段长，别忘发送时延；若题目明确忽略，则不要自行添加。

## 11. 跨层边界

- 以太网 MTU 1500B 不包含以太网首部/FCS。
- IP 分片属于网络层；TCP 通常通过 MSS 避免自身报文段触发 IP 分片，UDP 大报文则更容易被 IP 分片。
- 两次应用重传产生两个不同 IP 数据报，分片不能只按“内容相同”混合重组，必须匹配 IP 分片标识等条件。

## 12. 校正与条件

> [!warning] “面向连接就天然可靠、有序”
> **校正**：面向连接只是维护通信状态。TCP 之所以可靠有序，是因为它另外设计了序号、确认、重传、缓存与控制机制。

> [!warning] “TCP 连接路径固定”
> **校正**：TCP 端点与连接状态固定，底层 IP 路径可以变化；乱序由 TCP 在端系统恢复。

> [!warning] “端口是协议分配的”
> **校正**：应用通过 socket 请求，操作系统管理分配；TCP/UDP 分别维护端口命名空间。

> [!warning] “以太网 MTU 1500B 含以太网首部”
> **校正**：1500B 是以太网载荷上限，通常对应完整 IP 数据报；帧首部和 FCS 另计。

> [!warning] “保活计时器固定两小时且必然存在”
> **校正**：两小时是传统默认示例；是否启用、间隔与重试次数由操作系统和应用配置。

## 13. 绝对词检查

- **“ACK 不消耗序号”**：纯 ACK 不消耗；若同时携带数据，则数据仍消耗序号。
- **“FIN 是第四次挥手”**：谁主动关闭、ACK/FIN 是否合并都会改变报文排列。
- **“窗口越大吞吐率一定越高”**：受链路带宽、RTT、接收窗口、丢包与拥塞限制。
- **“UDP 不可靠所以应用一定不可靠”**：应用可自行在 UDP 之上实现可靠性。
