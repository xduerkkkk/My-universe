CRC
1. **直接发 `73` 行不行？**
    
    不行。如果中间信号干扰，`73` 变成了 `75`，我收到 `75` 怎么知道它错了？
    
2. **CRC 的做法：**
    
    - 你要在 `73` 后面**补一个 0**，变成 `730`。（这就相当于图片里的**移位补 0**）。
        
    - 然后你用 `730` 除以我们约定的暗号 `9`：$730 \div 9 = 81 \dots 1$ （余数是 1）。
        
    - 接下来，你把这个**余数 1**，偷偷替换掉刚才补的那个 0，替换的逻辑本质上是**“减去余数也就是把 `730` 变成了 `729`。
        
3. **发送与接收：**
    
    - 你把拼好的 `729` 发给我。
        
    - 我收到 `729` 后，马上用我们约定的暗号 `9` 去除：$729 \div 9 = 81 \dots 0$。
        
    - **重点来了！因为余数是 0（完美整除），我就敢 100%确定，数据在传输过程中没有出错！** 如果信号干扰变成了 `725`，我除以 `9` 余数肯定不是 0，我就知道数据坏了，让你重发。
        

**这就是 CRC 的全部逻辑！** 剩下的，只是把十进制换成了计算机喜欢的“二进制”而已。
![](../../../../../assets/image/01王道视频-1776763370383.jpeg)

- **$G(x) = x^3 + x^2 + 1$** 只是一个纸老虎，它就是用来生成我们刚才说的“暗号”的。

最高次幂是 3（$x^3$），这意味着什么？意味着最后产生的余数**最多只有 3 位**。

- 既然余数有 3 位，我们就得在信息后面**补 3 个 0**，变成 `101001000`。
    
- 这就好比上面例子里把 `73` 变成 `730`，给即将算出来的余数（CRC 码）腾地方
为什么不用普通的加减乘除？因为计算机硬件做普通的除法太慢了（要考虑借位）。所以前人发明了“模 2 除法”（其实就是 **异或运算 XOR**）。

- **异或规则极其简单：相同为 0，不同为 1。** （完全不用管什么借位）。
    
- 用带着 0 的数据 `101001000` 去“除以”暗号 `1101`。
    
- 算到最后，得出余数是 `011`。（这就是那 3 位 CRC 校验码）。
    

#### 第四步：拼接发送

- 把算出来的余数 `011`，填到刚才补 0 的位置上。
    
- 最终发送出去的数据就是：`101001011`

### 为什么“模 2 除法”就是异或？它怎么做到不改变前面数字的？

计算机硬件如果做普通的加减乘除，是非常慢的，因为要一直算进位和借位（比如 9999 + 1，要连进 4 次位，电路会等得不耐烦）。

为了在网络传输中追求极致的计算速度，数学家们引入了“模 2 运算”这种神奇的规则，它的核心法则只有一条：**不进位，不借位**。

在这种规则下，奇迹发生了：**加法、减法、异或，这三者变成了一模一样的东西！**

你来看看“不借位的减法”是什么结果：

- 1 - 1 = 0 （和异或“相同为 0”一样）
    
- 0 - 0 = 0 （和异或“相同为 0”一样）
    
- 1 - 0 = 1 （和异或“不同为 1”一样）
    
- 0 - 1 = **1** （注意这里！普通减法要借位，但模 2 减法不借位，直接等于绝对差值 1。这就和异或“不同为 1”一样！）
    

**既然减法 = 异或，那么除法是什么？** 你小学学过，除法本质上就是**不断地做减法**（比如 10 除以 3，就是 10-3-3-3 剩 1）。所以在模 2 的世界里，**除法就顺理成章地变成了“不断地做异或”**！

### 最终联动：为什么二进制里的“减去余数”像是“偷偷替换”？

刚才我们在十进制里说，要把余数**减掉**（730 - 1）才能完美整除。在二进制 CRC 里，我们同样是把补 0 后的数据，**减去算出来的余数**。

但是，因为**模 2 减法 = 异或**，我们来看看把带有三个 0 的数据 `101001000` 减去余数 `011` 会发生什么：

Plaintext

```
  101001000 (信息码+补的0)
-       011 (余数)
----------- (模2减法，即异或，不借位！)
  101001011
```

你看！因为是异或运算，任何数异或 0 都等于它自己。所以：

- 前面 `101001` 异或 `000000`，完全没变。
    
- 后面补的 `000` 异或 `011`，直接变成了 `011`。
    

它没有产生任何借位，完美保留了前面的信息码，看起来就像是把后面的三个 0 给**“生生替换”**掉了一样。这就是数学之美，也是 CRC 校验能在网卡里以极高速度运行的根本原因！

# 流量控制可靠传输

## 停止等待
滑动窗口，T 和 R 都是 1
确认机制，接受方接受到 i 号帧且没有检测出差错，则返回确认帧
重传机制，若发送方超时未收到确认帧，则重传
帧编号，要求 $W_T +W_R <= 2^n$  （所有都这样，不再赘述。理由是


假设我们用 $n$ 个比特来编号，那么总共可用的序号池大小就是 $2^n$（序号从 $0$ 到 $2^n - 1$）。

**第一步：发送方火力全开**

发送方一口气发送了填满整个发送窗口 $W_T$ 的数据帧。假设序号是从 $0$ 到 $W_T - 1$。

**第二步：接收方完美接收，窗口前移**

接收方运气很好，完美收到了这 $W_T$ 个帧。

此时，接收方会做两件事：

1. 发送确认帧（ACK）。
    
2. 将自己的接收窗口向前滑动 $W_T$ 个位置。
    
    此时，接收方正在**期待接收的新帧**的序号范围变成了：$[W_T, W_T + W_R - 1]$。
    

**第三步：天有不测风云（极端情况发生）**

接收方发出去的所有 ACK，在网络中全部丢失了！发送方一个都没收到。

**第四步：发送方超时重传**

发送方的计时器超时了。它认为自己刚才发的 $0$ 到 $W_T - 1$ 号帧全丢了，于是它开始**重传旧的 $0$ 号帧**。

**第五步：避免灾难的关键判决**

现在，重传的旧 $0$ 号帧到达了接收方。

接收方目前的接收窗口期待的序号范围是 $[W_T, W_T + W_R - 1]$。

如果这个“旧 $0$ 号”的序号，刚好落在了接收方期待的“新序号”范围内，接收方就会把它当成新数据收下，这就造成了极其严重的数据错误！

为了绝对防止这种情况发生，**新接收窗口的最右边界，绝对不能碰到下一轮的序号 $0$（也就是绝对不能超过序号池的总容量 $2^n$）**。

因此，数学表达就是：

接收窗口的上限索引 $< 2^n$

$$W_T + W_R - 1 < 2^n$$

因为窗口大小都是整数，所以得出核心公式：

$$W_T + W_R \le 2^n$$）

## 错误处理的规律
### 规律一：窗口滑动的“唯一通行证”
**规律：发送窗口的左边缘能否右移，只取决于“窗口内最早的那个帧”是否收到了应答。**

*   不论是哪种协议，发送窗口就像一列火车。火车头（窗口右侧）可以不断吃进新数据，但火车尾（窗口左侧，即最早的那个未确认帧）如果不动，整列火车就卡住了。
*   **在“数据帧丢失”或“确认帧丢失”时：** 那个最早的帧会因为等不到 ACK 而超时。只要它不被确认，窗口就**绝对不会移动**。
*   **后果：** 窗口被堵塞，发送端最终会停止发送，直到超时重传。

---

### 规律二：数据丢失 vs. 确认丢失（ sender 的视角）
**规律：对发送方（Sender）来说，数据丢失和确认丢失是“等价”的，最终都会触发超时重传。**

*   **数据帧丢了：** 接收方没收到 $\rightarrow$ 没发 ACK $\rightarrow$ 发送方超时 $\rightarrow$ **重传**。
*   **确认帧（ACK）丢了：** 接收方收到了 $\rightarrow$ 发了 ACK 却丢在半路 $\rightarrow$ 发送方没收到 $\rightarrow$ 发送方超时 $\rightarrow$ **重传**。
*   **共性结论：** 发送方很“多疑”。只要在规定时间内没看到对应的 ACK，它就默认对方没收到，直接重发。重发后，接收方如果发现是重复帧，直接丢弃数据并补发一个 ACK 即可。

---

### 规律三：累积应答（Cumulative ACK）的“掩盖”效应
**规律：在 GBN（以及某些实现的停止-等待）中，后一个 ACK 可以“顺便”确认前一个帧。**

这是理解“确认帧丢失”时最关键的规律。
*   假设发送了帧 1, 2, 3。
*   **场景：** ACK 1 和 ACK 2 都丢了，但 ACK 3 成功到达了。
*   **在 GBN 中：** 发送方收到 ACK 3，会认为“既然 3 都收到了，说明 1 和 2 肯定也收到了”（因为 GBN 接收端只按序接收）。
*   **结果：** 窗口直接越过 1 和 2，猛地向右滑动到 3 之后。**之前的 ACK 丢失被“掩盖”了，不影响传输。**
*   **在 SR（选择重传）中：** 不行。SR 是“点对点应答”，ACK 3 只管帧 3。ACK 1 丢了，帧 1 必须超时重传。

---

### 规律四：接收窗口大小决定了“挑食”程度
**规律：接收窗口 $W_r = 1$（如 SW, GBN）是“完美主义者”，$W_r > 1$（如 SR）是“缓存大师”。**

*   **当数据帧丢失时：**
    *   **$W_r = 1$ 的 GBN：** 非常固执。如果你丢了帧 2，后面来的帧 3, 4, 5 哪怕全到了，它也全部**乱序丢弃**，并一直发 `ACK 1`（告诉你：我要的是 2！）。这导致了 GBN 的“后退 N 帧”现象。
    *   **$W_r > 1$ 的 SR：** 比较包容。丢了帧 2，后面来的帧 3, 4, 5 会先**存在缓存里**。它只发 `ACK 3, 4, 5` 告诉发送方这些到了，等发送方重传帧 2 补上缺口后，窗口才一起滑动。

---

### 综合对比总结表

| 场景 | 规律总结 |
| :--- | :--- |
| **数据帧丢失** | 无论哪种协议，都会导致发送方**超时重传**。区别在于 GBN 浪费带宽（重传一堆），SR 精准补救。 |
| **ACK 丢失** | **GBN 具有鲁棒性**：靠后续的 ACK 能救回来；**SR 比较死板**：丢哪个 ACK 就重传哪个帧。 |
| **窗口移动** | 只有**窗口左界**被确认了，窗口才能右移。这就是为什么“丢帧”会造成“停顿”。 |
| **编号重复** | 为了不让接收方分不清“这是老帧还是新帧”，**窗口总大小必须小于序号范围的一半**（SR 是 $2^{n-1}$，GBN 是 $2^n-1$）。 |

**一句话记住它们的区别：**
*   **停止-等待**：一次只玩一个，简单但慢。
*   **GBN**：发送方大手大脚，接收方极其挑食（只要按序的）。
*   **SR**：发送方精准，接收方带缓存（能容忍乱序）。
