## 一、管程基本概念

### 1.1 定义与组成

**管程 (Monitor)** 是一种高级同步机制，由 **共享资源 + 操作方法 + 同步机制** 三部分组成：

```
Monitor MonitorName {
    // 1. 共享数据结构
    共享变量声明;
    
    // 2. 条件变量 (用于阻塞/唤醒)
    condition x, y;
    
    // 3. 对共享数据的操作 (过程/函数)
    public entry P1(...) { ... }
    public entry P2(...) { ... }
    
    // 4. 初始化代码
    initialization code;
}
```

### 1.2 核心特性

| 特性 | 说明 | 与信号量对比 |
|------|------|------------|
| **互斥性** | 任一时刻只有一个进程在管程内执行 | 需要手动用互斥信号量实现 |
| **封装性** | 共享变量只能通过管程内过程访问 | 信号量全局可见 |
| **语言级支持** | 编译器自动保证互斥 | 程序员手动 PV 操作 |
| **条件同步** | wait/signal 操作条件变量 | PV 操作信号量 |

## 二、管程 vs 信号量的语义差异 ⭐⭐⭐

### 2.1 Signal 丢失 vs V 累积

这是 **408 真题高频考点**！必须形成清晰对比：

||信号量 V|管程 Signal
|---|---|---|
|无等待者时|值+1，**累积**（下次 P 不阻塞）|**丢失**，无任何效果|
|有等待者时|唤醒一个|唤醒一个|
|语义|**记忆型**|**信号型**|
|典型错误|多次 V 导致多进程进入临界区|以为 Signal 会累积|

**例题辨析**：
```c
// 信号量版本
semaphore s = 0;
V(s); V(s);  // s = 2
P(s);        // 不阻塞, s = 1
P(s);        // 不阻塞, s = 0

// 管程版本
condition x;
x.signal(); x.signal();  // 两次都丢失
x.wait();                // 阻塞！因为没有累积
```

### 2.2 Wait 后的执行次序

管程有两种语义模型（408 考过选择题）：

| 模型 | Wait 后谁先执行 | 代表系统 |
|------|----------------|---------|
| **Hoare 语义** | 被唤醒进程立即执行 | 经典管程 |
| **Mesa 语义** | 唤醒者继续，被唤醒进程进入就绪队列 | Java (synchronized + notify) |

**408 默认**: Hoare 语义（除非题目明确说明）

## 三、管程的实现机制

### 3.1 两个队列

```
        请求进入
           ↓
    [Entry Queue]  ← 等待进入管程的进程
           ↓
    ┌──────────────┐
    │   Monitor    │
    │  (互斥执行)   │ ← 只有一个进程在内部
    └──────────────┘
           ↓
    condition x.wait()
           ↓
    [Condition Queue] ← 在条件变量上等待的进程
```

### 3.2 条件变量操作

| 操作 | 语义 | 当前进程状态 |
|------|------|------------|
| `x.wait()` | 阻塞在条件 x 上，**释放管程锁** | 进入 x 的条件队列 |
| `x.signal()` | 唤醒 x 队列中一个进程 | Hoare: 自己阻塞; Mesa: 继续执行 |

**关键**: wait 必须释放锁，否则其他进程无法进入管程改变条件！

## 四、经典同步问题的管程实现

### 4.1 生产者-消费者 (有界缓冲区)

```c
Monitor ProducerConsumer {
    int buffer[N];
    int count = 0;      // 当前产品数
    condition notFull, notEmpty;
    
    public entry Produce(item) {
        if (count == N)
            notFull.wait();  // 满了就等待
        buffer[count++] = item;
        notEmpty.signal();   // 唤醒消费者
    }
    
    public entry Consume() {
        if (count == 0)
            notEmpty.wait(); // 空了就等待
        item = buffer[--count];
        notFull.signal();    // 唤醒生产者
        return item;
    }
}
```

**对比信号量版本**:
- 不需要 mutex（管程自动互斥）
- 不需要手动维护 full/empty 值（用条件变量）
- 代码更清晰，不易出错

### 4.2 读者-写者问题

```c
Monitor ReaderWriter {
    int readerCount = 0;
    boolean writing = false;
    condition okToRead, okToWrite;
    
    public entry StartRead() {
        while (writing)  // Mesa 语义用 while，Hoare 用 if
            okToRead.wait();
        readerCount++;
    }
    
    public entry EndRead() {
        readerCount--;
        if (readerCount == 0)
            okToWrite.signal();
    }
    
    public entry StartWrite() {
        while (writing || readerCount > 0)
            okToWrite.wait();
        writing = true;
    }
    
    public entry EndWrite() {
        writing = false;
        okToWrite.signal();   // 优先写者
        okToRead.signal();    // 或广播 okToRead
    }
}
```

## 五、408 真题考点总结

### 5.1 选择题高频点

| 考点 | 常见陷阱 | 正确理解 |
|------|---------|---------|
| Signal 语义 | 以为会累积 | **丢失型**，无等待者时无效 |
| 互斥保证 | 需要额外加锁 | 编译器**自动保证**互斥 |
| Wait 释放锁 | 阻塞但持有锁 | **必须释放**，否则死锁 |
| 条件变量 ≠ 整型变量 | 当作计数器 | 只是阻塞队列的抽象 |
| Mesa vs Hoare | 被唤醒立即执行 | Mesa 还要重新竞争 |

### 5.2 大题常考模式

1. **给出信号量解法，改写成管程** ⭐⭐⭐
   - 互斥信号量 → 管程自动提供
   - 同步信号量 → 条件变量
   
2. **判断管程代码正确性**
   - 检查 wait 后条件是否会再次不满足
   - 检查 signal 是否在正确时机调用
   
3. **设计管程解决新问题**
   - 先写伪代码框架
   - 明确共享变量、条件变量
   - 写出各操作的前置/后置条件

## 六、预测题

### 预测题 1: 概念辨析 ⭐⭐

**题目**: 下列关于管程的叙述中，正确的是（  ）

A. 管程中的条件变量可以像信号量一样进行 PV 操作  
B. 多次执行 signal 操作会使后续 wait 操作不阻塞  
C. 进程在管程内执行 wait 操作时会释放管程的互斥锁  
D. 管程需要程序员手动实现互斥，而信号量由系统保证互斥

> [!success]- 答案与解析
> 
> **答案**: C
> 
> **解析**:
> - A 错: 条件变量只有 wait/signal，语义与 PV 不同
> - B 错: **signal 丢失，不累积**！这是核心区别
> - C 对: wait 必须释放锁，否则无法让其他进程改变条件
> - D 错: 管程由编译器保证互斥，信号量需手动 PV

---

### 预测题 2: 代码分析 ⭐⭐⭐

**题目**: 某管程实现如下，用于解决生产者-消费者问题：

```c
Monitor Buffer {
    int buf[10];
    int count = 0;
    condition notEmpty;
    
    public entry Put(item) {
        buf[count++] = item;
        notEmpty.signal();
    }
    
    public entry Get() {
        if (count == 0)
            notEmpty.wait();
        return buf[--count];
    }
}
```

该实现存在的问题是（  ）

A. 缺少 notFull 条件变量，缓冲区满时会越界  
B. signal 应在 wait 之前调用  
C. count 变量没有用信号量保护  
D. 应该用 while 替换 if

> [!success]- 答案与解析
> 
> **答案**: A
> 
> **解析**:
> - A 对: Put 没有检查 count == 10 的情况，会数组越界
> - B 错: signal 在 Put 中，wait 在 Get 中，不存在顺序问题
> - C 错: 管程自动互斥，count 已被保护
> - D 错: Hoare 语义下 if 够用；Mesa 语义才需要 while

### 预测题 3: 综合设计 ⭐⭐⭐

**题目**: 某系统有一个共享打印机，要求：
1. 每次只能有一个进程使用打印机
2. 进程可以"预约"打印机，预约成功后排队等待
3. 当前使用者结束后，按预约顺序分配给下一个进程

请用管程实现打印机管理，写出伪代码。

> [!example]- 参考答案
> 
> ```c
> Monitor PrinterManager {
>     boolean busy = false;        // 打印机是否在用
>     int waiting = 0;             // 预约排队数
>     condition printerFree;       // 等待打印机空闲
>     
>     public entry Request() {
>         if (busy) {
>             waiting++;
>             printerFree.wait();  // 排队等待
>             waiting--;
>         }
>         busy = true;             // 获得打印机
>     }
>     
>     public entry Release() {
>         busy = false;
>         if (waiting > 0)
>             printerFree.signal(); // 唤醒下一个
>     }
> }
> ```
> 
> **评分要点**:
> 1. busy 变量正确表示状态 (2分)
> 2. waiting 计数或条件队列管理 (2分)
> 3. Request 中正确 wait (2分)
> 4. Release 中正确 signal (2分)
> 5. 互斥性正确（管程自动提供）(2分)

### 预测题 4: Signal 语义深挖 ⭐⭐⭐

**题目**: 考虑以下代码片段（假设 Hoare 语义）：

```c
Monitor M {
    condition x;
    int count = 0;
    
    public entry P1() {
        x.signal();
        count++;
        print(count);
    }
    
    public entry P2() {
        x.wait();
        count++;
        print(count);
    }
}
```

若执行序列为: P1 → P2 → P1，输出结果是（  ）

A. 1 1 2  
B. 1 2 3  
C. 1 2  
D. 无输出（死锁）

> [!success]- 答案与解析
> 
> **答案**: B
> 
> **解析**:
> 1. **P1 第一次执行**:
>    - x.signal() **丢失**（无等待者）
>    - count = 1, 输出 1
>    
> 2. **P2 执行**:
>    - x.wait() **阻塞**（之前的 signal 已丢失）
>    - 暂停在这里
>    
> 3. **P1 第二次执行**:
>    - x.signal() 唤醒 P2
>    - Hoare 语义: P1 阻塞，P2 立即执行
>    - P2: count = 2, 输出 2
>    - P2 结束，P1 恢复执行
>    - P1: count = 3, 输出 3
> 
> 最终输出: **1 2 3**
> 
> **易错点**: 忘记第一次 signal 会丢失！

### 预测题 5: 对比题 ⭐⭐

**题目**: 将以下信号量解法改写为管程实现（哲学家就餐问题简化版）：

```c
semaphore chopstick[5] = {1, 1, 1, 1, 1};  // 5根筷子
semaphore mutex = 1;  // 保护取筷子动作

void philosopher(int i) {
    while (true) {
        think();
        P(mutex);
        P(chopstick[i]);
        P(chopstick[(i+1)%5]);
        V(mutex);
        eat();
        V(chopstick[i]);
        V(chopstick[(i+1)%5]);
    }
}
```

> [!example]- 参考答案
> 
> ```c
> Monitor DiningPhilosophers {
>     boolean chopstick[5] = {true, true, true, true, true};
>     condition self[5];  // 每个哲学家一个条件变量
>     
>     public entry PickUp(int i) {
>         // 等待两根筷子都可用
>         while (!chopstick[i] || !chopstick[(i+1)%5])
>             self[i].wait();
>         
>         // 拿起筷子
>         chopstick[i] = false;
>         chopstick[(i+1)%5] = false;
>     }
>     
>     public entry PutDown(int i) {
>         // 放下筷子
>         chopstick[i] = true;
>         chopstick[(i+1)%5] = true;
>         
>         // 唤醒可能等待的邻居
>         self[(i+4)%5].signal();  // 左邻居
>         self[(i+1)%5].signal();  // 右邻居
>     }
> }
> ```
> 
> **改写要点**:
> 1. mutex 不需要了（管程自动互斥）
> 2. chopstick 从信号量改为布尔数组
> 3. 用条件变量实现"等待两根都可用"
> 4. PutDown 时需要唤醒邻居
