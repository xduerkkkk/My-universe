
时间片轮转对于长短作业时间片都一样
先来先服务有利于长作业。长作业=CPU 繁忙型=计算类
最短作业优先适合 IO 繁忙型，为什么？
- **CPU 繁忙型（长作业）：** 一旦拿到 CPU，就恨不得连续计算 100 毫秒，中间绝不主动放弃 CPU。
    
- **I/O 繁忙型（短作业）：** 拿到 CPU 后，往往只需要花 1 毫秒打个日志或者发出一个网络请求，紧接着就会因为**等待 I/O** 而主动进入阻塞状态。因此，它在 CPU 眼里展现出来的“单次作业长度”**极短**

如果采用 **最短作业优先（SJF）**，调度器一算，I/O 繁忙型作业只需要 1 毫秒，CPU 繁忙型要 100 毫秒。调度器会毫不犹豫地把 CPU 优先塞给 I/O 繁忙型。

1. I/O 作业在 1 毫秒内闪电般用完 CPU。
    
2. 它立刻转去向磁盘或网络发起 I/O 请求（这就把 I/O 设备调动起来干活了）。
    
3. 在 I/O 设备自己慢吞吞读写的同时，CPU 可以回过头来死磕那个 100 毫秒的 CPU 繁忙型作业。
    

**结果：** CPU 和 I/O 设备**同时在满载运转（高度并行）**，系统的吞吐量和资源利用率达到了最高。

### 1. 高响应比优先（HRRN, Highest Response Ratio Next）

这是为了解决 SJF 的致命缺点——**“长作业饥饿（饿死）”**而诞生的。它在每次调度时，会计算所有就绪进程的**响应比 $R$**：

$$R = \frac{W + S}{S} = 1 + \frac{W}{S}$$

- 其中 $W$ 为**等待时间**（Waiting Time），$S$ 为**服务时间/预计运行时间**（Service Time）。
    
- **它偏爱谁？** 它是**端水大师**。
    
    - 当大家等待时间 $W$ 都差不多时，服务时间 $S$ 越短（短作业），响应比越高，**优先运行（照顾了短作业）**。
        
    - 如果一个长作业（$S$ 很大）等了足够长的时间，$W$ 变得极其巨大，它的响应比也会爆棚，**绝不至于被饿死（照顾了长作业）**。
        

### 2. 多级反馈队列（MLFQ, Multilevel Feedback Queue）

这是现代操作系统（如 Windows、Linux 的部分衍生实现）**在现实中真正使用**的算法，也是公认最完美的算法。

- **机制：** 设置多个队列，优先级从高到低。队列优先级越高，分配的时间片反而越短。
    
    1. 新来的进程，一律进入第一级最高优先级队列。
        
    2. 如果它在时间片内**没运行完**（说明是 CPU 繁忙型），就会被无情降级到下一级队列。
        
    3. 如果它运行到一半**因为 I/O 阻塞了**，醒来后依然留在高优先级队列甚至得到提升。
        
- **它偏爱谁？** **它动态地偏爱短作业和 I/O 繁忙型作业。** * 终端交互软件（如鼠标点击、键盘输入，属于 I/O 繁忙）永远停留在最高优先级队列，响应速度极快。
    
    - 后台挖矿或视频渲染程序（CPU 繁忙型）运行几轮后就会沉淀到最底层的低优先级队列，不耽误别人。
