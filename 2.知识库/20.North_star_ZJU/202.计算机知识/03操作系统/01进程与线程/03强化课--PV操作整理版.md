> - 源文件未修改。本笔记中的伪代码以考研操作系统常用的 P/V 语义为准：P(S) 申请资源或等待事件，V(S) 归还资源或宣布事件发生。

## 一、先建立统一的解题框架

### 1. P/V 到底在表达什么

一个信号量通常承担两类职责：

| 类型 | 初值 | P 的含义 | V 的含义 |
| --- | ---: | --- | --- |
| 互斥信号量 | 1 | 申请进入临界区 | 离开临界区 |
| 资源信号量 | 资源数 | 申请一个资源 | 归还一个资源 |
| 同步信号量 | 通常为 0 | 等待某个前置事件 | 宣布前置事件已完成 |

判断方法：

- 能说成“有几个”的，通常是资源计数，如空位、产品、碗、名额。
- 能说成“某件事做完以后才能继续”的，通常是同步事件。
- 能说成“这段共享状态一次只能由一个进程检查或修改”的，通常需要互斥。

> [!warning] 不要把普通变量和信号量混为一谈
> - waiting、count、currentFilm 这类普通变量负责记录复杂状态。
> - mutex 负责保护这些普通变量的检查与修改。
> - 资源信号量负责阻塞与唤醒，不能简单用一个未保护的整数变量代替。

### 2. 六步法：从中文动作推到 P/V

1. **找进程**：谁在并发执行？每类角色是一个进程还是多个同类进程？
2. **拆原子步骤**：用“加工 A”“把 A 放入箱中”这种粒度描述，不把多个有先后关系的动作揉成一句。
3. **画先后关系**：凡是 B 必须等 A 完成，就在 B 前放 P，在 A 后补对应的 V。
4. **找共享资源和共享变量**：资源用计数信号量；共享变量的读—改—写用 mutex 保护。
5. **写定义与初值**：名称、初值、含义必须一一对应。
6. **做极端调度检查**：让 CPU 长时间只运行某一个进程，检查是否越界、漏唤醒、重复进入或死锁。

### 3. 连续两个 P 的检查法

看到连续的 P，逐个问：

- 第一个 P 成功、第二个 P 阻塞时，进程手里扣住了什么？
- 能让第二个信号量增加的进程，是否需要先得到第一个进程扣住的资源？
- 是否出现“拿着 mutex 等资源，而资源释放者又要拿 mutex”的闭环？

生产者—消费者中通常应当：

~~~c
P(resource);   // 先等空位、产品等资源
P(mutex);      // 再进入很短的临界区
操作缓冲区;
V(mutex);
V(otherResource);
~~~

反过来先 P(mutex) 再等资源，容易出现“抱着锁睡觉”。

### 4. “尽可能少的信号量”如何判断

- **一次性的严格顺序**：若 A 完成后 B 才能执行，而且 A 不会再次回来抢资源，同步本身可能已经保证互斥。
- **循环中的容量 1 缓冲区**：仍需同时约束“不能空取”和“不能满放”，通常需要 empty=1、full=0 两个方向的信号量。
- **一个物理资源只有一个进程会使用**：不需要为它额外设置互斥信号量。例如只有丙使用水桶时，水桶无需再加锁。
- **同一事件要唤醒多个进程**：可对同一计数信号量执行多次 V，不一定要为每条边单独定义信号量。
- **容量大于 1 不等于必然需要 empty/full**：只有题目确实在维护“可放数量”和“可取数量”时才需要。先看逻辑，再套模型。

### 母题 A：互斥与原子性

> [!tip] 识别关键词

#### 题 1：2023 统考——用 swap 实现临界区互斥

> [!example]- 原题截图
> ![[_attachments/image/03强化课--PV操作-1780298756457.jpeg]]

##### 识别题型

这不是普通软件变量互斥，而是考查：

1. 忙等待进入区的循环条件；
2. swap 指令必须具有原子性；
3. 退出临界区时应把锁恢复为什么值。

##### 正确修改

原伪代码中的两个错误是：

- if 应改为 while，否则一次交换失败后仍会直接进入临界区。
- lock = TRUE 应改为 lock = FALSE，否则退出后锁仍处于占用状态。

~~~c
bool lock = FALSE;          // 线程间共享

process Pi {
    bool key = TRUE;        // 每个线程私有
    while (key == TRUE)
        swap(key, lock);    // 必须是原子指令

    临界区;

    lock = FALSE;
}
~~~

##### 为什么成立

- 第一个执行 swap 的线程把 lock 从 FALSE 换成 TRUE，同时自己的 key 得到旧值 FALSE，因此退出 while 并进入临界区。
- 后来的线程交换后 key 仍为 TRUE，只能继续忙等待。
- 离开时把 lock 置为 FALSE，下一位竞争者才可能在某次 swap 后得到 FALSE。

##### newSwap 函数为什么不能替代 swap 指令

普通函数由三条可分割的读写语句组成：

~~~c
 temp = *a;
*a = *b;
*b = temp;
~~~

线程可能在任意两条语句之间被切换。两个线程交错执行时，可能都依据旧的 lock 值判断自己获得了锁。硬件 swap 指令的关键不是“交换结果相同”，而是**整个交换不可被打断**。

> [!danger] 易错点
> 原子指令和实现相同功能的普通函数不是一回事。互斥依赖的是不可分割性，不只是最终值。

### 母题 B：生产者—消费者与固定阶段同步

> [!tip] 识别关键词
> 有先后阶段、事件传递、循环生产/消费或多阶段流水线。先画箭头，再决定是单向同步还是双向资源约束。

#### 题 2：容量为 1 时，为什么单次接力可用 1 个信号量，而循环生产必须用 2 个

##### 情形 A：一次性严格接力

若 P₁ 只执行一次 C₁，P₂ 必须在 C₁ 后执行 C₂，且 P₁ 结束后不会再次向缓冲区放入数据：

~~~c
semaphore ready = 0;

P1 {
    C1;
    V(ready);
}

P2 {
    P(ready);
    C2;
}
~~~

此时 ready 同时表达“C₁ 已完成”和“缓冲区已有数据”。由于 P₁ 不会回头放第二次，所以不需要 empty 去拦住 P₁。

##### 情形 B：两个进程无限循环

若 P₁ 不断放入、P₂ 不断取出，单个 ready 只能防止 P₂ 空取，不能防止 P₁ 在缓冲区已满时再次放入。

~~~c
semaphore empty = 1;
semaphore full  = 0;

P1 {
    while (TRUE) {
        P(empty);
        放入一个产品;
        V(full);
    }
}

P2 {
    while (TRUE) {
        P(full);
        取出一个产品;
        V(empty);
    }
}
~~~

##### 极端调度验证

假设 CPU 连续只运行 P₁：

- 第一轮 P(empty) 成功并放入产品；
- empty 变为 0；
- 第二轮 P₁ 会被 P(empty) 拦住，不能覆盖尚未取出的产品。

> [!summary] 结论
> 容量为 1 只说明状态是空/满二值，并不自动意味着一个信号量足够。还要看生产者是否会循环回来，以及是否需要双向约束。

#### 题 5：P₁、P₂、P₃ 按顺序输入 a、b、c，并由 P₁ 打印 x、y、z

> [!example]- 原题截图
> ![[_attachments/image/03强化课--PV操作-1780046584010.jpeg]]

##### 依赖关系

- 输入顺序：P₁ 输入 a → P₂ 输入 b → P₃ 输入 c。
- x=a+b：P₁ 要等 b 已输入。
- y=a×b：P₂ 输入 b 后即可计算。
- z=y+c−a：P₃ 要同时具备 y 和 c。
- 打印：P₁ 必须等 z 完成，才能打印 x、y、z。

严格的输入顺序已经让三个进程不会同时使用输入设备，因此不必再为输入设备单独设置 mutex。

##### 尽可能少的 3 个信号量方案

~~~c
semaphore aReady = 0;
semaphore bAndYReady = 0;
semaphore zReady = 0;

P1 {
    输入 a;
    V(aReady);              // 允许 P2 输入 b

    P(bAndYReady);          // 等 b 已输入、y 已算出
    x = a + b;

    P(zReady);
    打印 x, y, z;
}

P2 {
    P(aReady);
    输入 b;
    y = a * b;

    V(bAndYReady);          // 唤醒 P1
    V(bAndYReady);          // 唤醒 P3
}

P3 {
    P(bAndYReady);
    输入 c;
    z = y + c - a;
    V(zReady);
}
~~~

##### 为什么 P₂ 要 V 两次

P₁ 和 P₃ 都要等待“b 已输入且 y 已算好”这一事件。计数信号量的一次 V 只提供一个通行令牌，因此必须 V 两次，才能让两个等待者各通过一次。

> [!tip] 更易写但信号量更多的版本
> 可以把 bReadyForP1 和 yReadyForP3 拆成两个同步信号量，各 V 一次。考试若要求“尽可能少”，再合并为上面的计数信号量并 V 两次。

#### 题 6：2025 统考——挖坑、放苗填土、浇水

> [!example]- 原题截图
> ![[_attachments/image/03强化课--PV操作-1780212630462.jpeg]]

##### 题目约束拆解

- 甲：使用铁锹挖坑。
- 乙：取一个已挖好的坑，放苗，并使用铁锹填土。
- 丙：等待填土完成后，用水桶浇水。
- 未填好的树坑最多 3 个。
- 铁锹由甲、乙竞争；水桶只有丙使用，不发生竞争。

##### 最少信号量

~~~c
semaphore pitSlot = 3; // 还能再挖几个未完成的坑
semaphore hole = 0;    // 已挖好、等待乙处理的坑
semaphore planted = 0; // 已填土、等待浇水的树苗
semaphore shovel = 1;  // 铁锹互斥
~~~

##### 进程代码

~~~c
甲 {
    while (TRUE) {
        P(pitSlot);
        P(shovel);
        挖一个树坑;
        V(shovel);
        V(hole);
    }
}

乙 {
    while (TRUE) {
        P(hole);
        放入树苗;

        P(shovel);
        填土;
        V(shovel);

        V(pitSlot);     // 填完后，这个“未完成树坑”消失
        V(planted);
    }
}

丙 {
    while (TRUE) {
        P(planted);
        用水桶浇水;
    }
}
~~~

##### 为什么是 4 个而不是 5 个

- pitSlot 管“最多 3 个未完成树坑”；
- hole 管甲→乙；
- planted 管乙→丙；
- shovel 管甲与乙的互斥。

水桶虽是物理资源，但只有丙这一类单进程使用，没有并发竞争，所以不必设 bucket=1。

##### 并发性细节

乙“放树苗”时并未使用铁锹，因此不应过早 P(shovel)。让甲挖坑和乙放苗并行，只有挖坑、填土两个真正使用铁锹的阶段互斥。

### 母题 C：有界缓冲区与成套资源

> [!tip] 识别关键词
> 缓冲区容量有限，消费者必须同时取得一组不同类型的资源。除了 empty/full，还要检查“某一种资源占满”的状态。

#### 题 4：自行车生产线——一个车架、两个车轮才能组装

> [!example]- 原题截图
> ![[_attachments/image/03强化课--PV操作-1780056063833.jpeg]]

> [!note] 源笔记提醒
> 原方案“未考虑出死锁情况”。本题的关键不是只数空位，而是防止箱子被单一零件塞满。

##### 朴素方案为什么会死锁

若只设置 empty=N、frame=0、wheel=0：

- 箱子可能被 N 个车架占满；
- 工人 3 拿不到两个车轮，无法组装并释放空位；
- 工人 2 又因为 empty=0 无法放入车轮；
- 三方永久等待。

因此必须限制不同零件在箱中的最大积压量：

- 车架最多 N−2 个，保证满箱时至少留出两个车轮的位置；
- 车轮最多 N−1 个，保证满箱时至少有一个车架。

##### 信号量定义

~~~c
semaphore empty = N;          // 箱中空位置
semaphore frame = 0;          // 已有车架数
semaphore wheel = 0;          // 已有车轮数
semaphore frameQuota = N - 2; // 允许积压的车架额度
semaphore wheelQuota = N - 1; // 允许积压的车轮额度
semaphore boxMutex = 1;       // 保护实际放入、取出箱子的操作
~~~

##### 无死锁实现

~~~c
Worker1 {
    while (TRUE) {
        加工一个车架;

        P(frameQuota);        // 先取得“还能积压车架”的额度
        P(empty);
        P(boxMutex);
        把一个车架放入箱中;
        V(boxMutex);
        V(frame);
    }
}

Worker2 {
    while (TRUE) {
        加工一个车轮;

        P(wheelQuota);
        P(empty);
        P(boxMutex);
        把一个车轮放入箱中;
        V(boxMutex);
        V(wheel);
    }
}

Worker3 {
    while (TRUE) {
        P(frame);
        P(wheel);
        P(wheel);

        P(boxMutex);
        从箱中取一个车架和两个车轮;
        V(boxMutex);

        V(empty);
        V(empty);
        V(empty);
        V(frameQuota);
        V(wheelQuota);
        V(wheelQuota);

        组装一台自行车;
    }
}
~~~

##### 为什么 quota 要放在 empty 前面

如果生产者先占住一个 empty，再发现对应 quota 已用完而阻塞，它会“拿着空位额度睡觉”，可能妨碍真正缺少的另一类零件进入。先申请种类额度，再申请公共空位，资源层次更清楚。

##### 进度性证明

- 若箱子未满，至少还有 empty，可由缺少的零件生产者继续放入。
- 若箱子已满，由 frame≤N−2、wheel≤N−1 可推出箱中至少有 1 个车架和 2 个车轮，工人 3 一定能取得完整套件并释放 3 个空位。

### 母题 D：同类共享、异类互斥

> [!tip] 识别关键词
> 同方向或同类型可以并发，异方向或异类型必须排他。常用“第一位进入者加锁、最后一位离开者解锁”。

#### 题 3：单车道桥的交通管理

> [!example]- 原题截图
> ![[_attachments/image/03强化课--PV操作-1780055301195.jpeg]]

##### 第 1 问：桥上任何时刻只能有一辆车

一座桥就是一个互斥资源。

~~~c
semaphore bridge = 1;

NorthCar {
    P(bridge);
    由南向北过桥;
    V(bridge);
}

SouthCar {
    P(bridge);
    由北向南过桥;
    V(bridge);
}
~~~

##### 第 2 问：同方向可多辆并行，反方向不能相遇

这是“同类共享、异类互斥”模型。每个方向使用“第一辆车锁桥，最后一辆车放桥”。

~~~c
semaphore bridge = 1;
semaphore northMutex = 1;
semaphore southMutex = 1;
int northCount = 0;
int southCount = 0;

NorthCar {
    P(northMutex);
    northCount++;
    if (northCount == 1)
        P(bridge);          // 第一辆北行车锁住整座桥
    V(northMutex);

    向北过桥;

    P(northMutex);
    northCount--;
    if (northCount == 0)
        V(bridge);          // 最后一辆北行车放桥
    V(northMutex);
}

SouthCar {
    P(southMutex);
    southCount++;
    if (southCount == 1)
        P(bridge);
    V(southMutex);

    向南过桥;

    P(southMutex);
    southCount--;
    if (southCount == 0)
        V(bridge);
    V(southMutex);
}
~~~

##### 为什么不能用一个公共计数 mutex 包住 P(bridge)

若北行首车拿着公共 mutex 等 bridge，而桥上的南行末车必须先拿同一个 mutex 才能把 bridge 释放，就会形成死锁。两个方向分别保护自己的计数，可避免释放桥的一方被对方的计数锁堵住。

> [!warning] 公平性边界
> 上述答案保证安全和无死锁，但若北行车辆持续到达，南行车辆可能长期等待。若题目额外要求公平或按到达顺序，需要增加 turnstile 或显式排队机制。

#### 题 10：录像厅——同片观众并发、异片排队、换片时批量进入

> [!example]- 原题截图
> ![[_attachments/image/03强化课--PV操作-1780215477689.jpeg]]

##### 为什么普通“读者—写者第一人加锁、最后一人解锁”不够

它只能保证：

- 同一类观众可同时观看；
- 不同录像片不能同时放映。

但原题还要求：

- 等待其他录像片的观众按全局到达顺序排队；
- 当前录像结束后，由最早等待者选择下一种录像片；
- 所有已经等待该片的观众可作为一批进入。

因此需要一个受 mutex 保护的显式 FIFO 队列，而不只是三个简单计数器。

##### 共享状态与信号量

~~~c
int current = 0;              // 0 表示空厅；1、2、3 表示当前录像片
int inside = 0;               // 当前厅内观众数
int waiting[4] = {0, 0, 0, 0};
Queue Q;                      // 按到达顺序记录等待观众选择的片号

semaphore mutex = 1;
semaphore gate[4] = {0, 0, 0, 0};
~~~

以下伪代码假设 gate[k] 的阻塞队列对同片观众按到达顺序唤醒；若系统不保证 FIFO，可把 gate[k] 换成每位观众的私有信号量。

##### 观众进程

~~~c
Viewer(type) {
    P(mutex);

    if (current == 0) {
        current = type;
        inside = 1;
        V(mutex);
    }
    else if (current == type) {
        inside++;
        V(mutex);
    }
    else {
        Q.push(type);
        waiting[type]++;
        V(mutex);

        P(gate[type]);       // 等到该片被选为下一场
    }

    观看录像 type;

    P(mutex);
    inside--;

    if (inside == 0) {
        if (Q.empty()) {
            current = 0;
        } else {
            int next = Q.front();
            int k = 0;

            按原相对顺序扫描 Q;
            删除 Q 中所有片号为 next 的等待项;
            k = 被删除的数量;

            waiting[next] -= k;
            current = next;
            inside = k;      // 被唤醒者已预先计入厅内人数

            repeat k times
                V(gate[next]);
        }
    }

    V(mutex);
}
~~~

##### 运行逻辑

1. 空厅时，第一个到达者直接决定播放片号。
2. 新到观众若选择当前片，立即进入，inside++。
3. 选择其他片的观众进入全局 FIFO 队列并阻塞。
4. 最后一名当前观众离开时，查看 Q 的队首；队首片号决定下一场。
5. 将 Q 中所有已等待该片的观众按原先相对顺序成批唤醒；等待其他片的观众仍保留在队列中。

##### 正确性检查

- current 同一时刻只有一个值，所以不会同时播放两种片。
- current==type 的新观众不排队，满足“同片立即进入”。
- 下一片由 Q.front 决定，满足不同片请求之间的到达顺序。
- inside 在唤醒一批观众前一次性设为 k，避免某个被唤醒进程尚未获得 CPU 时系统误判录像厅又空了。

> [!warning] 与普通读者—写者的差别
> 普通第一人/最后一人模型可能让当前片的新观众不断插入，从而使其他片长期饥饿。本题虽允许同片新观众立即进入，因此理论上仍可能长期不换片；这是题目规则本身带来的结果。FIFO 约束只在真正换片时决定下一片。

### 母题 E：多资源申请与死锁

> [!tip] 识别关键词
> 一个进程要拿两根筷子、多个工具或多个资源后才能开始。重点检查是否出现环路等待。

#### 题 7：哲学家进餐与 2019 统考“筷子 + 碗”

> [!example]- 原题截图
> ![[_attachments/image/03强化课--PV操作-1780296901245.jpeg]]

##### 7.1 三种通用防死锁方法

###### 方法一：最多允许 n−1 人同时尝试取资源

~~~c
semaphore room = n - 1;
semaphore fork[n] = {1, 1, ..., 1};

Philosopher(i) {
    while (TRUE) {
        思考;
        P(room);
        P(fork[i]);
        P(fork[(i + 1) % n]);
        进餐;
        V(fork[i]);
        V(fork[(i + 1) % n]);
        V(room);
    }
}
~~~

最多只有 n−1 人进入取筷子阶段，无法形成 n 人首尾相接的完整环路等待。这里打破的是**循环等待条件**。

###### 方法二：规定不对称的取筷顺序

例如奇数号先左后右，偶数号先右后左；更常见的简化写法是只让一名哲学家反向取筷。核心是让所有人的资源申请顺序不再构成同向闭环。

###### 方法三：用全局取筷锁把“拿两根筷子”包成一个申请阶段

~~~c
semaphore pickMutex = 1;
semaphore fork[n] = {1, 1, ..., 1};

Philosopher(i) {
    while (TRUE) {
        思考;

        P(pickMutex);
        P(fork[i]);
        P(fork[(i + 1) % n]);
        V(pickMutex);

        进餐;

        V(fork[i]);
        V(fork[(i + 1) % n]);
    }
}
~~~

pickMutex 只限制“取筷子阶段”，不包住进餐阶段，所以取得互不冲突筷子的哲学家仍可同时进餐。若某人在 pickMutex 内等待第二根筷子，正在进餐者释放筷子时不需要 pickMutex，因此不会形成该锁上的死锁。

##### 7.2 加入 m 个碗：推荐的高并发答案

在 room=n−1 的方案上加入 bowl=m：

~~~c
semaphore room = n - 1;
semaphore bowl = m;
semaphore fork[n] = {1, 1, ..., 1};

Philosopher(i) {
    while (TRUE) {
        思考;

        P(room);                 // 防止完整环路等待
        P(bowl);                 // 申请一个碗
        P(fork[i]);
        P(fork[(i + 1) % n]);

        进餐;

        V(fork[i]);
        V(fork[(i + 1) % n]);
        V(bowl);
        V(room);
    }
}
~~~

###### 为什么满足“尽可能多同时就餐”

- 碗用计数信号量管理，不把整个进餐过程串行化。
- 筷子仍逐根独立管理，不相邻的哲学家可以同时进餐。
- room=n−1 不会把理论并发上限压到 1；圆桌上本来最多也只有 floor(n/2) 名哲学家能同时占有两根互不冲突的筷子。
- 实际并发上限为 min(m, floor(n/2))。

> [!warning] 边界
> 防死锁不等于防饥饿。若信号量唤醒次序不公平，某位哲学家仍可能长期拿不到资源；题目未要求公平时通常不额外处理。

### 母题 F：条件撤退与有限等待区

> [!tip] 识别关键词
> 满了就走、无顾客就睡、有限座位、服务窗口。不能只用会阻塞的 P 来代替“满了就离开”的条件分支。

#### 题 8：2011 统考——银行窗口与 10 个等待座位

> [!example]- 原题截图
> ![[_attachments/image/03强化课--PV操作-1780218380265.jpeg]]

##### 与理发师问题的对应关系

- 营业员相当于理发师；
- 顾客座位相当于等候椅；
- customers 统计已进入等待区、尚未叫号的顾客；
- called 表示营业员叫出了一位顾客；
- 取号机是顾客之间额外竞争的互斥资源。

##### 考试级抽象解法

~~~c
int waiting = 0;
semaphore mutex = 1;       // 保护 waiting
semaphore ticket = 1;      // 取号机互斥
semaphore customers = 0;   // 等待叫号的顾客数
semaphore called = 0;      // 已叫出的服务名额

Customer(i) {
    P(mutex);
    if (waiting == 10) {
        V(mutex);
        离开银行;
    } else {
        waiting++;
        V(mutex);

        P(ticket);
        从取号机获取号码;
        V(ticket);

        V(customers);
        P(called);
        获取服务;
    }
}

Clerk {
    while (TRUE) {
        P(customers);

        P(mutex);
        waiting--;          // 被叫顾客离开等待座位
        V(mutex);

        叫号;
        V(called);
        为该顾客服务;
    }
}
~~~

##### 为什么不能简单写 P(emptySeat)

若题意是“无座就离开”，普通阻塞式 P(emptySeat) 会让无座顾客在外面等待，而不是执行离开分支。因此需要 waiting + mutex + if/else，或者题目明确允许的非阻塞 tryP。

##### 严格按票号顺序时怎么办

上面的 called 是考试中常见的抽象，默认等待队列按取号顺序唤醒。若要求实现级严格 FIFO，应再维护一个受 mutex 保护的票号队列 Q，并为每位顾客设置私有信号量 call[i]：营业员取 Q 的队首并只 V 对应的 call[i]。

#### 题 9：睡眠理发师

> [!example]- 原题截图
> ![[_attachments/image/03强化课--PV操作-1780211354579.jpeg]]

##### 核心状态

- waiting：正在 n 把等候椅上坐着的顾客数，不包含正在理发椅上的顾客。
- mutex：保护 waiting 的检查与修改。
- customers：等待理发的顾客数；为 0 时理发师睡眠。
- barbers：理发师叫出一个顾客的信号。

##### 标准实现

~~~c
int waiting = 0;
semaphore mutex = 1;
semaphore customers = 0;
semaphore barbers = 0;

Barber {
    while (TRUE) {
        P(customers);       // 没顾客就在这里睡

        P(mutex);
        waiting--;          // 叫走一位，空出一把等候椅
        V(barbers);
        V(mutex);

        理发;
    }
}

Customer {
    P(mutex);
    if (waiting < n) {
        waiting++;
        V(customers);
        V(mutex);

        P(barbers);
        被理发;
    } else {
        V(mutex);           // 满座分支也必须开锁
        离开;
    }
}
~~~

##### 为什么理发师必须先 P(customers)，再 P(mutex)

错误顺序：

~~~c
P(mutex);
P(customers);
~~~

若此时没有顾客，理发师会拿着 mutex 睡眠。新顾客到来后需要 P(mutex) 才能检查座位，却永远拿不到；理发师又在等顾客，形成死锁。

##### 三个高频失分点

1. 满座离开分支忘记 V(mutex)。
2. 把理发这个耗时动作放在 mutex 内，导致所有新顾客连座位都无法检查。
3. waiting 在顾客坐下时增加，在被理发师叫走、离开等候椅时减少，而不是理发结束才减少。

## 四、原笔记中三条关键批注的统一解释

### 1. “未考虑出死锁情况”

看到一个消费者需要多种资源时，不能只检查每个资源总量，还要检查缓冲区是否可能被某一种资源占满。自行车题要用 frameQuota、wheelQuota 保证满箱状态一定包含完整套件。

### 2. “P₂ 要两次 V”

一个同步事件若有两个独立等待者，一次 V 只够放行一个。可以使用同一计数信号量 V 两次，也可以拆成两个信号量各 V 一次。

### 3. “搞复杂了”

精简信号量不是机械删除，而是识别冗余约束：

- 严格阶段顺序已经保证设备互斥，就不再加设备 mutex；
- 只有一个进程使用水桶，就不加 bucket；
- 但循环缓冲区的“空”和“满”是两个方向的约束，不能因为容量为 1 就删成一个。
