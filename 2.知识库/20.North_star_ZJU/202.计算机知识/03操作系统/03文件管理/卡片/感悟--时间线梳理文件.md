# Inode 版
## 阶段 0：风平浪静的静态世界（未进行任何文件操作）

在你的电脑还没开机，或者还没动这个文件之前，所有东西都是**静态地刻在磁盘上**的。

### 💾 此时的【外存（磁盘）】长这样：

磁盘被格式化成了不同的区域：

1. **Inode 区**：存放着成千上万个**磁盘 Inode（传统的静态 FCB）**。每个 Inode 有个固定的编号。里面只记硬核属性（大小、权限、物理块号），**绝对不存文件名**！
    
2. **数据区**：存放真正的内容。
    
    - **普通文件的数据块**：存你的文章、视频等。
        
    - **目录文件的数据块**：**重点来了！目录也是一个文件（叫目录文件）。** 它的内容是一张表，里面是一行行的**目录项（文件名, Inode 号）**。
        

### 🧠 此时的【内存】长这样：

- 只有操作系统的内核基础代码，关于你要操作的那个文件，内存里**一片空白，什么都没有**。
    

## 阶段 1：创建一个新文件（调用 `create`）

你在桌面右键新建了一个 `test.txt`。

Plaintext

```
用户：帮我建个文件叫 test.txt
系统：好叻，在外存给你上个户口。
```

### 💾 【外存（磁盘）】发生的动态变化：

1. **抢占 Inode**：系统在磁盘的 Inode 区找了一个空闲的 Inode（假设是 88 号），把默认权限、大小=0 写进去。
    
2. **登记户口（修改目录文件）**：系统跑到当前文件夹的**目录文件**里，在末尾追加一行记录：`("test.txt", 88号)`。
    
3. **改位图**：把磁盘空闲 Inode 位图对应的位置改成“已占用”。
    

### 🧠 【内存】的状态：

- **依旧什么都没有留存**。创建完后，CPU 释放临时缓冲区，内存回归清白。此时文件只是在外存“挂了个名”。
    

## 阶段 2：打开文件（调用 `open`）

程序准备去读写这个文件，执行了 `int fd = open("test.txt")`。**这是内存和外存发生大碰撞的时刻！**

### 1. 寻路（外存 $\rightarrow$ 内存）

- 系统去磁盘读当前目录的**目录文件**，在里面一行行瞅，找到了 `test.txt`，拿到了它的 **88 号 Inode**。
    

### 2. 在【内存】中疯狂拉表（建立三层数据结构）

系统在内存里为你连建三样东西：

- **内存 Inode 表**：系统把磁盘上 88 号 Inode 的静态属性复制到内存，并强行给它塞入几个动态属性（引用计数 count=1，脏位 dirty=0，设备号）。
    
- **系统打开文件表**：在全局系统表里占个空位，里面写着：“当前指向内存 88 号 Inode，目前有 1 个进程在用它。”
    
- **进程打开文件表**：在你的进程内部的数组（文件描述符表）里找个空位（比如 `索引 3`），里面的指针指向刚才的系统表。
    
- **最终结果**：把这个 `索引 3` 作为 **`fd = 3`** 返回给你的 C 语言程序。
    

### 💾 【外存（磁盘）】的状态：

- 一动不动，毫无波澜。它只负责在开头被读了一下 Inode。
    

## 阶段 3：读写文件（调用 `read / write`）

程序执行 `write(fd, "hello", 5)`。

Plaintext

```
用户：拿着 fd=3，给我写入 "hello"！
系统：顺着 fd=3 查进程表 -> 查系统表 -> 找到内存 88号 Inode -> 知道了物理块号 -> 开始干活。
```

### 🧠 【内存】内部的极限拉扯：

1. **元数据修改**：内存 88 号 Inode 里的 `文件大小` 瞬间从 0 变成了 5B。系统顺手把内存 Inode 的 **`dirty bit（脏位）` 标记为 1**。
    
2. **数据修改**：系统在内存里开辟了一块叫 **Page Cache（页面缓冲区）** 的地方，把 `"hello"` 扔进去，并把这块内存数据也标记为“脏”。
    

### 💾 【外存（磁盘）】的状态：

- **依然没有变！** 为了性能，此时磁盘上文件大小还是 0，数据区也还没写。
    
- **什么时候写盘？** 操作系统后台的守护进程每隔 30 秒，或者看内存不够用了，才会把内存 Page Cache 里的 `"hello"` 和内存 Inode 的最新大小，**异步批量刷回磁盘**。
    

## 阶段 4：关闭文件（调用 `close`）

程序大喊一声：`close(fd)`。

Plaintext

```
用户：我用完了，关掉它。
系统：收到，断开内存连接。
```

### 🧠 【内存】的善后工作：

1. **删进程表**：把你进程表里的 `索引 3` 抹掉。
    
2. **减计数器**：系统打开文件表里的引用计数 `count` 减 1。
    
3. **回收内存 Inode**：如果 `count` 变成了 0，说明全系统没人用它了。系统看了一眼它的 `dirty bit`：
    
    - 如果是 `1`：说明最后一次刷盘后又改过，**强制最后一次 I/O，把最新属性写回磁盘 Inode**，然后把内存 Inode 销毁。
        
    - 如果是 `0`：说明内存和磁盘是一致的，**直接抹掉内存 Inode**，省下 I/O。
        

### 💾 【外存（磁盘）】的最终归宿：

- 所有的账目（文件大小、修改时间、最新数据）全部落盘，重新变回阶段 0 的静态大本营。
    

### 💡 终极位置速查表

如果以后再乱，掏出这张表对照：

| **术语名称**              | **它本质是什么？**                          | **它活在哪里？**                 |
| --------------------- | ------------------------------------ | -------------------------- |
| **磁盘 Inode / 传统 FCB** | 静态的文件身份证                             | **绝对在外存（磁盘 Inode 区）**      |
| **目录文件**              | 一个特殊文件，存 `(文件名, Inode号)` 键值对         | **实体在外存（数据区），只有读取时会进内存缓存** |
| **目录项**               | 目录文件里的一行记录                           | **实体在外存（数据区）**             |
| **内存 Inode**          | 磁盘 Inode 的内存镜像 + 动态管理属性（count、dirty） | **绝对在内存（内核索引节点表）**         |
| **打开文件表（系统/进程）**      | 操作系统为了追踪谁在读写文件而拉的临时表格                | **绝对在内存**                  |
| **文件描述符 (fd)**        | 进程打开文件表数组的下标（一个整数）                   | **绝对在内存（用户程序拿拿着玩）**        |
# 纯 FCB 版
我们同样用时间线，来看看纯 FCB 模型下外存和内存的动态流转：

## 阶段 0：静态世界（未进行任何文件操作）

### 💾 此时的【外存（磁盘）】长这样：

磁盘上只有两大阵营：**目录文件** 和 **普通数据块**。

- **没有独立的 Inode 区**。
    
- **目录文件的数据块**：它的内容就是一张大表。表里的每一行就是一个**完整的、胖胖的 FCB**（里面塞满了：文件名、物理起始块号、文件大小、创建时间、权限……）。
    
- > **概念合一**：在这里，**一个目录项 = 一个完整的 FCB**。
    

### 🧠 此时的【内存】长这样：

- 一片空白，毫无文件的痕迹。
    

## 阶段 1：创建一个新文件（调用 `create`）

Plaintext

```
用户：帮我建个文件叫 test.txt。
系统：好叻，我直接去当前目录文件里给你“塞一行”。
```

### 💾 【外存（磁盘）】发生的动态变化：

1. **抢占目录项**：系统读取当前文件夹的**目录文件**，在里面找一个空闲的行（槽位）。
    
2. **直接写入满额 FCB**：把 `[test.txt | 大小=0 | 权限=rw | 起始块号=None | 时间=... ]` 这一整坨数据，**直接写进目录文件的那个槽位里**。
    
3. **磁盘修改**：目录文件由于多了一行，其所在的磁盘块内容被更新。
    

### 🧠 【内存】的状态：

- 依然清白，创建完后临时缓冲区释放，内存不留痕迹。
    

## 阶段 2：打开文件（调用 `open`）

程序执行 `int fd = open("test.txt")`。

Plaintext

```
用户：我要读写 test.txt！
系统：我去目录文件里把这一整行 FCB 给你“抠”到内存里来！
```

### 1. 寻路与搬运（外存 $\rightarrow$ 内存）

- 系统去磁盘读目录文件，一行行比对文件名，找到了 `test.txt` 那一行。
    
- 系统把这一行**完整的 FCB 属性（除了文件名，或者包含文件名）全部复制到内存中**。
    

### 2. 在【内存】中拉表

- **系统打开文件表**：在全局表里占个空位。因为没有独立的 Inode 了，所以这一项里直接容纳了**刚才从磁盘复制过来的 FCB 副本**，并强行加上动态属性（引用计数 count=1，脏位 dirty=0）。我们通常叫它**内存活动 FCB（Active FCB）**。
    
- **进程打开文件表**：在进程数组里找个空位（如 `索引 3`），指针指向系统打开文件表里的那个活动 FCB。
    
- **最终结果**：返回 `fd = 3`。
    

## 阶段 3：读写文件（调用 `read / write`）

程序执行 `write(fd, "hello", 5)`。

### 🧠 【内存】内部的改变：

1. **修改内存 FCB**：系统查到 `fd = 3`，定位到系统表里的**内存活动 FCB**，把里面的 `文件大小` 字段从 0 改成 5B。同时，把这个内存活动 FCB 的 **`dirty bit` 标记为 1**。
    
2. **修改数据**：数据依然写进内存的 Page Cache（缓冲区），标记为脏。
    

### 💾 【外存（磁盘）】的状态：

- 磁盘上的目录文件里，`test.txt` 那一行的文件大小**依然是 0**。磁盘数据块也还没动，静静等待后台异步刷盘。
    

## 阶段 4：关闭文件（调用 `close`）

程序执行 `close(fd)`。

Plaintext

```
用户：我用完了，关掉它。
系统：断开连接，顺便把最新的 FCB 户口本送回磁盘的目录文件里。
```

### 🧠 【内存】的善后工作：

1. 删进程表项，系统表的 `count` 减 1。
    
2. 当 `count == 0` 时，系统检查该**内存活动 FCB** 的 `dirty bit`：
    
    - 如果是 `1`（说明文件大小或属性变了）：系统大喊一声“起航！”，**启动磁盘 I/O，把这个修改后的最新 FCB，精准地写回磁盘上该目录文件对应的那个槽位里，覆盖掉旧的 FCB**。
        
    - 如果是 `0`：直接抹掉内存里的活动 FCB。
        

### 💾 【外存（磁盘）】的最终归宿：

- 磁盘上的**目录文件**被改写了，里面那一行 `test.txt` 的大小终于变成了 5B。
    

## 总结：两套模型的终极对比

我们可以用一张对比表，把你之前晕的地方彻底理顺：

| **比较维度**                 | **传统纯 FCB 模型**                   | **现代 Inode 模型**                       |
| ------------------------ | -------------------------------- | ------------------------------------- |
| **磁盘目录项里存什么？**           | **完整的 FCB**（文件名 + 所有属性）          | **极简的对子**（文件名 + Inode 号）              |
| **磁盘上有独立的属性区吗？**         | 没有，属性全死磕在目录文件里                   | 有，专门的 **Inode 区** 存属性                 |
| **打开文件时，内存里建什么？**        | 把整个 FCB 复制到内存系统表，成为**活动 FCB**    | 把磁盘 Inode 复制到**内存 Inode 表**，系统表挂指针指向它 |
| **修改了文件大小，close 时写回哪里？** | 写回磁盘的**目录文件**里的那一行               | 写回磁盘的**Inode 区**对应编号的位置               |
| **为什么纯 FCB 模型被淘汰了？**     | 目录文件太胖了！找个文件要读入大量无用属性，磁盘 I/O 极慢。 | 目录文件极瘦，一个盘块能装更多文件名，查文件巨快！             |
