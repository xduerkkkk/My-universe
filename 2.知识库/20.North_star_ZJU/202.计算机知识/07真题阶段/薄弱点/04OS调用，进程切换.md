
# 一些零碎的点
 - 进程 P 是在**内核代码的中间**（系统调用路径内检查到队满）被置为阻塞态并让出 CPU 的。
    - 现场保存在 P 的**内核栈**中。
    - 唤醒并被调度后，CPU 直接在**内核态**恢复执行，从当时挂起的那一行代码接着往下跑，把字符写入刚腾出的空位，随后返回用户态。**不需要、也不会让 P 先回用户态重新发起一次系统调用。**







#  普通函数调用的全过程完整串联如下：

---

### 1. 准备出发：调用者（Caller）传参
* **代码在执行**：PC 在代码段里一行行走，马上要调 `add(1, 2)`。
* **第一件事：传参**：
  * 先执行 `push 2`，再执行 `push 1`。
  * **指针动作**：每次 `esp -= 4`，把参数 2 和 1 依次塞进用户栈。
  * *（此时：栈顶 ESP 指向参数 1）*

### 2. 跨出门槛：执行 `call add` 指令
* **取指阶段**：
  * CPU 把 `call` 这条机器指令读进 IR 寄存器。
  * **PC 自动递增**，此时 **PC 已经精准指向了 `call` 下面的那条指令（即返回地址）**。
* **执行阶段（微操作发生）**：
  * 栈指针下移：`esp -= 4`。
  * 压入返回地址：`M[esp] <- PC`（把刚才算好的返回地址塞入栈顶）。
  * 强行装入目标地址：`PC <- add` 的入口地址（来自 `call` 指令本身自带的操作数）。
  * *（此时：栈顶 ESP 指向返回地址；PC 指向被调用函数的第 1 行代码）*

### 3. 进入现场：被调用者（Callee）立地基（建栈帧）
* **指令周期切换**：下一个周期，CPU 顺着新 PC，直接取到 `add` 函数开头的机器指令。
* **第一句：`push ebp`**：
  * 栈指针下移：`esp -= 4`。
  * 备份旧地基：`M[esp] <- ebp`（把调用者的旧 EBP 值存进栈里，防止待会儿冲掉）。
* **第二句：`mov ebp, esp`**：
  * 此时 `ebp = esp`，**当前函数的新栈帧地基正式确立**。
  * 从这一刻起，EBP 死死钉在这里，不管后面 ESP 怎么动，EBP 都不动。
* **第三句：`sub esp, K`**：
  * `esp` 往下减 $K$ 个字节，为本函数的局部变量抠出一片私有空间。
  * *（此时寻址逻辑闭环：`[ebp + 8]` 是刚才传进来的参数，`[ebp - 4]` 是自己的局部变量）*

### 4. 算完交差：被调用者拆除空间
* 计算完成，函数的返回值按惯例直接塞进通用寄存器（如 `eax`）。
* **第一步拆空间：`mov esp, ebp`**：
  * 让 `esp` 直接跳回 `ebp` 的位置。
  * 之前给局部变量留的 $K$ 字节空间被瞬间在逻辑上丢弃。
  * *（此时：栈顶 ESP 正好停在刚才存“旧 EBP”的位置）*
* **第二步还地基：`pop ebp`**：
  * 从栈顶把旧数值掏出来还给寄存器：`ebp <- M[esp]`。
  * 栈顶指针回收：`esp += 4`。
  * 调用者的基准 EBP 彻底还原！
  * *（此时：ESP 刚好露出并且正对着“返回地址”）*

### 5. 跳回原点：执行 `ret`
* **执行 `ret` 指令**：
  * 弹出返回地址打入 PC：`PC <- M[esp]`。
  * 栈顶指针再回收：`esp += 4`。
  * **PC 被强行覆写**，下一个周期 CPU 就顺理成章地回到了调用者函数的断点处。

### 6. 收尾扫地：调用者平衡堆栈
* 跳回调用者后，调用者执行一条指令（如 `add esp, 8`）。
* 栈指针往上退 8 个字节，刚才一开始压进去的那两个参数（1 和 2）彻底失效。
* **全流程结束**：PC 走它的代码段，ESP/EBP 丝毫不差地退回最初的位置，栈彻底平衡。



# 系统调用

你猜对了一半：**参数确实是先塞进寄存器，进入内核后再被压入内核栈。**


---

### 1. 用户态准备：装填寄存器（不走栈）
普通函数调用靠用户栈传参，但系统调用跨越了特权级，**不能直接依赖用户栈传参**（内核不能信任用户栈指针）：
* **系统调用号**：放入通用寄存器（如 `eax = 4` 代表 `sys_write`）。
* **业务参数**：依次放入其余通用寄存器（如 `ebx = fd`, `ecx = buf`, `edx = count`）。
* *（此时：CPU 依然是用户态 Ring 3，用的依然是用户栈）*

### 2. 跨越边界：触发软中断/陷阱（`int 0x80`）
这是与普通 `call` 最本质的区别。用户代码执行 `int 0x80` 的瞬间，**CPU 硬件电路在硬件层面自动、原子地完成以下 4 件事**：

1. **特权级翻转**：
   * 当前特权级从用户态（Ring 3）强制变为内核态（Ring 0）。
2. **强制换栈（极为关键）**：
   * CPU 硬件从任务状态段（TSS）中读取操作系统预先配置好的**内核栈顶指针**（`ss0:esp0`）。
   * **`esp` 寄存器瞬间被换成了内核栈的指针！** 从这一刻起，后续所有的压栈动作全发生在**内核栈**上。
3. **硬件自动压栈保存“用户态案发现场”**：
   * 硬件在**内核栈**上按固定顺序自动压入 5 个关键寄存器：
     $$\text{压入：用户态 SS} \to \text{用户态 ESP} \to \text{EFLAGS (标志/状态字)} \to \text{用户态 CS} \to \text{用户态 PC (EIP)}$$
   * *（对比普通 call：普通 call 只压一个 PC 到用户栈；而这里把用户当时用的栈指针 ESP、状态字 EFLAGS、断点 PC 全压进了内核栈）*
4. **强行装填 PC（入口不可由用户指定）**：
   * 普通 `call` 是指令写去哪就去哪；**系统调用绝对不允许用户指定跳转地址**（否则会有特权漏洞）。
   * CPU 拿着中断向量号 `0x80`，去查内存中的**中断描述符表（IDT）**，找到内核系统调用总入口函数（如 `system_call`）的地址，直接装入 PC。

### 3. 内核接管：保存寄存器并调用服务例程
此时 PC 已经指向了内核代码：
1. **保存现场（参数入栈）**：
   * 内核入口代码立即执行一连串 `push`，把刚才用户放了参数的通用寄存器（`eax, ebx, ecx, edx...`）**全部一口气压入内核栈**。这就印证了你的猜想：参数从寄存器落到了内核栈上（在内核中拼成一个结构体 `pt_regs`）。
2. **查系统调用表**：
   * 内核读取压在栈里的 `eax`（系统调用号），去查内核的**系统调用表（`sys_call_table`）**：
     $$\text{目标函数} = \text{sys\_call\_table}[\text{eax}]$$
3. **执行内核业务逻辑**：
   * 这一步内核才会执行类似 `call sys_write`。这里面是内核内部的普通 C 函数调用，执行文件写入等底层硬件操作。
   * 计算完毕后，将结果（如写入的字节数）写入保存现场的 `eax` 位置。

### 4. 退出返回：完全不同的指令 `iret`
函数不能用 `ret` 返回，因为 `ret` 只能弹出一个 PC，根本无法处理特权级和换栈。必须使用特权指令 **`iret`（Interrupt Return）**：

1. **恢复通用寄存器**：
   * 内核把刚才压栈的通用寄存器 `pop` 出来，此时 `eax` 里带着返回值。
2. **执行 `iret` 硬件指令**：
   * CPU 硬件从内核栈上依次逆向弹出：
     $$\text{弹出：用户态 PC} \to \text{用户态 CS} \to \text{EFLAGS} \to \text{用户态 ESP} \to \text{用户态 SS}$$
3. **硬件自动恢复现场与特权级**：
   * 伴随这一弹：**`esp` 瞬间从内核栈切回了用户栈**；
   * 特权级自动从 Ring 0 **切回 Ring 3**；
   * PC 恢复为用户的断点，CPU 丝滑地回到用户程序下一行继续跑。

---

### 对比总结表（408 必考差异）

| 机制差异       | 普通函数调用（`call / ret`） | 系统调用（`trap / iret`）                       |
| :--------- | :------------------- | :---------------------------------------- |
| **触发指令**   | `call`（普通控制转移指令）     | `int 0x80` / `syscall`（访管/陷阱指令）           |
| **特权级别**   | **不改变**（始终在用户态）      | **切换**（Ring 3 $\to$ Ring 0 $\to$ Ring 3）  |
| **使用的栈**   | **全程单一栈**（用户栈）       | **发生栈切换**（用户栈 $\to$ 内核栈 $\to$ 用户栈）        |
| **硬件保存内容** | 仅保存 **PC** 到用户栈      | 自动保存 **PC + CS + EFLAGS + ESP + SS** 到内核栈 |
| **入口寻址方式** | 指令操作数直接给定            | 必须通过**中断描述符表（IDT）**间接查找                   |
| **返回指令**   | **`ret`**（只弹 PC）     | **`iret`**（弹断点、弹状态字、弹用户栈指针、降特权级）          |

# 进程切换

承接前面建立的体系，理解进程上下文切换最关键的一点是：

> **进程切换绝对不可能在用户态直接发生！**
> 它必须且只能在**内核态**下完成。也就是说，CPU 一定是先通过**系统调用**或**硬件中断**陷入了内核，由操作系统接管后，才执行上下文切换。

我们设定场景：**进程 A 正在运行，时钟中断到来（时间片耗尽），操作系统决定剥夺 A 的 CPU，切换给就绪队列中的进程 B。**

顺着 CPU 指针（PC、ESP、CR3）和内存状态的变化，完整的执行流程线如下：

---

### 第一阶段：被动陷入内核（进程 A 保存用户态现场）

这一步完全就是之前讲的中断/异常响应，发生在**进程 A 的私有内核栈**上。

1. **时钟中断触发（硬件自动执行）**：
   * CPU 硬件打断进程 A 的用户代码执行。
   * 特权级：$\text{Ring 3} \to \text{Ring 0}$。
   * 换栈：`esp` 切换为**进程 A 的内核栈**。
   * 硬件自动压栈保存进程 A 的用户态现场：
     $$\text{进程 A 的用户态 SS} \to \text{用户态 ESP} \to \text{EFLAGS} \to \text{用户态 CS} \to \text{用户态 PC}$$
2. **内核中断入口保存通用寄存器（软件执行）**：
   * 中断服务例程将进程 A 用户态使用的通用寄存器（`eax, ebx, ecx...`）全部压入**进程 A 的内核栈**。
   * **此时的状态**：进程 A 的用户态运行现场（代码断点、用户栈顶、数据寄存器）已经百分之百完整地封存在了 **A 的内核栈** 顶端。

---

### 第二阶段：触发调度器（确定换下 A，换上 B）

1. **时钟中断处理逻辑**：
   * 中断处理函数减少进程 A 的剩余时间片。
   * 发现时间片减为 0，内核将进程 A 的状态由“运行态”标记为“就绪态”，并重新放回就绪队列。
   * 内核设置重新调度标志（`need_resched = 1`）。
2. **激活调度程序 `schedule()`**：
   * 中断处理准备返回前，检测到需要调度，直接调用调度核心函数 `schedule()`。
   * 调度算法（如 CFS 调度器）从就绪队列中挑出下一个该运行的进程：**进程 B**。

---

### 第三阶段：核心切换 `context_switch()`（两大切换）

操作系统把当前执行进程从 A 切换到 B，本质上只做两件硬核的事：
**一是切换虚拟内存空间（地址映射切换），二是切换 CPU 寄存器与内核栈（硬件执行流切换）。**

#### 1. 切换虚拟地址空间（`switch_mm`）
* **操作**：把**进程 B 的页目录基地址（Page Directory Base）**写入 CPU 的控制寄存器 **CR3**。
  $$\text{CR3} \leftarrow \text{进程 B 的页目录物理地址}$$
* **效果**：
  * **一瞬间，整个虚拟地址空间全变了！** 
  * 线性地址到物理地址的映射规则完全切成了进程 B 的视角。
  * **副作用（408 核心考点）**：修改 CR3 寄存器会导致 CPU 内部的**快表（TLB）全部被硬件强制刷新/无效化**（除非启用了带有 ASID/PCID 标签的硬件特性）。

#### 2. 切换内核栈与处理器状态（`switch_to`，最精妙的一步）
地址空间换完后，CPU 目前依然在跑内核代码，此时必须把内核级上下文切成 B。

1. **保存进程 A 的内核现场**：
   * 进程 A 正在调用函数，把 A 当前内核执行相关的寄存器（如内核态下的 `ebp, ebx, esi, edi`）压入 **A 的内核栈**。
   * 将当前 CPU 的 `esp`（指向 A 的内核栈顶）保存到 **进程 A 的 PCB（`task_struct` 中的 `thread_struct`）** 里：
     $$\text{PCB}_A \rightarrow \text{kernel\_esp} \leftarrow \text{当前 ESP}$$
2. **加载进程 B 的内核现场（灵魂一跃）**：
   * 内核从 **进程 B 的 PCB** 中取出 B 上次被换下时保存的内核栈指针：
     $$\text{当前 ESP} \leftarrow \text{PCB}_B \rightarrow \text{kernel\_esp}$$
   * **此时此刻：CPU 已经在使用进程 B 的内核栈了！**
3. **恢复进程 B 的内核寄存器**：
   * 伴随一连串 `pop`，从 **进程 B 的内核栈** 中弹回 B 的内核寄存器（`edi, esi, ebx, ebp`）。
   * 执行 `ret` 指令：从 B 的内核栈顶弹出一个返回地址打入 PC。
   * **此时：CPU 已经彻底在进程 B 的内核执行流里继续跑了！**

---

### 第四阶段：从内核态返回到进程 B 的用户空间

此时进程 B 接管了 CPU，但它还在内核态。它怎么回到它自己的用户代码？

1. **更新 TSS（任务状态段）**：
   * 内核将 TSS 中的内核栈指针更新为 **进程 B 的内核栈底**，确保下一次发生中断时，CPU 能正确压入 B 的内核栈。
2. **恢复进程 B 的通用寄存器**：
   * 从 B 的内核栈中连续 `pop` 出 B 上一次被中断打断时保存的所有用户态通用寄存器（`eax, ebx, ecx...`）。
3. **执行 `iret` 指令（大功告成）**：
   * CPU 硬件从 **进程 B 的内核栈** 上依次弹出：
     $$\text{弹出：进程 B 的用户态 PC} \to \text{用户态 CS} \to \text{EFLAGS} \to \text{用户态 ESP} \to \text{用户态 SS}$$
   * **硬件动作伴随生效**：
     * 特权级自动切回 **Ring 3**（用户态）；
     * 栈指针切回 **进程 B 的用户栈**；
     * PC 指向 **进程 B 上次被暂停时的那一行用户代码**。

**至此，进程 A 的痕迹彻底隐退，进程 B 像从来没有被中断过一样，继续向下执行。**

---

### 极简脉络全景图

```
[进程 A 用户态]
       │
 (时钟中断触发)
       ▼
[进程 A 内核态] ── 硬件+软件把 A 的所有寄存器压入【A 的内核栈】
       │
 (调度器选择 B)
       ▼
  切换 CR3   ── 把页表基址换成 B 的（虚拟空间切换，TLB 失效）
       │
  切换 ESP   ── 把 CPU 的 ESP 从【A 的内核栈】切到【B 的内核栈】
       ▼
[进程 B 内核态] ── 从【B 的内核栈】逆向 pop 出 B 当初存的内核寄存器
       │
  (执行 iret)
       ▼
[进程 B 用户态] ── 硬件恢复 B 的用户 PC、用户栈 ESP、切回 Ring 3
```

---

### 408 核心考点速查

1. **上下文切换由谁完成？** 
   * **纯软件**。由操作系统内核的调度代码与上下文切换例程（如 `switch_to`）执行指令完成。
2. **切换进程需要换哪些上下文？**
   * **用户级上下文**：通用寄存器、PC、用户栈指针（保存在内核栈上）。
   * **系统级上下文**：虚拟地址空间（CR3 寄存器）、内核栈指针（保存在 PCB 中）。
3. **为什么进程切换开销比线程切换大得多？**
   * 同一进程内的线程共享虚拟地址空间，**线程切换不需要改写 CR3，不需要刷新 TLB**。
   * 进程切换**必须换 CR3，导致 TLB 全清**，随后的内存访问会经历一连串严重的 TLB 缺失（Cold Miss），这是进程切换最大的性能代价所在。

# 系统调用+中断
### 全链路大闭环：从系统调用到中断与驱动的完整交互

现在把你之前问的所有知识点（系统调用、用户栈/内核栈、上下文切换、中断隐指令、驱动程序）**合成一个完整的大事件**。

**场景**：用户程序执行 char c = getchar ();（需要从键盘读入一个字符），而键盘此时还没按键。

整个计算机底层发生的故事如下：

codeCode

```
[用户态] 用户程序: 执行 getchar() -> 封装为 read() 系统调用
   │
   │ 1. 触发系统调用 (int 0x80 / syscall)
   ▼
[内核态] 硬件切特权级(Ring 3 -> 0)，换【内核栈】，压入用户现场(PC, ESP, EFLAGS)
   │
   │ 2. 内核虚拟文件系统/设备独立性软件路由到【键盘驱动程序】
   ▼
[设备驱动程序] 
   * 检查键盘控制器的状态寄存器，发现没有按键按下。
   * 驱动把当前进程标记为【阻塞态 (WAITING)】，挂入键盘的等待队列。
   * 调用 schedule()，发起【进程上下文切换】！
   │
   │ 3. 上下文切换发生
   ▼
[进程切换] 
   * 换 CR3（虚拟内存切走），换 ESP 到别的就绪进程内核栈。
   * CPU 切去跑别的进程（如后台播放音乐）。当前进程彻底休眠。
   │
   │ 4. 过了 3 秒，用户在键盘上敲了字母 'A'！
   ▼
[硬件动作] 
   * 键盘控制器硬件电平变化，向中断控制器（PIC/APIC）发送电信号（中断请求 IRQ 1）。
   * 中断控制器向 CPU 的 INTR 引脚发信号。
   │
   │ 5. 中断响应 (中断隐指令，纯硬件完成！)
   ▼
[CPU 硬件] 
   * 当前指令周期结束，CPU 发现中断信号。
   * 硬件【关中断】。
   * 硬件自动压栈保护当前正在跑的倒霉进程的断点（PC, PSW）。
   * 硬件拿着中断向量号 1 去查【中断向量表/IDT】。
   │
   │ 6. 查出来的这个 ISR 入口地址是谁给的？
   │    —— 就是驱动程序最初调用 request_irq() 注册/挂接进去的！
   ▼
[驱动程序的中断服务例程 (ISR) 执行] (对应选项 I 和 II)
   * CPU 跳转到驱动预留的 ISR 代码。
   * ISR 从键盘数据寄存器读取扫描码（'A'）。
   * ISR 向控制器发送应答信号（清除硬件中断标志）。
   * ISR 把扫描码转为 ASCII 码，存入内核缓冲区。
   * ISR 将之前休眠的那个进程的状态从【阻塞态】修改为【就绪态】，移入就绪队列！
   │
   │ 7. 中断退出与调度
   ▼
[内核调度] 
   * 执行 iret 恢复现场，开中断。
   * 调度器在后续某个时钟滴答中挑中刚唤醒的进程。
   * 再次发生【进程上下文切换】，切回该进程的内核栈，恢复通用寄存器。
   │
   │ 8. 系统调用返回
   ▼
[返回用户态]
   * 执行 iret，弹栈恢复用户态 PC, ESP，切回 Ring 3。
   * 用户程序的 getchar() 终于拿到了字符 'A'，继续往下执行！
```

### 三者的绝对定义与层次定位

用这个标准层次模型死死记住它们的分工：

1. **系统调用（Syscall）**：
    
    - **方向**：自顶向下（软件主动发起）。
        
    - **角色**：用户程序请求操作系统服务的**大门**（如请求读设备）。
        
2. **设备驱动程序（Device Driver）**：
    
    - **方向**：上下承接。
        
    - **角色**：翻译官。向上对内核提供统一的读写接口（read/write），向下直接读写外设芯片的物理寄存器。
        
3. **中断服务例程（ISR / 中断处理程序）**：
    
    - **方向**：自底向上（硬件事件触发）。
        
    - **角色**：紧急救火员。外设硬件完工后叫醒 CPU，由驱动内嵌的 ISR 负责把硬件吐出来的数据收缴到内核，并**唤醒等在那里的进程**。
