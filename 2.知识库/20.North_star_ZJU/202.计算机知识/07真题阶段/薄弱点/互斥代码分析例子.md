
# 例题 1

这里有三个核心问题：关于“进程意外下线”的前提偏差、当前代码的“空闲让进”与“忙则等待（互斥）”判断及反例构造，以及 408 常考的四大软件互斥算法的统一拆解。我们逐一解决。

---

### 一、纠正前提偏差：进程在临界区意外下线算不算违反“空闲让进”？

**直接指出你的理解偏差**：在操作系统讨论同步互斥机制（无论是软件算法、硬件指令还是信号量）时，有一个**硬性理论前提**：
**假设任何进入临界区的进程，都必须在有限时间内执行完临界区代码并正常离开，绝不允许在临界区内异常终止（崩溃）或陷入死循环。**

如果不做这个假设，世界上没有任何一种同步算法（包括 Peterson 算法和信号量）能正常工作——哪怕用信号量，进程在 `P(S)` 之后崩溃，没有执行 `V(S)`，其他进程也永远进不去。

再从**“空闲让进”的精确定义**来看：
“空闲让进”指的是**当没有任何进程处于临界区时**，任何请求进入临界区的进程都必须被允许立即进入。
- 如果 $P_0$ 正在执行 `critical section` 时崩溃下线，它的程序计数器（PC）停留在临界区内，此时**临界区处于“忙（被占用）”状态，根本不满足“空闲”这一前提条件**，自然谈不上是否违反“空闲让进”。
- 所谓“意外下线不阻碍别人”的要求，只针对**剩余区（remainder section）**：一个进程在剩余区崩溃或永远不再申请进入临界区，绝对不能阻碍其他进程进入临界区。

### 二、本题代码的精确分析与反例构造

看题目代码的核心特征：**先检查对方标志（第 1 行），后修改自己标志（第 2 行）**。

#### 1. 为什么满足“空闲让进”？
*   **判定方法**：假设临界区空闲，且只有一个进程（比如 $P_0$）想进，$P_1$ 在剩余区（根本不想进，即 `flag[1] == false`），看 $P_0$ 能否无阻碍通过进入区。
*   **执行过程**：临界区空闲且 $P_1$ 不想进时，`flag[1]` 必定为 `false`。$P_0$ 执行第 1 行 `while(flag[1]);`，条件为假，直接跳过循环，执行第 2 行 `flag[0] = true;` 并顺利进入第 3 行临界区。没有任何阻碍，因此**满足空闲让进**。

#### 2. 怎么构造例子证明不满足“忙则等待（互斥）”？
*   **构造反例的核心技巧**：找进入区中**“检查变量”与“修改变量”之间的时间窗口**。在这两者之间强行发生进程切换（上下文切换）。
*   **具体调度序列构造**：
    初始状态：`flag[0] = false`，`flag[1] = false`。
    1. **$P_0$ 执行第 1 行**：`while (flag[1]);`。此时 `flag[1]` 为 `false`，$P_0$ 跳出循环，准备执行第 2 行。
    2. **【发生进程切换】**：在 $P_0$ 还没来得及把 `flag[0]` 设为 `true` 时，时间片用完，切换到 $P_1$。
    3. **$P_1$ 执行第 1 行**：`while (flag[0]);`。因为第 2 步中 $P_0$ 还没改标志，此时 `flag[0]` 依然是 `false`！所以 $P_1$ 也顺利跳出循环。
    4. **$P_1$ 执行第 2、3 行**：将 `flag[1]` 设为 `true`，**进入临界区**。
    5. **【发生进程切换】**：切换回 $P_0$。
    6. **$P_0$ 继续执行第 2、3 行**：$P_0$ 之前已经跳过了第 1 行的 `while` 检查，现在直接执行第 2 行将 `flag[0]` 设为 `true`，然后**也进入临界区**。
*   **结果**：$P_0$ 和 $P_1$ 同时处于第 3 行 `critical section`，**违反“忙则等待”（未实现互斥）**。

### 三、用同样的方法，把 408 常考的这类题过一遍

408 考察软件互斥算法，本质上就是考察 **单标志法、双标志先检查法（即本题）、双标志后检查法、Peterson 算法** 以及它们的变体。

评判标准固定为三条（让权等待一般单独看是否有一方在 `while` 空转）：
1. **忙则等待（互斥）**：按上述“在检查和赋值之间切走”的方法，看能否让两个进程同时跳出 `while`。
2. **空闲让进**：让一个进程停在剩余区（或根本不启动），看另一个进程能否连续进入临界区 2 次以上。
3. **有限等待**：看两个进程同时想进时，会不会都在 `while` 里死循环（饥饿/活锁），或者某一个进程能不能无限次插队。

下面按同一套模板拆解另外三种常考题型：

---

#### 题型 1：单标志法（使用 `turn` 变量）
```c
int turn = 0; // turn 表示当前允许进入临界区的进程号

// P0 进程                      // P1 进程
while (turn != 0);              while (turn != 1);
critical section;               critical section;
turn = 1;                       turn = 0;
remainder section;              remainder section;
```
*   **忙则等待（满足）**：`turn` 在同一时刻只能是 `0` 或 `1`（单一基本变量读取/赋值具有原子性）。无论怎么切换，不可能同时满足 `turn == 0` 和 `turn == 1`，绝对不会同时进入临界区。
*   **空闲让进（违反！常考点）**：
    *   **反例构造**：初始 `turn = 0`。假设 $P_0$ 从头到尾都不想进临界区（一直在剩余区），此时临界区是**空闲**的。现在 $P_1$ 想进，执行 `while (turn != 1);`，因为 `turn` 是 `0`，$P_1$ 直接被卡死在循环里。
    *   **机制原因**：该算法强制要求 $P_0 \to P_1 \to P_0 \to P_1$ 轮流进入。如果拿到权限的进程不进，另一个进程面对空闲的临界区也进不去。

---

#### 题型 2：双标志后检查法
为了修复你题目中“先检查后上锁”的漏洞，改成**“先上锁（修改自己标志），后检查对方标志”**：
```c
bool flag[2] = {false, false};

// P0 进程                      // P1 进程
flag[0] = true;                 flag[1] = true;
while (flag[1]);                while (flag[0]);
critical section;               critical section;
flag[0] = false;                flag[1] = false;
```
*   **忙则等待（满足）**：进程必须先将自己的 `flag` 置为 `true` 才能到达 `while` 语句。如果双方都到了临界区，说明一方跳出 `while` 时看到的对方 `flag` 为 `false`，这在双方都已经执行了第 1 行 `flag[i] = true` 的前提下是不可能同时成立的。
*   **空闲让进（满足）**：如果只有 $P_0$ 想进，`flag[1]` 为 `false`，$P_0$ 置 `flag[0] = true` 后检查 `flag[1]`，直接通过。
*   **有限等待（违反！同时违反空闲让进的广义情况）**：
    *   **反例构造**：在**两个进程的第 1 行和第 2 行之间**切换。
        1. $P_0$ 执行第 1 行：`flag[0] = true;`
        2. **【切换】** $P_1$ 执行第 1 行：`flag[1] = true;`
        3. 此后，$P_0$ 执行 `while(flag[1]);` 死循环，$P_1$ 执行 `while(flag[0]);` 也死循环。
    *   **结果**：临界区明明是空闲的，但两个进程都进不去，且无限期等待下去（产生类似死锁的活锁/饥饿现象）。因此**既违反空闲让进（双方争抢时），也违反有限等待**。

---

#### 题型 3：Peterson 算法（结合 `flag` 和 `turn`）
408 最爱考的终极软件算法，经常通过**调换第 1、2 行的顺序**来出变形题：

**【标准正确版】**：
```c
bool flag[2] = {false, false};
int turn = 0;

// P0 进程                                      // P1 进程
1: flag[0] = true;                              1: flag[1] = true;
2: turn = 1;                                    2: turn = 0;
3: while (flag[1] && turn == 1);                3: while (flag[0] && turn == 0);
4: critical section;                            4: critical section;
5: flag[0] = false;                             5: flag[1] = false;
```
*   **为什么全满足（除让权等待外）**：
    *   **空闲让进**：若 $P_1$ 不想进，`flag[1] == false`，$P_0$ 在第 3 行的 `flag[1] && turn == 1` 必为假，直接进。
    *   **忙则等待 & 有限等待**：若双方都想进，都执行完第 1、2 行后，`flag[0]` 和 `flag[1]` 全为 `true`。但 `turn` 变量只能有一个最终值（取决于谁**最后**执行第 2 行）。假设 $P_1$ 最后执行 `turn = 0`，那么 `turn` 最终为 `0`，$P_0$ 的 `while` 条件 `turn == 1` 不成立，$P_0$ 立刻跳出循环进入临界区，绝不会死锁，也不会同时进。

**【408 高频变形题：如果把 Peterson 算法的第 1 行和第 2 行颠倒会怎样？】**
即变成：**先谦让（改 `turn`），后表达意愿（改 `flag`）**：
```c
// 变形后的 P0                   // 变形后的 P1
1: turn = 1;                    1: turn = 0;
2: flag[0] = true;              2: flag[1] = true;
3: while (flag[1] && turn == 1); 3: while (flag[0] && turn == 0);
```
*   **判定结论**：**违反忙则等待（无法保证互斥）！**
*   **反例构造（套用我们的切片法）**：
    初始 `flag[0] = false, flag[1] = false`。
    1. **$P_0$ 执行第 1 行**：`turn = 1;`
    2. **【切换】** 此时 $P_0$ 还没来得及设 `flag[0] = true`。
    3. **$P_1$ 一口气执行第 1、2、3 行**：
        *   第 1 行：`turn = 0;`（把 `turn` 改成了 0！）
        *   第 2 行：`flag[1] = true;`
        *   第 3 行：检查 `while (flag[0] && turn == 0)`。注意！此时 `flag[0]` 还是 `false`！所以 $P_1$ 顺利跳出 `while`，**进入临界区**。
    4. **【切换】** 回到 $P_0$ 继续执行第 2、3 行：
        *   第 2 行：`flag[0] = true;`
        *   第 3 行：检查 `while (flag[1] && turn == 1)`。注意！刚才第 3 步里 $P_1$ 已经把 `turn` 改成了 `0`！所以 `turn == 1` 为假，$P_0$ 也顺利跳出 `while`，**进入临界区**。
    5. **结果**：$P_0$ 和 $P_1$ 同时进入临界区，互斥失效。

---

### 总结：考场做题步骤（30 秒破题法）
遇到任何陌生或变形的互斥代码题，按以下三步走：
1. **看有没有死等循环（`while`）**：只要进入区是用 `while` 空转等待的，直接判定**“不满足让权等待”**（因为占着 CPU 空转）。
2. **单进程测试（测空闲让进）**：遮住 $P_1$ 的代码（令 $P_1$ 处于初始状态不动），只让 $P_0$ 自己跑。如果 $P_0$ 能连续进出临界区两次，就**满足空闲让进**；如果第一次或者第二次被卡在 `while`（如单标志法），就**不满足空闲让进**。
3. **双进程卡位切换（测互斥与有限等待）**：
    *   找到 `while` 语句**前面**的赋值语句。
    *   如果 `while` 前面**没有**对自己 `flag` 赋值的语句（如你截图的题），或者修改 `flag` 前先改了 `turn`（如颠倒的 Peterson），直接在进入 `while` 刚结束或改完 `turn` 时切换进程，必能构造出**两个进程同时进临界区（违反忙则等待）**。
    *   如果 `while` 前面改了自己的 `flag`，且 `while` 条件里只看对方的 `flag`（无 `turn` 裁决），则在双方刚改完自己 `flag` 时切换，必能构造出**双方都在 `while` 里死循环（违反有限等待）**。


这两条规律没有完全吃透，是因为我刚才只给了你“操作口诀”，没有把底层的**变量状态读写机制**彻底剥开。我们现在抛开口诀，从计算机底层执行指令的**读写顺序**来把这两个原理彻底讲透，然后做 4 道针对性例题。

# 变式 4
### 一、深度拆解：为什么会有这两种截然不同的失败结果？

在双进程互斥代码中，进入区（Entry Section）干的事情只有两件：
1. **写（Write）**：修改全局变量（如 `flag[0] = true` 或 `turn = 1`），实质是**向对方广播自己的状态**。
2. **读（Read）**：在 `while` 循环里读取全局变量（如 `while(flag[1])`），实质是**检查对方的状态以决定自己是否阻塞**。

只要是软件算法，“写”和“读”就必定分属两条不同的机器指令，中间**一定可以被中断切换**。所有的漏洞，都源于**“写”和“读”的排列组合问题**。

---

#### 深入理解第一条：什么情况下会“同时进临界区（违反忙则等待）”？

**核心本质**：一个进程已经通过了 `while` 检查（读操作完成，拿到了通行证），但**还没来得及向对方发出阻拦信号（写操作未完成）**，或者**发出的阻拦信号被对方覆盖了**。

我们分两种情况看这个漏洞是怎么产生的：

**情况 A：`while`（读）在 `flag = true`（写）的前面**
```c
1: while (flag[1]);   // 读对方状态
2: flag[0] = true;    // 写自己状态（加锁）
```
*   **底层逻辑**：第 1 行是“检查门里有没有人”，第 2 行是“把门锁上”。
*   **漏洞必然性**：当 $P_0$ 刚执行完第 1 行时，它通过了检查（认为自己可以进临界区了）。但此时第 2 行还没执行，内存中 `flag[0]` 依然是 `false`。此时切到 $P_1$，$P_1$ 看到的内存状态和刚才 $P_0$ 看到的**完全一模一样**（双方都是 `false`）。所以 $P_1$ 也必然通过第 1 行的检查。
*   **结论**：只要“写 `flag`”在“读 `flag`”后面，就意味着**先拿通行证、后关门**。在拿证和关门之间切走，对方也能拿到通行证，必定违反“忙则等待”。

**情况 B：颠倒的 Peterson 算法（先写 `turn`，后写 `flag`，再读）**
```c
1: turn = 1;                    // 写 turn
2: flag[0] = true;              // 写 flag
3: while (flag[1] && turn == 1);// 读 flag 和 turn
```
*   **底层逻辑**：在 Peterson 算法中，`while` 拦住进程需要**两个条件同时为真**：① 对方想进（`flag` 为真） **且** ② 轮到对方进（`turn` 指向对方）。只要破坏其中一个条件，进程就能进临界区。
*   **为什么标准版是对的？** 标准版最后一步是写 `turn`。由于 `turn` 只有一个，两个进程都执行完前两步后，`turn` 的最终值只能指向其中一方（比如等于 1），这就强行保证了必有一方被卡住，另一方通过。
*   **为什么颠倒后就错了？** 颠倒后，$P_0$ 先执行第 1 行 `turn = 1`，此时切走。注意：此时 $P_0$ **还没有执行第 2 行 `flag[0] = true`**！
    *   $P_1$ 登场：它执行 `turn = 0`（**直接覆盖了刚才 $P_0$ 写的 `turn = 1`**），接着写 `flag[1] = true`。然后 $P_1$ 到达第 3 行检查 `while(flag[0] && turn == 0)`。因为刚才 $P_0$ 没来得及写 `flag[0]`，此时 **`flag[0]` 是 `false`**！条件 ① 不满足，$P_1$ 直接进临界区！
    *   切回 $P_0$：$P_0$ 补上第 2 行 `flag[0] = true`，然后到达第 3 行检查 `while(flag[1] && turn == 1)`。因为刚才 $P_1$ 已经把 `turn` 改成了 `0`，此时 **`turn == 1` 是 `false`**！条件 ② 不满足，$P_0$ 也直接进临界区！
*   **结论**：$P_1$ 靠着“$P_0$ 还没写 `flag[0]`”混进了临界区；$P_0$ 靠着“$P_1$ 帮它改掉了 `turn`”也混进了临界区。

---

#### 深入理解第二条：什么情况下会“双方死锁在 while 里（违反有限等待）”？

**核心本质**：两个进程在进入 `while`（读）之前，都已经完成了“写 `flag = true`”的操作。此时双方都把门焊死了，而且 `while` 循环里**没有引入第三方仲裁变量（如 `turn`）来打破僵局**。

看代码结构：
```c
1: flag[0] = true;    // 写自己状态（加锁）
2: while (flag[1]);   // 读对方状态
```
*   **底层逻辑**：为了防止刚才那种“同时混进去”的情况，必须把 `flag = true` 放在 `while` 前面（先关门，再检查）。
*   **为什么绝对不会违反“忙则等待”？** 因为任何进程想要到达第 2 行，内存里的 `flag` 必定已经是 `true` 了。绝不可能出现一方在检查时，另一方到达了第 2 行却还是 `false` 的情况。所以**互斥是绝对安全的**。
*   **为什么会死循环？** 既然双方都在第 1 行写 `true`，如果在两个进程都刚执行完第 1 行时发生切换：此时内存中 `flag[0] == true` 且 `flag[1] == true`。
*   接下来双方都进入第 2 行 `while`。注意看 `while` 的条件：只检查对方的 `flag`。而把 `flag` 改回 `false` 的代码在哪里？在**第 4 行的退出区（临界区后面）**！
*   这就构成了死局：不进临界区就执行不到第 4 行改 `false`；对方不改 `false` 自己就跳不出第 2 行的 `while`。没有 `turn` 变量来强制指定谁先走，两个进程对称地卡死在第 2 行，**违反有限等待**。

#### 【例题 2】带自谦让机制的双标志法（Dekker 算法简化变体）
共享变量 `bool flag[2] = {false, false};`，两进程代码如下：
```c
// 进程 P0                      // 进程 P1
1: flag[0] = true;              1: flag[1] = true;
```

### 三、答案与逐行切片解析

#### 【例题 1 答案】：C（不满足忙则等待，满足有限等待）
*   **解析**：
    *   注意看 $P_1$ 的代码：第 1 行是 `while(flag[0])`（读），第 2 行才是 `flag[1] = true`（写）。$P_1$ 犯了**“先读后写”**的致命错误！
    *   **构造违反“忙则等待”的序列**：
        1. 初始 `flag[0] = false, flag[1] = false`。
        2. 先让 **$P_1$ 执行第 1 行**：`while(flag[0]);`。因为此时 $P_0$ 还没启动，`flag[0]` 是 `false`，$P_1$ **顺利跳出循环**！
        3. **【发生切换】**：在 $P_1$ 执行第 2 行修改 `flag[1]` 之前，切换到 $P_0$。
        4. **$P_0$ 执行第 1、2、3 行**：$P_0$ 先把 `flag[0]` 设为 `true`，然后检查 `while(flag[1])`。因为刚才第 2 步里 $P_1$ 还没来得及把 `flag[1]` 设为 `true`，所以 `flag[1]` 依然是 `false`！$P_0$ 顺利跳出循环，**进入临界区**。
        5. **【发生切换】**：切回 $P_1$。$P_1$ 早就跳出了第 1 行的 `while`，现在直接执行第 2 行 `flag[1] = true`，然后**也进入临界区**。
        6. 两者同时在临界区，**违反忙则等待**。
    *   **为什么满足有限等待？** 因为只有 $P_0$ 先改 `flag[0]`，$P_1$ 是先查后改，绝不可能出现双方同时把各自 `flag` 设为 `true` 并同时卡在 `while` 里的情况。

#### 【例题 2 答案】：C（满足忙则等待，但不满足有限等待）
*   **解析**：
    *   **看忙则等待**：任何进程要离开 `while` 进入第 6 行临界区，最后干的一件事必然是判定 `while` 条件为假（即对方 `flag` 为 `false`），且此时自己的 `flag` 必定为 `true`（无论是从第 1 行进来的，还是在循环内第 4 行改回 `true` 的）。因此绝不可能双方同时看到对方为 `false` 而混进临界区，**满足忙则等待**。
    *   **看有限等待（构造活锁序列）**：
        1. $P_0$ 执行第 1 行：`flag[0] = true;`
        2. **【切换】** $P_1$ 执行第 1 行：`flag[1] = true;`
        3. 双方都进入 `while` 循环体。
        4. $P_0$ 执行第 3 行：`flag[0] = false;`
        5. **【切换】** $P_1$ 执行第 3 行：`flag[1] = false;`
        6. $P_0$ 执行第 4 行：`flag[0] = true;`
        7. **【切换】** $P_1$ 执行第 4 行：`flag[1] = true;`
        8. 此时回到了和第 2 步完全相同的状态！如果两个进程推进速度完全一致（交替执行），它们会永远在第 2~5 行之间同步闪烁，谁也进不去临界区（活锁），**违反有限等待**。

#### 【例题 3 答案】：B（不满足忙则等待）

            *   `flag[0] = true;`
            *   `turn = 0;`

        2. **【发生切换】**：当 $P_0$ 正在临界区里执行时，切换到 $P_1$。
        3. **$P_1$ 执行第 1、2、3 行**：

            *   `turn = 1;`（注意：$P_1$ 把 `turn` 改成了 `1`！）

#### 【例题 4 答案】：B（满足 ② ③，不满足 ①）

### 1. 关于【空闲让进】的总结
> **你的总结**：“假设只有 $P_0$ 一个进程，其他进程代码啥都没执行，看 $P_0$ 能不能进临界区。”

*   **修正补丁**：不能只看能不能进**第 1 次**，必须看 **$P_0$ 能不能连续进出 2 次**（且 $P_1$ 也要单独测一下第 1 次）。
*   **为什么？（反例警告）**：
    回想**单标志法**（初始 `turn = 0`）：
    ```c
    // P0 进程
    while (turn != 0);
    critical section;
    turn = 1; // 退出区把 turn 改成了 1
    ```
    如果你只测 $P_0$ 进第 1 次：初始 `turn` 就是 `0`，$P_0$ 第 1 次顺畅无比地进了临界区！你就会误判它满足空闲让进！
    但是，当 $P_0$ 离开临界区时把 `turn` 改成了 `1`。此时 $P_1$ 依然啥都没干，**$P_0$ 想第 2 次进入空闲的临界区**，就会被 `while(turn != 0)` 卡死！（或者初始 `turn = 0` 时，你单独测 $P_1$ 进第 1 次，也会直接卡死）。
*   **精确口诀**：**$P_1$ 不动，让 $P_0$ 独自连续跑两圈；$P_0$ 不动，让 $P_1$ 独自跑一圈。** 只要有一次卡住，直接判**不满足空闲让进**。

### 2. 关于【忙则等待（互斥）】的总结

*   **针对 ②（具体怎么看）**：如果是“先设置、再 `while`”，且用了 `flag` 数组，你只需要看下面这两种情况会违反忙则等待，**不用盲目去凑例子**：

### 3. 关于【有限等待】的总结
> **你的总结**：“只有一种情形，就是 `while` 前设置，但是是 `flag` 这种双变量，设自己？”

*   **修正补丁**：你说的这种（双标志后检查法：先设自己 `flag[i] = true`，然后 `while(flag[j])` 且没有 `turn` 帮忙）确实是 408 **最常考的违反有限等待的情形**（双方同时设完 `true` 后卡死在 `while` 里）。
*   **但是！还有第二种常见情形也会违反有限等待（即产生“饥饿”）**：
    不仅“双方都进不去（死锁/活锁）”叫违反有限等待，**“一方能无限次进去，另一方永远插不上队（饥饿）”**也叫违反有限等待！
    *   **典型例子**：刚才**【例题 1】的不对称代码**：

    *   再比如：如果 `while` 条件里有 `turn`，但退出临界区后**只把一边的 `turn` 固定死**，导致总是同一个进程优先，另一个进程争抢时永远输，也违反有限等待。
