## 二、真正的筛选目标：不是热门，而是三件事能否同时兑现

KK 的目标是：

1. 毕设与复试准备高度重合，能够拿着自己的工作讲清楚、经得起追问。
2. 能承接已有 Agent / LLM 经历，但不只是再搭一个类似的应用。
3. 借毕设探索未来研究方向，而不是现在就给自己贴一个永久标签。

“高度重合”应理解为：**做毕设的过程，同时积累复试需要的基础理解、技术表达和研究证据。**

| 目标 | 判断问题 |
| --- | --- |
| 复试能讲透 | 能否解释问题、原理、方案取舍、实验结果和失败原因？ |
| 毕设能落地 | 是否有数据、基线、代码、算力，以及可控的最小任务？ |
| 能探索方向 | 做完后能否知道自己喜欢研究什么，而不只是又学会一个框架？ |

**理想选题：已有积累能复用，但又必须向下深挖一层。**

对 KK 来说，这一层可以是：从“会搭 Agent”走向“能解释并改善 Agent 的某个具体缺陷”。

> [!tip] 区分两种兴趣
> “我对这个应用感兴趣”不等于“我喜欢研究它背后的技术问题”。
> - 喜欢个人助理这个产品，可能真正喜欢的是记忆筛选，也可能是产品交互。
> - 喜欢 Agent 的效果，可能真正享受的是失败分析，也可能是并发、调度和性能优化。
> - 喜欢机器人演示，并不自动意味着喜欢动作表示、控制、数据处理或仿真实验。

## 四、基于实际简介的三个课题详析

### 1. 记忆管理：研究边界最清楚，目前最推荐

**题目：基于记忆筛选的大语言模型智能体记忆管理方法研究｜张旭**

#### 从简介中读出的研究闭环

- 起点：A-Mem 开源代码，而不是从零开发记忆框架。
- 数据：公开长对话数据集，但具体名称和划分尚未指定。
- 复现：记忆构建、检索、问答流程。
- 改动：**写入阶段的重复信息筛选**。
- 约束：关注新事实与时间信息的保留。
- 评价：在相同存储或上下文预算下比较问答表现、记忆规模、检索时延、模型调用开销。

因此，更准确的研究问题是：

> **如何识别“不带来新信息的重复写入”，减少资源消耗，同时避免误删事实更新、时间变化和新增细节？**

这比之前仅从题名推测的“按重要性筛选检索结果”更具体：**主要改动点在写入侧，不是优先改问答侧或检索侧。**

#### “去重”为什么不只是一个相似度阈值

以下是用于解释问题的虚构例子：

| 新旧内容关系 | 示例 | 需要防止的错误 |
| --- | --- | --- |
| 同一事实换种说法 | “我现在住在杭州”与“我目前居住在杭州” | 把纯重复不断写入 |
| 状态更新 | “我住在杭州”与“我已经搬到上海” | 因语义相近，误删新事实 |
| 计划与已发生事实 | “计划下个月搬到上海”与“上个月已搬到上海” | 混淆意图、时间和实际事件 |
| 重复部分夹带新信息 | 复述居住地，同时新增搬家时间或原因 | 整条丢弃时一并损失新增细节 |

研究重点不是笼统证明“去重更好”，而是识别什么可以去重、什么必须保留，以及在不同预算下会付出什么代价。

A-Mem 本身包含结构化记忆构建、关联与记忆演化，而不是一个仅存储文本向量的空框架。因此，需理解原有写入链路再插入筛选，检查是否影响关联与演化。[^amem]

#### 建议讨论的最小实验设计

1. 复现固定版本的原始 A-Mem 基线。
2. 增加一个朴素的相似度去重对照。
3. 在相似度去重基础上，加入一种保护新事实 / 时间信息的机制。
4. 固定问答模型、检索方式和预算规则，尽量只改变写入筛选。
5. 做消融：去掉事实 / 时间保护时，节省和误删如何变化？

> [!important] 不预设实验必须获胜
> 如果在相近问答质量下减少存储或调用，是一种结果；如果压缩后总体正确率略降，但找到可解释的质量—成本边界，也是有价值的分析。不能在实验前承诺所有指标同时提升。

#### 需要特别做严谨的四件事

- **区分两类预算。** 总存储预算与问答时检索上下文预算不是一回事。可以分别设计两组实验；若固定的是预算上限，仍要报告实际使用量。
- **不只数记忆条数。** 至少补充存储文本 Token 或字节；必要时计入元数据、向量和索引。条数少不必然意味着总存储少。
- **计算完整开销。** 新增去重判断也要计入。建议分开记录写入构建、检索、问答，再给出总开销。若在昂贵的记忆生成之后才去重，未必节省前面的调用。
- **保护实验独立性。** 不用测试问题、答案或测试集反馈调筛选规则；阈值在开发集确定。新增事实与时间类问题应分组检查，避免总体指标掩盖误删。

这些是建议的实验要求，不是简介已经承诺完成的内容。

#### A-Mem 的代码起点要问清

作者区分了系统集成实现与论文复现实验实现；论文实验仓库提供 LoCoMo 相关运行说明，但这不代表导师已指定 LoCoMo。应先确认采用哪个仓库、哪个提交版本和哪个模型配置。[^amem-code]

不需要为了“追新”自行换掉导师指定的基线。先固定可复现起点，再确定局部改进。

#### 复试可以讲出的核心故事

> 我最初尝试用语义相似度过滤重复记忆，但发现它可能误删状态变化和时间信息。因此我研究写入阶段的冗余与信息增量，在相同预算下对比问答质量与资源开销，并分析什么信息不能被压缩掉。

这是未来完成实验后可以争取讲出的叙事模板，**目前尚无实验结果，不能当作已经做过的工作**。

可深入准备的基础问题：向量表示与相似度、检索、信息更新、时间表示、数据划分、消融实验、时间与空间开销。

### 2. 错误恢复：研究兴趣仍值得保留，任务边界仍偏宽

**题目：面向多轮交互任务的智能体错误恢复方法｜白静**

简介明确了问题动机和目标，但尚未给出：

- 在哪个任务环境中做？
- 使用什么 Agent 和基线？
- 是工具显式报错，还是表面正常但方向错误？
- 研究当前任务内恢复，还是跨任务利用失败经验？
- 错误根因如何标注或验证？
- 如何控制额外工具调用、Token 与尝试次数？

这些不是一句“失败轨迹分析”就自动解决的，应在选题前收窄。

#### 一个重要区分：记录失败，不等于定位根因

可以要求自己把链路拆开：

1. 检测失败信号。
2. 找到可疑步骤。
3. 提出可检验的错误原因。
4. 选择恢复动作。
5. 验证是否真正恢复。

不能只让模型给出一段听起来合理的解释，就认定完成了根因定位。建议尽量使用有明确反馈、可回放或可控制错误的环境。

#### 不要原封不动接受“现有方法缺乏历史利用”为文献结论

Reflexion 已研究将任务反馈转为语言反思并保存在情景记忆中，用于后续尝试。因此，题目的真正差异需要落在更具体的位置，例如任务内恢复、可验证的根因定位、特定错误类型或受限预算，而不只是“增加历史记忆”。[^reflexion]

这不是否定简介，而是提醒：简介是研究动机，完整的相关工作边界仍需调研。

#### 什么时候可以重新排到第二

如果导师能提供现成环境、基线、失败轨迹，并同意只研究一两类错误，这个题目可以重新超过并行题。

建议最小对照：原始 Agent、简单重试、已有反思类方案、拟议恢复方案。尽量控制相同的调用或尝试预算，避免把“花更多资源重试”误认为机制提升。

复试可讲方向：失败检测、错误分类、状态理解、反馈可靠性、恢复代价，以及如何区分机制收益与额外计算收益。

### 3. 并行优化：真实的系统能力训练，但资源与层次决定可行性

**题目：Agent 并行计算系统性能优化方法研究｜朱虎明**

从简介看，工作不只是“调用更多 Agent”，而是：

> **理解推理系统 → 剖析实际负载 → 定位瓶颈 → 实现优化 → 验证端到端效果。**

这是该题对 KK 最有价值的部分。它要求解释“慢在哪里、为什么慢、改动为什么有效”，而不仅是展示并发执行。

#### 三个优化层次要区分

| 层次 | 可以向导师确认的示例 | 需要确认的条件 |
| --- | --- | --- |
| 工作流层 | 独立工具调用并行、任务依赖调度、流水执行 | 是否有可运行任务、依赖信息和端到端测量工具 |
| 推理服务层 | 请求调度、批处理、缓存等 | 是否有可控模型服务、服务器和测量权限 |
| GPU / 算子层 | 内核、通信或底层执行优化 | 是否要求专门的硬件、工具和额外前置知识 |

这是用于澄清范围的分层，不代表简介要求三个层次全做。

ReAct 的推理、行动和观测交替进行，因此单次任务中可能存在真实的信息依赖，不能默认每一步都能并行。LLMCompiler 则提供了依赖识别与并行函数编排的具体研究参考，说明可研究的并行化不必全部发生在 GPU 内核层。[^react][^llmcompiler]

#### 建议的评价底线

- 固定模型、任务集、硬件或资源配额，说明外部 API 条件。
- 同时报告正确率 / 成功率，避免以少做任务或答错换取加速。
- 区分单任务完成时延与多请求吞吐。
- 除模块耗时外，报告端到端结果；建议重复测量并报告波动。
- 报告增加的计算、调用和硬件资源，不能只给加速倍数。
- 区分可控制的系统瓶颈与外部 API 波动或限流。

这些是建议的实验口径，不是承诺某种优化一定有效。

#### 与复试基础的关系

它适合深入准备任务依赖图、调度、并发与并行、共享状态、资源竞争、时延与吞吐、性能分析等问题。

但“能连接 408”不等于替代基础复习，也不等于目标院校必问这些内容。

#### 条件性第二选择的前提

至少要确认：

1. 老师希望主要在哪一层优化？
2. 是否已有可运行的 Agent 工作负载与基线？
3. 服务器、GPU、经费和 profiling 工具由谁提供？
4. 本科要求是复现并改进一种优化，还是必须提出全新系统机制？

若这些资源齐备，而且 KK 对系统更有兴趣，它可以成为第一选择；若资源不明确，暂不优先于范围更清楚的记忆题。

## 五、值得保留的候补

### 候补 A：表格理解智能体

**基于 LLMs 的表格理解智能体设计与评测关键技术研究｜李卫斌**

如果前三个缺少合适资源，认真考虑这个。从题名看，它强调设计与评测，可向导师确认能否围绕明确问题展开，例如：

> 面对表格计算任务，怎样选择直接回答、调用代码或执行结构化查询？

吸引力在于：把注意力放在任务定义、工具选择、正确性验证和错误分析，而不是铺一个很大的产品系统。

### 候补 B：工具调用隐私保护

**面向工具调用的大语言模型智能体隐私保护方法研究｜张旭**

如果特别喜欢“Agent 在什么情况下会越权或泄露信息”，可以提高优先级。

AgentDojo 提供了工具使用场景下提示注入攻击与防御的评测参考，但**提示注入防御不等于隐私保护的全部**。

必须问清：

1. 保护什么信息？
2. 信息可能泄露给谁？
3. 攻击者能控制什么？
4. 防护效果和正常任务完成率如何一起评估？

若这些问题不清楚，容易停留在“增加安全提示词”。

### 候补 C：视觉 Token 动态剪枝

**面向多模态大模型的视觉 Token 动态剪枝方法研究｜导师待补充**

这是名单中值得保留的模型侧跨方向备选。

它与记忆筛选在直觉上都有“有限预算下保留什么信息”的问题，但研究对象、实现层次和所需知识不同，不能将二者混为一谈。FastV 等工作研究了多模态模型内部视觉 Token 的冗余与剪枝，可用于理解该方向的实际工作方式。

如果想验证自己是否喜欢读模型内部代码、分析注意力、做精度—效率实验，可以重点了解它。

先确认：开放模型、基线代码、算力、预期改动范围，以及是否允许在已有方案上做受控的小改进。

## 六、为什么暂不把个人助理与具身智能放第一

### 个人助理：警惕重复已有能力

已有 RAG、Agent、记忆系统经历。如果题目主要是再把这些模块接起来，新增能力可能有限。

但若导师明确要求研究知识更新、个性化或记忆机制，可以重新进入第一梯队。

**不能仅凭“系统设计与实现”判定浅，也不能仅凭“方法研究”判定深。要看实际问题和个人贡献。**

### 具身智能：先验证兴趣与资源，不凭演示效果转向

目前能确定的是做过 Agent / LLM，不能由此推导出喜欢机器人数据、控制、动作表示或仿真实验。

也不能看到 VLA 就认定必须有机器人或必须从头训练。OpenVLA 官方实现提供了模型、微调及相关实验说明，具体门槛取决于实际路线。

建议不是排除，而是：**除非导师有成熟代码、数据、实验环境和清晰的小任务，否则不把它作为备考期间的默认转向。**

## 七、还不知道研究方向时，如何选择

先区分自己更享受哪一种工作，而不是先挑一个领域标签。

| 更享受的工作 | 优先尝试的题目 |
| --- | --- |
| 分析失败案例，设计机制，比较方案为什么有效 | 记忆管理、错误恢复、隐私保护 |
| 分析运行过程、性能数据、调度与资源消耗 | Agent 并行计算、AIOS |
| 读模型内部实现，改结构或训练方案，做模型实验 | 视觉 Token 剪枝、VLM 小样本分类 |

**已有经历决定从哪里起步，不决定只能去哪里。**

当前可以暂定：

- **研究兴趣：面向真实任务的可靠、高效 LLM 智能体。**
- **毕设切口：记忆筛选 / 错误恢复 / 调度优化，三选一。**
- **模型侧探索备选：视觉 Token 动态剪枝。**

做完一个具体问题，再判断是否愿意继续深挖，比现在仅凭标题决定长期方向更可靠。

## 八、下一步：联系三位导师，而不是继续同时比较 24 个题目

先联系记忆管理、错误恢复、并行计算三个题目的导师。对每位问同一组问题，形成可比较的信息。

### 向导师核实的五个问题

1. **本科毕设最低需要完成什么？**
   - 复现加改进、系统实现，还是有更具体的成果要求？
2. **有没有建议阅读的论文、可运行基线和数据？**
   - 请老师给出最接近实际任务的起点。
3. **需要什么算力、API 经费或实验环境？由谁提供？**
4. **能否收敛成一个明确问题，而不是同时完成多个模块？**
5. **能否在复试前形成一轮可解释的实验结果？**
   - 不要求届时完成整篇论文，但应已有基线、自己的尝试、结果和失败分析。

### 核实记录

| 核实项 | 记忆管理：张旭 | 错误恢复：白静 | 并行计算：朱虎明 |
| --- | --- | --- | --- |
| 具体研究问题 | 已明确：写入侧重复筛选，保护新事实与时间 | 失败轨迹与恢复策略；需继续收窄 | 已明确性能剖析与优化；层次待确认 |

| 算力、经费与环境 | 待确认 | 待确认 | 待确认，尤其影响可行性 |
| 指导与反馈安排 | 待确认 | 待确认 | 待确认 |

## 九、复试最终要能讲出的故事

不是：

> “我做了一个用了很多技术的 Agent 系统。”

而是：

> **“我发现了一个具体问题，解释了它为什么发生，设计并比较了几种方案，知道自己的改进在哪些情况下有效、哪些情况下无效。”**

建议最终积累以下材料：

- 一个明确的问题定义。
- 一个能运行的基线。
- 一个可独立解释的改进点。
- 一组条件一致的对照实验。
- 一份失败案例与局限分析。
- 对本人贡献边界的清楚说明。

**这才是毕设、复试和未来研究兴趣真正可以重合的地方。**

## 十一、三个课题的简介原文

> 以下由 KK 于 2026-11-02 补充。保留为分析依据，不将简介中的研究动机直接视为已经验证的文献结论。

> [!quote]- 记忆管理｜张旭｜简介原文
> 智能体可以通过存储和检索历史交互信息，为后续问答和决策提供支持，但记忆不断积累会造成内容重复、检索成本增加和无关信息干扰。本课题拟调研智能体记忆管理与检索增强方法，基于A-Mem开源代码，在公开长对话数据集上复现典型记忆构建、检索和问答流程。在此基础上，围绕记忆写入阶段的重复信息筛选开展轻量化改进，并关注新事实和时间信息的保留。通过在相同存储或上下文预算下比较问答表现、记忆规模、检索时延和模型调用开销，分析记忆质量与资源使用之间的关系

> [!quote]- 错误恢复｜白静｜简介原文
> 基于大语言模型的智能体能够通过多轮推理与工具调用完成复杂任务，但在长程交互过程中容易出现工具调用错误、任务规划偏差及环境状态理解错误等问题，且错误可能逐步累积，导致任务执行失败。现有方法通常依赖简单重试或重新规划，缺乏对历史错误信息的有效利用以及错误根因的定位。本课题拟研究多轮交互任务中的智能体错误恢复方法，通过失败轨迹分析与恢复策略优化，提高智能体在复杂任务中的执行成功率与鲁棒性，并在典型多轮交互智能体任务中验证。

> [!quote]- 并行优化｜朱虎明｜简介原文
> 基于大模型的Agent正从单轮问答走向多步推理、工具调用、检索增强与多Agent协作的复杂工作流，系统的性能瓶颈也随之发生了本质变化。推理成本与时延已成为Agent规模化落地的最大障碍，系统级并行计算性能优化因此成为人工智能技术系统领域的研究热点。
>
> 本次毕业设计要求学生理解大模型推理系统的工作原理与关键性能指标，会对典型Agent负载（ReAct、多Agent协作工作流等）进行并行计算性能剖析、定位瓶颈，并实现一种或多种优化手段，在真实工作负载上量化验证端到端加速效果。
